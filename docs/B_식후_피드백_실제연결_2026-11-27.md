# 식후 피드백 실제 저장·API 연결 인수인계

2026-11-27 한국 시간. 기반 main `eaea05e`. 원래 전용 브랜치의 커밋 두 개는 최신 main 위로 rebase했다. main 병합·푸시는 하지 않는다.

## 이번 완료 범위

- `meal_feedback_store.py`: A의 PostgreSQL connection/identity를 재사용하는 전용 SQLite/PostgreSQL 저장 어댑터. 가구·식사·저장 item·세션 참여자·구성원 소속을 확인한다.
- `meal_feedback_api.py`: 인증된 GET/PUT, 요청 검증, 400/401/403/404/409/503 매핑, no-store.
- `meal_feedback_app.py`: 공통 app.main/AI/음성 모델을 import하지 않는 별도 Flask factory. 실제 DB만 사용하고 초기화·fake 성공이 없다.
- `meal_feedback_schema.sql` + `scripts/setup_meal_feedback.py`: A 검토용 전용 schema와 명시적 1회 설치 도구. 기존 A migration/repository 파일은 그대로다. 테스트 DB에만 적용했다.
- 기존 배포 진입점 `app/b_runtime.py`는 수정하지 않았다. GET/PUT 허용 목록·Blueprint·readiness를 포함한 적용 가능한 패치를 별도 제공한다.

SQLite는 BEGIN IMMEDIATE, PostgreSQL은 기존 권한 잠금 → 대상별 advisory transaction lock → 관계 행 FOR SHARE → CAS 순서다. 최초 생성은 UNIQUE(record_id,member_id) + ON CONFLICT DO NOTHING, 수정은 WHERE revision 조건과 영향 행 수를 검사한다. 동일 재시도는 행·revision·updated_at을 늘리지 않는다. 서로 다른 오래된 값은 409다. 요청 중 새 DB/테이블/seed를 만들지 않는다.

읽기는 PostgreSQL READ ONLY, SQLite query_only transaction으로 실행한다. 저장·commit 실패는 rollback 후 503이고 응답에 driver 세부·접속 정보·원문을 넣지 않는다. 평가 사실은 현재 행으로부터만 파생하며 preference_evidence에 추가하지 않는다. 학습 매핑·가중치는 계속 pending_mapping이다.

## 실제 연결 상태 구분

| 대상 | 상태 |
|---|---|
| 독립 Flask 앱의 GET/PUT | 등록·실행·검증 완료 |
| 임시 SQLite/PostgreSQL 영속 저장 | 실제 SQL로 검증 완료 |
| 다른 세션 B 배포 런타임 | 패치만 준비, 미적용 |
| app.main 기존 서버 | 변경 없음, 피드백 미등록 |
| 운영 Supabase schema·실데이터 | 적용/변경 없음 |
| C 디스플레이·음성 입력 | 계약과 mock만 제공, 실제 UI 미연결 |
| 외부 AI·추천 점수 반영 | 호출·수정 없음 |

## A 적용 사항

전용 schema 후보는 기존 meal_records와 members를 참조하는 단일 테이블이다. 기존 테이블 ALTER, 식사 완료, 재고 차감, 개인화 table append는 없다. 설치 도구는 기존 기반 테이블이 있어야 동작하고 재실행은 이미 있는 테이블을 덮어쓰지 않고 실패한다.

운영 채택 전 A가 확인할 것:

1. 후보를 공식 migration 체계에 넣을지, 이 명시 설치 도구를 별도로 사용할지 선택한다. 아직 001~008 이력에 새 version을 기록하지 않았다.
2. 개인 schema에서 migration 역할로만 설치한다. PostgreSQL public schema에는 설치를 거절한다. 운영 schema를 Data API exposed schemas에 추가하지 않는다.
3. 기존과 같은 제한된 server role에 schema USAGE, meal_feedback SELECT/INSERT/UPDATE를 명시적으로 부여한다. 테이블 소유권·schema CREATE·SUPERUSER·BYPASSRLS는 필요 없다. 새 identity sequence도 필요 없다.
4. PUBLIC/anon/authenticated에는 권한을 주지 않는다. 설치 도구는 PUBLIC 권한 및 존재하는 anon/authenticated 역할의 권한을 철회한다. 가구 격리는 기존 서버 authorize와 객체 검사로 수행한다. 새 Supabase JWT나 RLS 정책을 임의로 만들지 않았다. 별도로 RLS를 도입할 경우 앱 역할 정책도 A가 검증해야 한다.
5. record/member FK에 cascade를 새로 가정하지 않았다. 기존 삭제·보관 정책과 연결을 검토한다. 운영 백업/복구와 TLS·권한 검증은 기존 A 절차를 따른다.

운영 적용은 이번 세션에서 실행하지 않았다. 명령 형식은 다음과 같다. 관리자가 의도한 DB/schema를 환경에 주입한 뒤에만 실행한다.

```text
python scripts/setup_meal_feedback.py
```

이 도구는 연결 환경 파일을 자동으로 읽지 않으며, 기존 A migrations를 대신 실행하지 않는다. SQLite는 명시적 KINI_DB_BACKEND=sqlite와 기존 절대 경로 KINI_DB_PATH가 필요하다. PostgreSQL은 KINI_DB_BACKEND=postgres, 명시적 비공개 KINI_DB_SCHEMA와 기존 DB 연결 환경을 사용한다. 누락/오류를 SQLite로 대체하지 않는다.

## 평가 선택지와 독립 앱 실행

확정된 방향은 선택 평가·패스·지정 평가자 없음·해당 식사 참여자 응답·디스플레이/음성 입력이다. 선택지는 사용자 승인 추천안을 확인해 deploy/b/meal-feedback-options.v1.json으로 매핑했다. 계약 문서의 승인 선택지 표를 따른다. 이를 보완한다는 이유로 임의의 운영 코드를 추가하지 않았다.

승인된 선택지가 생기면 절대 경로 JSON 파일을 `KINI_MEAL_FEEDBACK_OPTIONS_FILE`에 지정한다. 형식은 taste/seasoning/difficulty 각각 문자열 코드 배열이다. **테스트의 test_*나 mock_*는 운영 선택지가 아니다.** `FeedbackOptions` 객체를 factory에 직접 주입할 수도 있다.

```python
from app.meal_feedback_app import create_app
from app.services.meal_feedback import FeedbackOptions

# approved_codes는 기획·B가 승인한 세 항목 코드 배열의 dict.
app = create_app(options=FeedbackOptions(approved_codes))
```

환경 파일을 사용한 로컬 통합 진입점:

```text
python -m flask --app app.meal_feedback_app:create_app run --host 127.0.0.1
```

이 앱에는 기존 로그인 endpoint가 없다. 기존 인증 API가 발급한 동일 DB의 가구 세션 토큰을 사용한다. 선택지 미설정이면 GET/skip은 가능하고 submitted는 명시적 503이다. 설정 파일이 잘못되면 앱 생성을 실패시킨다. 이 앱 자체는 운영 런타임의 TLS/schema/역할 배포 검사를 대신하지 않으며 기존 배포를 교체하지 않는다.

## 배포 세션이 검토할 연결 패치

파일: `docs/patches/meal_feedback_b_runtime.patch`.

다른 worktree의 `app/b_runtime.py`를 읽기만 했으며, 검증 당시 배포 브랜치 HEAD는 `8c477f1`이었다. 패치는 현재 파일 기준으로 생성했다. 포함 내용:

- RESOURCE_ROUTES에 두 피드백 GET/PUT regex 추가.
- 내부 앱에 새 Blueprint/SQL 서비스 등록 및 승인 options 파일 로드.
- 외부 proxy dispatch의 허용 HTTP 메서드에 PUT 추가. 기존 허용 목록으로 다른 PUT은 계속 차단.
- readiness가 meal_feedback 테이블도 확인하도록 추가. schema 적용 전에 패치하면 readiness가 실패하는 것이 정상이다.

배포 담당이 전용 기능 커밋을 반영하고 A schema·역할을 준비한 뒤, 아래로 현재 파일에 적용 가능한지 먼저 확인한다. Windows checkout의 줄바꿈이 달라지면 `--ignore-space-change`를 함께 쓸 수 있다. 이번 세션에서는 check만 수행했다.

```text
git apply --check docs/patches/meal_feedback_b_runtime.patch
git apply docs/patches/meal_feedback_b_runtime.patch
```

app.main 경로를 쓰는 경우에는 대신 다음을 등록한다. 두 진입점 변경을 동시에 강제하지 않는다.

```python
from app.meal_feedback_app import load_feedback_options
from app.services.meal_feedback import MealFeedbackService
from app.services.meal_feedback_api import create_meal_feedback_blueprint
from app.services.meal_feedback_store import SqlFeedbackStore

service = MealFeedbackService(SqlFeedbackStore().transaction, options=approved_options)
app.register_blueprint(create_meal_feedback_blueprint(service))
```

공통 경로 수정은 담당 배포 세션이 수행한다. 기존 proxy의 admission/deadline·AI·privacy gateway는 이 커밋이 수정하지 않는다. 패치가 적용되는지·Python 문법은 확인했지만, 패치 후 클라우드 런타임 end-to-end 실행은 아직 하지 않았다.

## C 연결

저장된 record_id와 응답하는 member_id를 사용해 계약의 GET/PUT을 호출한다. 초기 패스는 API 호출 없이 닫는다. 기존 평가를 보는 중 그냥 패스/닫기도 기존 값을 보존한다. 참여자가 확인된 뒤의 skipped PUT은 그 사람의 평가만 처리하며 명시적 기존 평가 철회와 구분한다. 한 명의 skip이 식사 전체 평가를 끝내지 않는다.

화면 로딩/저장 성공/입력 오류/401/403/404/409/503을 구분한다. 409이면 재조회 후 사용자 확인을 받는다. 503이나 timeout에서 성공 화면으로 이동하지 말고 입력을 유지한다. 승인 코드와 revision을 포함한 동일 재시도는 서버가 멱등 처리한다.

음성은 승인 코드와 참여자를 확인한 뒤 같은 구조화 PUT으로 보내는 입력 경로다. 이번 API는 원본 음성이나 자유 발화를 받지 않으며 새 STT·화자 인식·voice endpoint를 제공하지 않는다. 기존 mock은 합성 예제임을 유지한다.

## 배포 통합 정정 (2026-11-27)

선택지 재승인은 불필요하다. 승인 파일과 안정 코드는 계약 문서에 기록했다. 옵션 미설정 503은 설정 실패 경로이며 미확정 기획 때문이 아니다.

1로 켜면 테이블 컬럼과 PostgreSQL SELECT/INSERT/UPDATE 권한을 추가 확인한다. 요청 시 DDL은 없다.
