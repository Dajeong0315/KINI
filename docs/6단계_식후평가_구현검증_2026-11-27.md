# 6단계 식후 평가 구현·검증

작업·검증일: 2026-11-27 KST. **6단계 구현·실제 서버·PC 화면 검증 완료.** 사용자 후속 결정에 따라 기존 구현을 재사용·수정했다.

## 확정 정책

- **식사당 평가 1건**. 해당 식사 참여자 누구나 맛·간·난이도에 응답할 수 있다. 0인분이거나 섭취 항목이 없어도 식사 세션 참여 관계가 있으면 가능하다. 사전 지정 평가자는 없다.
- 최초 응답자 ID는 기록용으로 유지하며 다른 참여자도 같은 평가를 조회·수정한다. 수정·네트워크 재시도는 새 평가로 집계하지 않는다. API의 기존 참여자 경로는 권한 확인용이고 현재 평가의 자원 키는 `record_id` 하나다.
- 식사 저장 성공 뒤 평가하기/건너뛰기를 한 번 제공한다. 보고서에서 수동 조회·수정할 수 있다. 자동 재질문·알림은 없다.
- 초기 건너뛰기와 기존 평가 화면 닫기는 PUT 없이 종료한다. 기존 평가를 지우거나 중립·불만으로 바꾸지 않는다. 전부 비운 상태의 제출은 거절하고 패스를 안내한다. 명시적 철회 UI는 추가하지 않았다.
- 맛은 **해당 메뉴의 추천 순위에만**, 간·난이도는 **해당 메뉴의 조리 안내에만** 반영한다. 알레르기·영양·건강 제한·재고·조리량은 평가로 바꾸지 않는다.

## 기존 구현 재사용과 변경

- 기존 `MealFeedbackService`, SQL 어댑터, 인증 GET/PUT, 선택지 파일·수정 revision 계약을 재사용했다. 별도 담당자의 재구현을 요청하지 않았다.
- migration `010_meal_feedback.sql`: 기본 키 `record_id`로 식사당 1건을 DB에서도 보장한다. PostgreSQL의 식사 단위 advisory lock, 행 CAS, revision 검증으로 다른 참여자의 최초 제출 경합과 오래된 수정 덮어쓰기를 막는다. 같은 값 재시도는 시각·revision을 늘리지 않는다.
- 평가 대상은 `meal_records → meal_sessions → meal_session_participants → members.household_id`로 확인한다. 다른 가구·비참여자는 404, 무인증·만료는 401, 조회 전용 쓰기는 403이다. 최초 응답자가 아닌 참여자로 조회해도 같은 평가를 반환한다.
- raw 현재 평가만 읽고 `preference_evidence`에 복제·append하지 않는다. 수정은 같은 행 교체, skipped는 효과 없음이다. 기존 식사 섭취 기반 증거는 그대로 유지한다.
- 화면은 참여자 확인, 맛·간·난이도별 일부 응답, 저장·수정·닫기, 오류 후 입력 보존, 409 후 명시적 최신 평가 재조회, 재로그인 후 기존 평가 복원을 제공한다.
- 비동기 조회 후 생성된 평가 버튼이 계속 비활성으로 남는 문제를 UI 시험에서 발견해 수정했다. 기존 비활성 mock 화면은 feature OFF일 때 유지된다.
- `app.main`과 B runtime 모두 명시적 feature flag와 승인 선택지 파일을 사용한다. 로컬은 별도 DB에 schema를 설치하고 절대 경로·설정을 지정해야 한다. 요청 중 DDL·seed·fake 저장은 없다.

## 개인화 정책 v1과 한계

`meal_feedback_personalization.py`가 현재 가구의 확정 평가 중 이번 추천 참여자와 과거 식사 참여자가 겹치는 자료를 읽는다. 응답자 개인 취향으로만 귀속하거나 모든 재료의 선호로 확대하지 않는다.

- 메뉴별 최근 식사 평가 최대 5건의 현재 맛 평가를 사용한다. 만족 +2, 보통 0, 불만족 -2의 평균을 사용하며 기존 개인화 총점 상한 ±15 안에서만 적용한다. 생략·skip은 표본으로 넣지 않는다.
- 기존 상한에 걸린 경우 설명 근거에는 실제 적용된 점수와 원래 조정량을 구분한다. 과도한 누적을 막기 위한 초기 제한값이며 실제 사용자 품질·최적 가중치를 입증한 수치는 아니다.
- 간·난이도는 같은 메뉴의 최근 응답을 안내 문구로 제공한다. ‘짜다/싱겁다’는 영양 수치의 측정 결과가 아니며 나트륨값·양념량·건강 제한을 자동 변경하지 않는다. 어려움 평가는 단계 미리 읽기·재료 준비 등 일반 조리 안내로 연결한다.
- 영양·알레르기 등 후보 제외를 통과한 메뉴에만 맛 점수를 적용한다. 평가에 의한 안전 제외 우회는 없다. OpenAI·Ollama 보조 검사 호출은 0회이며 기존 rules-only 모드를 유지한다.

서버 canary 실측 1회씩: 평가 GET 3.241초, 최초 PUT 3.386초, 동일 재시도 3.313초, 수정 3.398초, 재조회 3.190초, 다음 추천 15.875초. 동시 부하·백분위·휴대폰 지연이 아니다. 서버 예산 18초·브라우저 20초 유지. 실제 휴대폰에서 6단계 새 평가 화면을 직접 확인한 결과는 아직 없으며 PC 화면 크기 시험과 구분한다.

최종 release 재시작 뒤 평가 1행·revision 4와 다음 추천의 `raw_adjustment=2`, 상한 적용 후 `adjustment=0`, `personalization_score=15`를 확인했다. 기존 선호 신호가 이미 상한에 도달한 이 시연 자료에는 추가 점수를 붙이지 않는다. 상한 미도달 합성 비교에서는 +2/−2에 따른 순위 변경과 skip 복원이 통과했다. 첫 최종 점검 스크립트는 무조건 +2가 적용된다고 가정해 실패했으며, 실제 상한 동작을 대조해 점검 기준을 수정했다. 제품의 상한을 완화하지 않았다.

시험 중 과거 ‘참여자별 별도 평가’ 기대값을 새 식사 단위 정책으로 갱신했고, 새로운 비동기 모달의 비활성 버튼을 수정했다. 브라우저 시험의 닫기 버튼 selector 중복은 테스트에서 고쳤다. 최초 맛 점수 시험은 기존 다양성 점수 차이가 ±2보다 커 순서가 바뀌지 않았으므로, 동등한 이전 식사 횟수 조건으로 비교를 바로잡고 점수 증가·순위 변경·skip 복원·안전 제외를 검증했다.

운영 DB에 장애 주입·파괴적 시험을 하지 않았다. 서버 시험은 에이전트가 만든 합성 식사 기록 **1번**만 사용했다. 사용자의 휴대폰 시험 기록 3번은 변경하지 않았다. 같은 시연 계정에서 이 에이전트 검증 평가가 조회될 수 있다.

## 배포·권한·복구

- 최종 release: `step6-20261127-7190d25e3091`, source manifest 158개 파일 해시 확인.
- archive SHA256: `eae7ac735586dd20e2289dcb582ecdbd1bd93802867eb28e9fb90d318d9bc7ec`.
- 먼저 canary `step6-20261127-08038b70518d`에서 실제 흐름과 HTTPS UI를 확인했다. 최종 변경은 개인화 상한에서 실제 조정량을 보고하는 부분과 계약 주석이다. 관련 정책 시험을 재실행했다.
- Supabase migration 001~010 적용, 새 테이블 소유자 `kini_migrator`, RLS 활성. `kini_app` SELECT/INSERT/UPDATE 허용, DELETE 없음, anon 읽기 없음. 기존 public 카탈로그 권한을 확장하지 않았다.

- root 전용 backup `/etc/kini-b/runtime.env.before-step6-20261127`과 metadata `/etc/kini-b/step6-rollback.json`을 준비했다.
- 이전 9-migration release는 재시작 시 엄격한 migration 검사에 걸릴 수 있다. 따라서 **schema 10 호환 rollback release** `/opt/kini-b/releases/step6-rollback-compatible-20261127`를 별도로 만들고 DB 점검 통과를 확인했다. 기존 검증된 5단계 코드에 migration 010 파일만 추가한 호환 묶음이며 원래 release는 보존했다.
- 복구: 현재 환경의 feedback flag를 0으로 변경 → current를 위 호환 release로 원자 전환 → kini-b 재시작 → readiness·인증 재조회 확인. DB 평가·migration 이력을 삭제하지 않는다. 환경 파일 전체 복원으로 이후 추가된 비밀을 덮어쓰지 않는다.
- canary와 전용 테스트 DB 컨테이너를 정리하고 최종 readiness를 확인한다. 시연 자격과 실제 환경 파일은 저장소에 포함하지 않는다.

이번 6단계 변경은 아직 커밋·푸시하지 않았다. 이전 `750c848`은 1~5단계 커밋이며 6단계 배포 커밋으로 표시하지 않는다. 7·8단계는 이 문서의 완료 범위에 포함하지 않는다.
