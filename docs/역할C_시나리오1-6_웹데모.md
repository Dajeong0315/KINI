# 역할 C — 기존 메인페이지 시나리오 1~6

브랜치: `feature/mobile-recommendation-flow`

## 구현 기준

기존 `index.html`의 오늘·추천·레시피·조리·기록·냉장고·리포트·프로필 화면과 냉장고/모바일 테마를 유지한다. 새 페이지로 교체하지 않고 데이터와 컨트롤을 연결했다. 기본 `style.css`는 수정하지 않았으며 추가 컨트롤은 `scenario.css`로 보완했다.

FigJam 시나리오 기준:

1. 초기 설정 (`80:573`)
2. 식사 시작·추천 (`80:610`)
3. 조리 중 대화·변경 (`84:1202`)
4. 식사 후 섭취 기록 (`84:1687`)
5. 식재료 입고·인식 (`93:818`)
6. 일상 관리·리포트·알림 (`93:840`)

최신 개발 아키텍처는 별도의 `KINI_Workflow_v2` (`151:1802`)를 따른다. 현재 C 구현은 그 구조의 **UI mock**이며 OpenAI/Ollama/YOLO/Supabase/SQLite와 연결하지 않는다. 운영용 추천·영양·안전 정책을 구현하거나 수정한 것이 아니다.

## 데이터와 실행

- `scenario_demo.js`: 합성 가족·재료·레시피·영양값과 mock 상태 전이. 운영용 검증 엔진으로 사용하지 않는다.
- `api_client.js`: UI와 데이터 공급자 사이 경계. 추후 A/B가 확정한 로컬 API로 교체할 위치.
- `app.js`: 기존 화면의 DOM 렌더링·입력·이동·오류 처리.
- `scenario.css`: 폼·다이얼로그·경고 등의 추가 스타일.

서버 의존성이 준비됐다면 기존대로 `python -m app.main`으로 실행하고 `http://127.0.0.1:5000`에 접속한다. 기존 main은 `pydantic` 등 requirements 의존성을 요구한다. C 작업에서 requirements나 환경 설정은 수정하지 않았다.

화면은 기본적으로 예시 가족으로 시작하며 초기 설정은 가족 메뉴 또는 상단 가족 이름에서 연다. 모든 변경은 탭 메모리에만 남는다. 새로고침·상단 ‘테스트·초기화’에서 초기화된다. localStorage·외부 분석 로그·브라우저 DB·외부 API를 사용하지 않는다. 실제 민감정보를 입력하지 않는다.

## 시나리오별 확인 순서

### 1. 초기 설정

상단 가족 이름 또는 가족·프로필 → 초기 설정.

- 기존 예시 가족 불러오기, 최소 설정, 전체 설정, 현재 가족 수정, DEMO 초대 코드 분기.
- 새 가족명 → 구성원 추가·제거 → 예시 목표/평소 식사량/제외 재료 → 설정 확인 → ‘수정할게요’ 또는 ‘맞아요’.
- 최소 설정은 이름과 구성원만 받고 나머지는 기본값으로 시작.
- 전체 설정은 구성원별 당뇨 여부(미입력/없음/있음)와 사용자 설정 식사 주의사항(200자)을 선택 입력한다. 미입력은 ‘없음’으로 간주하지 않는다. 확인·수정 화면에서 유지하며, 일반 프로필 목록에는 주의사항 등록 여부만 표시한다.
- 건강정보는 현재 탭의 메모리에만 존재한다. 추천 후보에는 병명·주의사항 원문을 넣지 않고 ‘건강 조건에 맞춘 식단 미검증’이라는 일반 경고만 표시한다. 당뇨를 이유로 식사량·영양 목표·추천 적합성을 자동 변경하지 않는다.
- 실제 연동 시 이 필드는 로컬 개인 프로필 API/DB에만 저장해야 한다. 외부 LLM·운영 지표로 전체 화면 상태를 보내면 안 되며, B의 최소화·허용 필드 계약을 별도로 적용해야 한다. 현재 mock 분리를 실제 개인정보 전송 게이트로 간주하지 않는다.
- 실제 로그인·음성 인증·초대 서비스·건강검진 연동·암호화 저장은 미구현.
- 기존 식사 기록의 구성원 ID가 다른 사람으로 바뀌지 않도록, 기록이 있는 탭에서는 가족 재정의를 막는다. 새 가족 설정은 데모 초기화 후 진행.

### 2. 메뉴 추천

오늘 화면 참여자 선택 → 추천 → 균형/컨셉, 조리 시간, 맛, 구매 허용 선택 → 후보 → 근거 → 상세.

- 참여자 미선택 오류.
- 예시 6종에서 조건에 맞는 3개 후보와 추가 후보를 표시. 더 보기는 기존 후보를 반복하지 않는다.
- 조건·참여자·재고·다음 목표 변경 시 이전 추천과 선택 해제.
- `demo_data`, 확인 필요, 제외 사유 표시. 영양은 합성 값이다.
- 상단 ‘테스트·초기화’에서 api_error/privacy_blocked/no_safe_recommendation/stale_unvalidated를 선택하고 다음 추천 요청. 실패 시 이전 카드와 선택은 제거.
- 정상으로 되돌린 뒤 다시 추천하면 복구.
- 구매 허용으로 후보를 찾았어도 필요한 재고를 등록하기 전 조리는 시작하지 못한다.

### 3. 조리 중 대화·변경

레시피에서 데모 확인 체크 → 조리 시작.

- 레시피를 유지하고 기본 단계 이동. 사용자가 질문하기 전 음성이나 메시지를 자동으로 내보내지 않음.
- 질문·발화 예시: ‘두부 100g만 넣을게’, ‘버섯 빼줘’, ‘조리 끝났어’.
- 입력에서 얻은 변경은 확인 폼의 후보이며 자동 적용하지 않음. 전체 사용량 g 입력·확인 후 반영.
- 불확실한 반 모/반 통 등은 임의 중량으로 변환하지 않음.
- 변경 후 예시 영양 재계산. 재고 부족·제외 재료·음수·모든 재료 제거는 거부.
- 조리 종료 시 사용 재료 확인 → 추가 변경 또는 섭취 기록.
- 조리 취소는 재고 차감·식사 기록을 만들지 않음.

### 4. 섭취 기록

조리 완료 확인 → 구성원별 기본 섭취량 초안 → 예외 수정 → 확인 → 저장 → 리포트.

- 기본량은 프로필에 설정한 평소 인분만 사용하며 건강 목표 때문에 임의로 바꾸지 않음.
- 직접 입력, 음성 발화 예시(‘하늘 0.5인분’, ‘지아 안 먹었어’), 사진 선택 후 수동 확인 분기.
- 사진은 로컬 미리보기만 하며 메뉴·중량을 AI로 인식했다고 표시하지 않음.
- 조리 기록은 총 섭취량이 만든 인분을 초과하면 거부. 안 먹은 구성원은 0인분 가능.
- 최종 사용 재료의 영양과 개인별 인분으로 저장. 중복 저장 방지.
- 조리 사용량 전체를 한 번만 재고에서 차감(남은 음식의 섭취량과는 별개).
- 오늘 화면 ‘이미 먹은 식사 기록’은 예시 메뉴를 직접 선택하며 냉장고 재고를 차감하지 않음.

### 5. 입고·인식

냉장고 → 입고 인식 데모 → 확실/불확실/미매칭 예시.

- 확실: 당근 200g 초안을 확인 후 반영.
- 불확실: 실제 이름·중량 확인 전 등록 불가.
- 미매칭: ‘냉장만두 한 봉지’ 등을 실제 중량 확인 후 임시 등록. 기준 영양정보가 없음을 표시하고 자동 추천·계산에서 제외.
- 실제 YOLO·카메라·ThinQ·동기화 호출은 없음.
- 재료 등록 또는 상세 › 수정 → 재고·홈 배너·다음 추천에 반영.
- 소비기한 경과·0g·임시 재료는 사용 가능한 재고에 포함하지 않음. 이는 mock 분기이며 제품 안전 판정이 아님.

### 6. 리포트·일정

리포트 → 개인/가족, 오늘/최근 7일 → 기록 합계·추이·내역.

- 기록이 없으면 0과 빈 안내. 이전 화면의 고정 82%나 가짜 과거 데이터 사용하지 않음.
- 다음 목표 선택은 mock 추천의 설명 조건에 반영. 운영용 점수·건강 정책 변경은 아님.
- 오늘 마감은 확인 상태이며 추가 기록 가능. 추가 기록이 있으면 해당 날짜의 마감 상태 해제.
- 직접 설정한 일반 보조식품 이름·시간 → 오늘 체크/해제.
- 처방·복용량 추천, 실제 푸시·예약 알림, 백그라운드 알림은 없음.

## 자동 검증

```powershell
node --check app/static/app.js
node --test tests/ui/scenarios.test.cjs
.\.venv\Scripts\python.exe -B -m pytest tests/ui/test_template.py -q -p no:cacheprovider
```

브라우저 E2E에서는 기존 테마와 390px/PC 폭에서 가로 넘침, 다이얼로그 포커스·닫기, 레시피 선택, 오류 복구, 섭취량 저장까지 별도 확인한다. 모델·공식 영양 데이터·외부 DB·보안 통합 검증을 이 테스트로 대체하지 않는다.
