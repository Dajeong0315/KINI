# 5단계 실제 휴대폰 통과 및 재고·저장 확인

확인일: 2026-11-27 KST.

**사용자가 실제 휴대폰에서 전체 절차를 완료했고 다른 문제가 없었다고 보고했다.** 미출고 확인란이 맞으면 통과라는 조건을 제시했으며, 배포 코드의 문구가 정확히 일치한다. 3단계와 5단계 실제 휴대폰 확인 대기를 해소한다. 기종·브라우저 버전은 미확인이고 휴대폰 응답 시간은 측정하지 않았다. 직접 관찰한 PC 자동 시험과 사용자 보고를 구분한다.

## ‘식재료가 두 개 생김’ 확인

실제 Supabase에 대해 읽기 전용으로 시연 가구의 재고와 적용 이벤트를 대조했다.

- 당근의 기존 큰 재고 묶음은 ID 3이다.
- 10g 묶음 ID 4는 에이전트의 5단계 정상 API 검증에서 생성한 입고 이벤트 7에 연결된다.
- 10g 묶음 ID 5는 이후 휴대폰 시험에서 생성된 입고 이벤트 11에 연결된다.
- 두 10g 항목은 서로 다른 입고 이벤트 각 1건이며, 이번 입고 한 건이 두 재고 행으로 복제된 증거는 없다. 같은 시연 계정에 에이전트의 검증용 입고가 남아 있어 비슷한 항목이 함께 보였다.

기존 `inventory_events.confirm`의 `stock_in` 계약은 항상 새 재고 묶음을 만든다. 입고 시점·소비기한이 서로 다른 재고를 구분하기 위한 방식이다. 같은 재료의 기존 행 수량을 덮어쓰거나 합치지 않는다. **같은 재료의 전체 보유량은 각 묶음의 남은 g 합계**다. 출고는 선택한 재고 묶음 ID와 중량을 확정하고 차감한다. 기존 `client_event_id`와 확정 fingerprint로 같은 이벤트 재전송의 중복 반영을 막는다.

## 미출고 확인란

`app/static/app.js`의 수동 출고 확정 확인란 문구는 다음과 같다.

> 아직 출고하지 않은 재료이며 위 재고와 중량을 확인했습니다

사용자가 확인한 문구가 맞다. 이미 A에서 출고 확정된 재료를 새 수동 출고로 다시 확정하지 않겠다는 확인이다. 기존 확정 출고는 기존 이벤트 ID로 연결하는 별도 흐름을 유지한다.

## 식사 기록 3건 확인

실제 저장된 `meal_records`와 `cooking_sessions`를 읽기 전용으로 대조했다.

| 식사 기록 ID | 식사 세션 / 조리 세션 | 생성 근거 |
|---|---|---|
| 1 | 3 / 3 | 에이전트 3단계 정상 저장 검증 |
| 2 | 4 / 4 | 에이전트 5단계 조리 변경·저장·재조회 검증 |
| 3 | 5 / 5 | 이후 사용자의 실제 휴대폰 전체 흐름 |

각 세션은 completed이며 기록당 개인 섭취 항목은 1개다. **같은 조리를 세 번 저장한 상태가 아니다.** 현재 시연 계정에 보이는 총 3건 중 에이전트 검증 기록이 2건, 이번 사용자 시험 기록이 1건이다.

기존 화면의 저장 중 가드와 완료 후 비활성 상태, 서버의 조리 행 잠금·완료 상태 검증 및 출고 이벤트 단일 사용 계약을 유지했다. 이 확인에서 운영 쓰기·데이터 삭제·수정·실패 주입이나 추가 모델 호출은 실행하지 않았다. 새 제품 수정이 필요하다는 근거가 없어 불필요한 저장 로직 변경·테스트 재실행은 하지 않았다.

## 완료 판정

- 3단계: 실제 휴대폰 저장·재조회와 확인란 확인을 사용자 보고로 완료.
- 4단계: 보조 검사·OpenAI 설명 비활성, 호출 0회·USD 0이라는 사용자 결정 범위로 완료. 실제 AI 품질·성능 완료가 아니다.
- 5단계: 별도 PostgreSQL 오류·동시성 시험, 실제 서버 정상 흐름, PC 모바일 화면, 실제 휴대폰 사용자 확인까지 통과.

**1~5단계의 첫 배포 가능한 기능 묶음 확인을 완료했다.** 현재 기능 범위는 승인된 public 카탈로그 기반 규칙 추천·고정 설명·A 출고·B 섭취 저장·이력·영양 리포트이며, 원재료 영양 추정치라는 한계를 유지한다. 배포 소스·설정·복구와 시험 수치는 [통합 검증](5단계_핵심흐름_통합검증_2026-11-27.md)에 있다. 구현 커밋·푸시는 하지 않았으며 6~8단계는 이 완료 판정에 포함하지 않는다.
