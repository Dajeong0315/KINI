# Vision AI 서버 동시 실행 조건 확인

확인일: 2026-11-27 KST. 사용자 추가 확인 요청에 따른 읽기 전용 코드 점검이다.
기준 Vision 브랜치: `origin/feature/fridge-vision-yolo`, 커밋 `3963a44`.
Vision 코드·모델·DB를 수정하거나 서버에 배포하지 않았다.

## 확인한 구성

- 기본 모델은 `yoloe-v8m-seg.pt`(YOLOE 중형)이며 없을 때 다운로드하는 코드다.
- `YoloComparer`가 Ultralytics 모델을 로드·warmup한다. 사용자 이름표 비교에는 추가 CLIP ViT-B/32를 CPU에 로드한다.
- `main.py`는 OpenCV 카메라/영상 입력과 `cv2.imshow`·키보드 확인을 사용하는 프로그램이다.
  기본 영상 경로도 Windows 로컬 경로다. 기존 파일을 Linux headless API 서비스로 그대로 실행할 수 있다고 가정하지 않는다.
- 별도 `openai` 엔진은 외부 Vision API를 호출한다. 이번 B 배포에서는 활성화·호출하지 않는다.
- Vision requirements는 범위 지정이며 CPU PyTorch/CLIP 등을 포함한 재현 lock 및 실제 서버 RAM/지연 측정은 미확인이다.
- 자체 Supabase 재고 동기화가 있다. 이것을 B 실행기나 A의 권한·표준 재료·중량·단일 출고 계약에 연결했다고 주장하지 않는다.

## 현재 서버 자원과 판단

승인한 B EC2는 m7i-flex.large, 2 vCPU, 8 GiB, gp3 40 GiB, GPU 없음이다.
첫 SSH 확인에서 OS 표시 메모리 7,776 MiB, available 7,279 MiB(모델 설치 전), 루트 여유 약 36 GiB였다.
B 서비스 MemoryMax 1 GiB, Ollama MemoryMax 6 GiB는 각각 상한이며 실제 상시 사용량이 아니다.
이 상한을 그대로 두고 Vision까지 동시에 올리면 여유를 보장할 수 없다.

Vision까지 최종 서버에 배치해야 한다는 요구는 인수인계에 반영한다.
현재 서버가 Vision 동시 실행까지 충족한다는 사양 확정/성능 판정은 보류한다.
GPU 필수 여부도 모델명만 보고 단정하지 않는다. CPU 추론 가능성과 발표에서 필요한 지연은 별도다.

## Vision 담당과 맞출 다음 연결 단위

1. 발표에서 사용할 정확한 모델·weights/digest·입력 해상도·한 번에 받을 이미지 수·목표 지연·동시 요청 수 확정.
2. 카메라/화면은 기기 입력으로 두고, 서버는 인증된 before/after 이미지 또는 검증된 입력을 받는 headless 추론 계약으로 분리.
3. 이미지 원본의 개인정보·보존/삭제 정책, 요청/모델 timeout, Unknown/불확실 응답과 사용자 확인 계약 결정.
4. 인식 결과는 A 표준 재료·실제 g 확인·가구 권한·재고 이벤트 경계를 통해 연결. Vision 직접 저장을 임의로 운영 연결하지 않음.
5. 전용 프로세스·배포 디렉터리·메모리 제한으로 Vision 단독 및 B+Ollama 동시 RSS/CPU/지연을 측정.
6. 자원이 부족하면 모델 교대 로드·배치 분리·사양 변경안을 측정 결과로 비교. 유료 증설/추가 자원은 별도 승인 없이 만들지 않음.

이 항목은 B의 기존 추천 서비스 첫 실행 검증을 막는 선행 조건으로 삼지 않는다.
