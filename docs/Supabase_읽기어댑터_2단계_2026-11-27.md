## 구현

- `SupabasePublicCatalog`는 기존 PublicCatalog의 캐시·release 키·형식 검증을 재사용한다.
  SQL은 SELECT만 실행하며 public.data_sources, active_data_releases, data_releases,
  catalog_foods, catalog_recipes, catalog_recipe_steps, catalog_recipe_nutrients를 명시적으로 읽는다.
  기존 public UUID와 압축 영양 numeric 컬럼을 앱의 JSON/float 계약으로 정규화한다.
- `KINI_PUBLIC_CATALOG_BACKEND=app`가 기본이며 기존 경로를 유지한다.
  `supabase`를 명시하면 직접 읽기와 private 매핑 경로를 사용한다.
- 기존 catalog_ingredient_links는 private catalog_foods에 FK가 걸려 있으므로 public 행을
  연결하려면 복제나 FK 변경이 필요하다. 이를 피하기 위해 009는 private 영역에
  public_catalog_ingredient_links만 추가한다. ingredient_id·release_id·food_id·reviewed_at의
  기존 명시적 검토 계약을 유지하고 expected_name·review_evidence를 추가한다.
  public DDL/DML·카탈로그 복제·임의 FK 변경은 없다.
- source approved·release published·현재 pointer·검토 근거·정확한 외부 ID와 이름을 모두 확인한다.
  g 기준만 중량 영양 계산에 허용한다. ml를 g로 바꾸거나 NULL을 0으로 처리하지 않는다.
  cloud 모드에서 매핑 부재·누락 영양·미승인 자료를 demo 영양 성공으로 대체하지 않는다.
  DB/권한 오류는 예외로 실패하며 fake 결과를 만들지 않는다.
- 추천 inventory_usage에 nutrition_release_id·nutrition_food_id를 추가해 출처를 확인할 수 있다.
  public release/권리 상태와 private 매핑 해시를 추천 context에 넣어 변경 시 저장·재사용 검증을 무효화한다.
  기존 알레르기·성분표 확인·식품 안전 검사는 유지한다.
- check_server_db는 cloud 활성화 시 제한 앱 역할의 public SELECT와 migration 009를 점검한다.
  요청 처리에서 migration·매핑 생성은 실행하지 않는다.

## 실제 자료 검토와 최소 표본

`config/public_catalog_reviewed_sample.json`은 실제 Dashboard에서 읽은 recipe 3010의
생당근 10g과 food R106-041007601-0000의 명시적 연결 검토 근거다.
public source/release가 approved/published인 것을 확인했다.
이 파일은 운영 매핑을 자동 적용하지 않으며 로컬 ID·인분 수를 추측하지 않는다.
recipe servings는 NULL이므로 해당 reference를 완성된 1인분 추천 메뉴로 등록하지 않았다.

private에 보존할 데이터·확정 재료 ID와 앱 역할이 준비되면 검토된 입력만 링크한다.
실제 카탈로그를 읽는 CLI는 아래와 같다. 보호된 환경에서 접속 정보를 주입하며 출력에 비밀값은 없다.

```text
python scripts/check_public_catalog.py --food-id R106-041007601-0000 --grams 10 --recipe-id 3010
```

CLI는 READ ONLY 트랜잭션과 rollback을 사용한다. 원재료 10g의 영양 기여만 계산하고
레시피 전체·완성식·1인분 결과로 표시하지 않는다. 연결 자격이 없어 아직 실제 Supabase에서
이 Python CLI를 실행하지 않았다. Dashboard SQL 조회와 Python 실접속을 혼동하지 않는다.

## 검증과 제한

합성 단위/추천 검증은 별도 SQLite DB와 attached public 스키마만 사용한다.
실제 카탈로그 ID·영양값을 합성 테스트 값으로 속이지 않으며 테스트의 ID·수치는 별도 생성했다.
단위·누락/음수 영양·미승인/미게시·잘못된 이름·미검토/근거 없음·release 변경·DB 실패,
매핑 변경 해시·알레르기 제외·추천 출처 표시·인분 미확정 유지가 검증 대상이다.
최종 관련 검증 **68 passed / 34.31초**:

```text
python -m pytest -p no:cacheprovider tests/test_supabase_catalog.py tests/test_recommendation_provider.py tests/test_public_cache.py tests/test_server_db_preparation.py tests/test_recommendation.py tests/test_data_quality.py -q
```

실제 PostgreSQL 검증은 로컬 Docker의 신규 postgres:16-alpine 컨테이너만 사용했다.
운영 URL과 별도 `KINI_STEP2_TEST_URL`을 전달했다. Python 3.12.16/psycopg 3.3.9/pytest 8.4.2.
001~009 최초 적용 및 재실행, 별도 private schema, public numeric·UUID,
NOSUPERUSER/NOBYPASSRLS 역할·SELECT 전용 grant·명시적 RLS policy를 검증했다.
쓰기 권한 없는 역할로 어댑터 영양 조회 성공: **1 passed / 1.48초**.
일회용 컨테이너에는 실제 사용자 데이터나 운영 연결 정보를 넣지 않았다.
검증 종료 후 이번 전용 컨테이너를 중지·제거했으며 다른 컨테이너는 변경하지 않았다.

실제 프로젝트의 private schema는 없고 서버는 아직 합성 SQLite다.
현재 2단계 완료 기준인 **실제 앱 역할 연결의 추천 결과**는 미완료다.
로컬 SQLite는 보존한 채 백업·변환·건수/FK 검증 계획만 준비돼 있으며 이전 실행은 하지 않았다.

## 적용 전 남은 경계

운영 적용은 이전 사용자 지시의 “계획만으로 main 직접 푸시나 운영 데이터 변경 승인을 가정하지 않는다”를 따른다.
다음 변경은 아직 실행하지 않았다:

1. 관리 역할로 기존 public을 보존하고 kini_private를 만들며 검토한 001~009를 적용.
2. migration 소유 역할과 NOSUPERUSER/NOBYPASSRLS 앱 로그인 역할 분리.
   앱에 private 사용·필요 테이블 DML, public 위 7개 테이블 SELECT만 부여.
   RLS는 앱 역할로 실제 읽을 수 있도록 기존 정책을 확인하고 필요한 SELECT 정책 변경 범위를 검토.
3. 서버의 보호된 환경에 TLS verify-full·CA·앱 연결을 설정. 비밀번호를 채팅/Git에 넣지 않음.
4. 실행 중인 B 배포 c6be1e0의 미병합 코드를 보존·통합한 release로 검증 후 전환.
   현재 main 기반 소스만 덮어써 B 런타임을 없애지 않음.
5. 보존 여부가 결정된 데이터만 이전하거나 승인된 새 합성 가구·재료에 최소 링크를 생성.
6. 실제 제한 역할로 읽기 CLI → 추천 정상·누락·권한 실패 → 출처 확인.

단순 조직 조회 권한 부족으로 소유자에게 구현을 넘길 상황은 아니다.
먼저 필요한 것은 위 DB·서버 변경 범위 승인과 로컬 SQLite 보존 결정이다.
