## 저장 구조와 실측 용량

최종 측정: 전체 PostgreSQL DB **166,811,315 bytes = 약 166.8MB**, 공개 카탈로그 관련 테이블·인덱스·TOAST **154,951,680 bytes = 약 155.0MB**.
500,000,000 bytes 논리 예산 대비 약 333.2MB가 남는다. 물리 disk/WAL/Storage bucket/egress는 별도 측정 대상이다.

| 구역 | 실측 후 논리 계획 |
|---|---:|
| 시스템 | 30MB |
| 식품·영양 | 80MB |
| 레시피 | 40MB |
| 공통 원본 ID/hash·버전·검색 | 80MB |
| 냉장고 변화 예약 | 150MB |
| 운영 지표 | 20MB |
| 적재·복구 여유 | 50MB |
| 안전 여유 | 50MB |

공개 pool 합계 200MB는 그대로다. 초기 70/100/30 배분을 실측에 맞춰 80/40/80으로 조정했다.
이 값은 파일을 미리 나눈 partition이나 테이블별 hard quota가 아니다. 전체 DB 300MB 목표/350MB 경고/400MB 중단, public pool 200MB 검사를 유지한다.
냉장고 150MB는 아직 사용하지 않은 논리 예약이다. 가구 재고/입출고/섭취 원본 이력은 SQLite 로컬 전용이다.

영양은 cloud catalog_foods에 기준량·단위와 energy_kcal/protein_g/carbohydrate_g/fat_g/sodium_mg/sugar_g를 저장한다.
카탈로그 snapshot hash/출처/version을 보존하면서 반복 JSON과 6개 sparse 행/index 비용을 줄였다.
catalog_food_nutrients_resolved는 새 칼럼과 legacy sparse 영양을 같은 조회 형태로 제공한다.
NULL은 미상이며 0으로 바꾸지 않는다. API 원본 157필드의 나머지 필드는 로컬 gzip에 보관한다.
비타민·미네랄 등 미매핑 항목까지 cloud 추천 근거에 연결됐다고 주장하지 않는다.
이미지 파일·음성·벡터 임베딩은 저장하지 않았다.

대량 삽입 후 source_records와 catalog_foods의 PK 인덱스를 REINDEX해 공간을 줄였다. 원본 행과 FK는 유지했다.
운영 중 재구성은 잠금이 생기므로 별도 적재 작업 시간에 실행한다. db/maintenance_catalog_indexes.sql 참고.
전체 영양 release 두 개를 동시에 200MB pool에 유지할 여유는 없다. 향후 갱신은 차분·오프라인 이전본 보관 등 용량 정책을 정한 뒤 구현한다.
현재 자동 삭제/자동 갱신·자동 rollback 보존 작업은 없다.

## 로컬 DB·HTTP·Redis 확인

검증한 동일 source snapshot을 cloud와 동일 release UUID로 app/data/kini.sqlite3에 미러링했다.
로컬 활성 식품 347,321건 / 레시피 1,152건 / 식품 영양 sparse 값 2,055,428개로 cloud와 일치한다.
SQLite integrity_check=ok, foreign_key_check=0. 기존 가구/회원은 각각 0개이며 새 개인 자료를 생성하거나 cloud로 복사하지 않았다.
로컬 DB 파일은 **592,814,080 bytes = 약 592.8MB**다. 기존 SQLite sparse 영양 및 정규화 snapshot 구조여서 cloud와 크기가 다르며 Supabase 500MB 예산에 포함되지 않는다.
로컬 원본 gzip: 영양 34,705,094 bytes, 레시피 462,359 bytes. DB·원본·.env·생성 SQL은 Git 제외다.

실제 데이터별 공개 상세 GET을 2회 호출해 HTTP 200 → 200, Redis miss → hit를 각각 확인했다.
이 API는 SQLite 공개 카탈로그/Redis만 사용한다. 원본이 없을 때 외부 API를 실시간 호출하지 않는다.
개인 추천·가족·재고·건강·토큰은 Redis에 저장하지 않는다.
서비스 중 cloud 자동 동기화는 아직 없다. 이 PC의 검증된 snapshot mirror를 사용하는 상태다.

## 재현 및 남은 통합

```powershell
python scripts/collect_mfds.py --source mfds_nutrition --page-size 500 --output output/catalog-build/mfds-full
python scripts/collect_mfds.py --source mfds_recipe --output output/catalog-build/mfds-full
python scripts/prepare_mfds.py --source mfds_nutrition --input output/catalog-build/mfds-full/mfds_nutrition --revision YYYY-MM-DD --exclude-invalid
```

prepare가 만든 bounded SQL을 관리 도구로 번호순 적재하고 validate.sql, publish.sql을 실행한다.
재실행 SQL은 ON CONFLICT DO NOTHING으로 중복 삽입을 피하며 정확한 행 수를 검사한다.
권리 검토 승인·검증 전에는 활성 pointer를 바꾸지 않는다. 최신 전체 데이터를 다시 받으려면 새 snapshot 디렉터리를 사용한다.

cloud publish를 확인한 뒤 아래 예처럼 미러링한다. 실제 현재 plan은 ignored output/catalog-build/production-plans/<release UUID> 아래 있다.

```powershell
python scripts/mirror_mfds_snapshot.py --plan output/catalog-build/production-plans/RELEASE_UUID --snapshot output/catalog-build/mfds-full/mfds_nutrition
```

C 협업: 공개 상세/재고/동기화 상태 표시, 실제/시연 자료 구분, 사용자 전체 흐름 E2E.
