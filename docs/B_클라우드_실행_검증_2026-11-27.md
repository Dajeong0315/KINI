## 시작·중지·복구와 비용

관리 접속은 팀 네트워크의 `ubuntu@100.81.162.14`와 이 PC 전용 키를 사용한다.
개인키는 배포하지 않았다. 다른 팀원의 관리 권한이 자동 부여된 것은 아니다.

```sh
sudo systemctl start ollama kini-b
sudo systemctl is-active kini-b ollama
curl --fail https://kini-b-20261127.tailacd652.ts.net:8443/health/ready
sudo systemctl restart kini-b
sudo systemctl stop kini-b
sudo tailscale serve --https=8443 off
# 접속 복원
sudo tailscale serve --bg --https=8443 http://127.0.0.1:5101
# 모델을 사용하지 않을 때
sudo systemctl stop ollama
```

설치·환경·합성 초기화·rollback은 `deploy/b/README.md` 참조.
복구: B 중지 → 검증된 이전 release로 current 링크 교체 → 시작 → ready·인증 smoke.
요청/모델 본문 로그를 저장하지 않아 앱 로그 회전 대상은 없다. 시스템 journal은 OS 정책을 따른다.

현재 EC2·B·Ollama·Tailscale Serve 실행 중. 자동 중지·유료 전환은 설정하지 않았다.
AWS EC2 Sydney 콘솔에서 위 인스턴스를 **중지**하면 실행 비용을 줄일 수 있다.
서비스만 중지하면 EC2 비용은 계속 발생하며 EC2 중지 중에도 gp3 저장 비용은 남는다.

## 후속 연결

- A: PR#39 코드는 확보했지만 B에 private schema·migration·제한 역할·TLS 연결은 전달/검증되지 않았다.
  public 카탈로그 존재와 개인 저장 기반 완료는 별개다. A 담당 적용 후 `check_server_db.py` 통과 및

  조리 완료에는 A의 확정 출고 event가 필요하며 B가 A 재고 API를 대신 공개하지 않는다.
- C: 위 HTTPS·login/Bearer·서버15초/현행 client20초 조건과 body.status 처리가 필요하다.
  다른 origin의 CORS/프록시·모바일·화면 연결은 미검증이며 C 파일을 수정하지 않았다.
- 식후 피드백: 사용자 후속 요청에 따라 3개 기능 커밋을 로컬 배포 브랜치에 반영·통합 검증할 예정이다.
  이 결과의 cloud d3ec292에는 포함하지 않는다. schema·역할·승인 선택지 준비 전 readiness/경로를 활성화하지 않는다.
- Vision: 별도 `B_Vision_서버_동시실행_확인_2026-11-27.md` 참조. GUI/카메라의 서버 입력/API 전환,
  A event 연결과 자원 실측이 필요하다. 이번에 배포하거나 GPU/추가 인스턴스를 만들지 않았다.
