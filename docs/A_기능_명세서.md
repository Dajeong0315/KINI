# A 데이터 플랫폼 기능 명세서

버전 v1 / 2026-11-25 / 담당 A.
연결 문서: [API 명세서](A_API_명세서.md), [아키텍처](A_아키텍처.md).
구현은 현재 코드 기준이며, '예정'을 완료 기능이나 현재 endpoint로 해석하지 않는다.

## 1. 목적과 담당 경계

가상 냉장고에서 확인한 재고가 실제 SQLite에 저장되고 B의 추천 입력과 C의 화면에서
동일한 데이터로 사용될 기반을 제공한다. 공개 식품 데이터는 출처·버전·단위를 검증해 관리한다.
실제 ThinQ 인증·기기 연결은 진행하지 않는다. Supabase에는 공개 카탈로그/비식별 지표만 두고
가족·개인 조건·재고 이력·원문·로그인 토큰은 로컬에 둔다.

| 담당 | 책임 |
|---|---|
| A | adapter, DB/migration/repository, import/release, 재고 이벤트, 캐시/데이터 상태, 환경 설정 |
| B | 추천·알레르기·영양 정책, AI·개인정보 게이트, 추천/조리/섭취 handler |
| C | 화면·API 클라이언트·가족 선택·재고 확인 UX·오류 표시·E2E |
| 인식 모듈 담당(합의 필요) | YOLO 학습/추적/출입 판정·이벤트 UUID 생성 |

## 3. 상세 동작과 완료 기준

### A-F01 DB 초기화

- 입력: DB 경로, 선택적 demo 옵션. 기본은 빈 private DB다.
- 동작: 기존 테이블을 삭제하지 않고 필요한 테이블/컬럼·인덱스를 추가한다.
- 빈 private DB는 재실행해도 데모 가족이 자동 생성되지 않는다. 기존 demo DB는 설정 변경으로 지워지지 않는다.
- 완료 기준: 개인 DB의 households=0, 반복 초기화 후 기존 행 유지, FK 위반 0·무결성 ok.
- 배포 기준: 실제 DB 파일·비밀키·모델·음성 파일은 Git에 올리지 않는다.

### A-F02 권한과 식사 참여자 연결

- 로그인 계정과 식사 구성원을 분리한다. 보호자 계정으로 로그인해 아이를 식사 참여자로 선택할 수 있다.
- 계정→가구 권한→로그인 세션을 확인한 뒤 서버가 household_id를 정한다.
- 조회는 viewer 포함, 변경은 owner/editor만 가능하다. 만료·폐기·비활성 계정은 차단한다.
- create_meal_for_session은 참여자 전체의 가구 소속을 확인하고 meal 및 participant 행을 함께 만든다.
- 활성 카탈로그 release는 meal_data_context에 고정한다.
- 완료 기준: 타 가구 구성원이 하나라도 있으면 식사 생성 롤백. 세션 만료/로그아웃 후 접근 차단.
- 잔여: HTTP 로그인·가입·전체 B handler의 객체 권한 검사·브라우저 세션 UX.

### A-F03 검출 이벤트 접수

- actor: mock 제공자 또는 향후 detector. source=yolo 값만으로 실제 모델 연결을 뜻하지 않는다.
- 선행: 로컬 가구 쓰기 권한과 하나의 논리 출입 이벤트 UUID.
- 정상: 이벤트를 pending_confirmation으로 로컬 저장한다. 검출만으로 재고량은 변하지 않는다.
- 예외: 같은 UUID의 다른 내용은 409, confidence 범위/추가 필드 오류는 400.
- 완료 기준: 재시도 후 이벤트 1행, 재고 변화 0, 대기 수 증가 1.
- detector 추가 조건: 프레임 반복·가림·재등장을 동일 출입 이벤트로 묶는 tracking 규칙 필요.

### A-F04 입고·출고 반영

- actor: 재료/실중량을 확인한 사용자. C는 확인 전에 반영 성공을 표시하지 않는다.
- 입고: 활성 표준 재료·g·선택 소비기한을 받아 lot별 새 재고를 만든다.
- 출고: 같은 가구·재료의 특정 lot에서 차감한다. 잔량 초과·타 가구·다른 재료는 거절한다.
- 처리: BEGIN IMMEDIATE 안에서 재고, 이벤트 상태, 버전, 확인 계정·변경 전후 수량을 함께 저장한다.
- 예외: 같은 확인은 200 재사용, 다른 확인은 409. 실패는 전체 롤백.
- 완료 기준: 재전송 중복 반영 없음. 1000g에 동시 700g 출고 두 건이면 한 건만 성공, 잔량 300g.
- 품질 경계: 새 입고의 data_status=needs_confirmation. 수량 승인이 알레르기 안전 승인은 아니다.
- 잔여: 포장·라벨·상태 확인 UX, 소비기한 정책, 조리 완료의 재고 차감은 B/C 협의 사항이다.

### A-F05 이벤트 거절

- pending은 rejected로 바꾸고 수량·버전은 유지한다. 동일 거절 반복은 허용한다.
- applied는 거절하지 못하며 별도 보정 이벤트로 처리한다.
- 완료 기준: 거절 후 confirm은 409, 재고 변화 0.

### A-F06 재고 조회

- 세션 가구의 lot별 재료·g·소비기한·data_status, 적용 버전·시각·대기 수를 제공한다.
- 현재 0g lot 포함·페이지 나눔 없음. C는 조회 결과와 품질 안내를 함께 보여준다.
- 현재 버전은 A 이벤트 반영만 추적하며 기존 handler/수동 SQL 변경은 포함하지 않는다.
- 완료 기준: 적용한 새 lot가 조회되고 타 가구 lot는 보이지 않는다.
- 잔여: 모든 쓰기 경로의 버전 통일, read transaction 일관성, 기존 JSON API의 C 전환.

### A-F07 공개 데이터 운영

- 입력: source, revision, 정규화된 공개 데이터 JSON 또는 COOKRCP01 응답 파일.
- staging→validation→validated/quarantined. 검증 실패 release는 추천용으로 배포하지 않는다.
- 영양 기준량과 g/ml/serving을 보존한다. 누락값은 NULL/행 없음이며 0으로 바꾸지 않는다.
- publish는 validated와 source 이용 조건 승인을 요구한다. 로컬 typed 행과 pointer를 함께 변경한다.
- rollback은 같은 출처의 이전 published release를 가리킨다. 원본 release는 지우지 않는다.
- publish/rollback마다 cache_version을 증가시키고 기존 식사 release는 유지한다.
- 완료 기준: 잘못된 기준량·음수 영양 격리, 중복 ID stage 원자성, 롤백 후 버전 증가.
- 잔여: 이용 조건 승인 관리 화면/CLI, 원본 API 수집·호출 제한·페이지 처리·재시도, 원격 writer.

### A-F08~09 Supabase 카탈로그와 로컬 투영

- 현재 원격 11개 공개 카탈로그 테이블과 운영 지표 1개 테이블이 있다.
- 카탈로그의 source 3개·영양 코드 6개는 등록됐지만 실제 식품/레시피/release는 아직 적재하지 않았다.
- RLS 및 서버 역할 전용 접근, 기준량·영양값·FK·published pointer 제약을 적용했다.
- 목표: 승인 release만 다운로드해 완전성 검증 후 로컬 pointer를 전환한다. 실패 시 기존 release 유지.
- 원격/로컬 스키마는 동일하지 않다. PostgreSQL jsonb/UUID·추가 필드·검증 보고서 구조 변환이 필요하다.
- 현재 local stage는 새 UUID를 발급하므로 원격 release ID 보존/매핑도 sync 구현에서 결정해야 한다.
- 완료 기준(예정): 재다운로드 멱등, 중간 실패 미노출, 원격 DB 장애 중 로컬 저장 유지,
  검토된 ingredient/recipe 링크로만 B 엔진에 반영.

### A-F10~13 가상 기기·상태·지표·캐시

- 가상 기기: 로컬 mock 목록·설정 온도·문 상태·지연 시나리오를 제공할 예정. 실기기 토큰 발급 없음.
- 상태: 현재 로컬 release/모드/미연결 기능 상태만 제공한다. 원격 ping이나 ThinQ 동기화 증명이 아니다.
- 지표: 허용 4필드 일별 절대 합계만 업로드. 원문/회원/가구/기기/세션 ID는 전송 전 차단한다.
- 캐시: 공개 카탈로그를 source/release/version으로 분리. 대상별 TTL/jitter와 Redis/memory/disabled provider를 구현하고 장애 시 DB fallback한다.
- 완료 기준(예정): fake cache의 hit/miss/만료/복구 시험, release 변경 시 오래된 값 미사용,
  캐시·집계 실패가 개인 저장 트랜잭션이나 B의 안전 규칙을 우회하지 않음.

## 4. 통합 데모 시나리오

| 시나리오 | A 처리 | B/C 확인 |
|---|---|---|
| 두부 인식 후 입고 | pending→사용자 확인→새 lot+버전 | C가 대기/승인 구분, B가 같은 SQLite 재고 사용 |
| 두부 100g 출고 | 지정 lot 차감·감사 기록 | C 재조회, 다음 추천 재고 입력 반영 |
| 네트워크 재전송 | 같은 UUID/본문으로 멱등 처리 | 중복 버튼/자동 재시도에도 한 번만 반영 |
| 초과 출고 | 400·전체 롤백 | 부족 안내, 성공 표시 금지 |
| 잘못된 인식 | reject·수량 유지 | 후보 수정은 새 이벤트 또는 확인 시 표준 재료 선택 |
| 타 가구 접근 | 403 또는 이벤트 404 | 해당 가구 데이터 표시 금지 |
| 외부 데이터 오류 | release 격리/기존 pointer 유지 | 데이터 상태 확인, 무검증 데이터로 대체 금지 |
| OpenAI 오류 | A 저장 경로는 별도 유지 | B/C는 api_error로 추천 중단. A가 대체 메뉴를 생성하지 않음 |

## 5. 다음 통합 전에 합의할 사항

1. B/C 공통 API에 로그인 가구 권한을 적용하고 실제 개인정보 입력 시점을 정한다.
2. C의 대기 이벤트 목록/상세 요구, lot 선택·라벨 확인·0g 표시를 확정한다.
3. YOLO 클래스·평가 지표·검증셋·tracking 담당자를 정한다. confidence 0.95를 '정확도 95%'로 부르지 않는다.
4. 식약처 응답 fixture와 승인 키, 만개의레시피 제휴/파일 권한을 확보한다.
5. 원격 카탈로그 downloader·매핑·추천 투영·캐시 계약을 고정한다.

## 6. 검증 및 인수 기준

- tests/test_data_platform.py와 tests/test_inventory_events.py가 A 기능의 자동 검증 근거다.
- 기존 전체 테스트 실패를 숨기지 않으며 최신 수치는 [개발 현황](A_개발현황.md)에 기록한다.
- 실제 YOLO·카메라·ThinQ·OpenAI·휴대폰 E2E 완료는 단위 테스트 통과로 대체하지 않는다.
- 개인정보 사용 전 전체 인증·권한·암호화/키 관리·삭제/보존/백업 복구가 필요하다.
