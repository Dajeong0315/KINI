## 구현

- `kini_result_bridge.py`는 최신 Vision sink의 UUIDv5 namespace와 `capture_id|action|item_id|index` 계약을 재사용한다. 촬영 결과 JSON을 기존 엄격한 `KiniInventoryClient`로 보낸다. 새 인식·재인식 알고리즘이나 직접 DB 쓰기를 구현하지 않았다.
- `scripts/vision_kini_bridge.py`는 완료된 실제 YOLO 결과를 후보로 접수하거나 로컬 재시도 큐를 재생한다. `--login`은 터미널에서 계정·가구 ID와 숨김 비밀번호를 받고 토큰을 메모리에만 보관한다. 환경 토큰도 지원하며 값은 출력하지 않는다.
- source는 yolo이며 개수당 후보 1건이다. 개수는 g로 바꾸지 않는다. Unknown 항목은 보내지 않고, 이름을 실제로 확인한 뒤 새 결과로 처리한다. 품목별 confidence를 만들어 넣지 않는다. 같은 촬영 결과는 동일 UUID를 사용한다.
- 기존 가구 인증 재고 조회에 YOLO 대기 목록 최대 100개와 남은 개수를 추가했다. manual 이벤트가 앞에 쌓여도 YOLO 목록이 가려지지 않는다. 조회·쓰기 권한·가구 경계는 기존 API가 적용한다.
- 화면은 식재료 → 인식 확인 대기 → 표준 재료 확인 → 실제 g·입출고 방향·출고 lot 확인 → 확정 순서다. 이름 매칭이 불명확하거나 Unknown이면 자동 확정하지 않는다. 입고는 소비기한별 새 lot, 출고는 선택한 동일 재료의 기존 lot만 차감한다.
- 거절은 재고를 바꾸지 않는다. B 실행기에 기존 거절 API를 연결했다. DB migration·테이블·공개 카탈로그 변경은 없다.
- 응답 유실 시 확인 요청 내용을 보관하고 입력을 잠근 뒤 같은 event ID·내용으로 재시도한다. 서버의 기존 원자적·멱등 확정을 재사용한다. 가구·계정 변경 시 보관한 내용을 제거한다. 재접속·새로고침은 서버 대기 상태를 다시 읽는다.
- 실제 AI 오류를 fake 성공으로 대체하지 않는다. 운영 추천·Ollama·OpenAI 설정은 변경하지 않는다.

## 실행 절차

1. 별도 Vision checkout의 README대로 공개 모델을 준비한다. 기존 실행 환경·가중치를 덮어쓰지 않는다. `--engine yolo --no-sync`로 실제 비교 후 생성된 `captures/<capture_id>/result.json`을 사용한다. 실패한 실행·mock 결과를 성공 출력으로 바꾸지 않는다.
2. 로컬 KINI라면 loopback API를 사용한다. 원격 kini-b라면 별도 터미널에서 `ssh -N -L 127.0.0.1:15101:127.0.0.1:5101 -o ExitOnForwardFailure=yes kini-b`를 실행한다. 이 터널은 SSH 인증·암호화 경계를 쓰며 공개 포트나 임의 remote URL 허용을 추가하지 않는다.
3. PowerShell에서 `$env:KINI_A_API_URL='http://127.0.0.1:15101'`를 설정한다. 토큰을 명령 줄·채팅에 붙이지 않고 `python scripts/vision_kini_bridge.py --login --result <완료된-result.json> --queue "$env:LOCALAPPDATA/KINI/Vision/queue.jsonl"`을 실행한다. 계정과 가구를 터미널에서 확인하고 비밀번호는 숨김 입력한다.
4. 휴대폰 KINI의 해당 가구 → 식재료 → 재고 새로고침 → 인식 후보 확인. 실제 표준 재료·저울 중량·출고 lot을 확인해 확정하거나 거절한다. 별도 Vision UI에서 ‘확인’을 누른 사실을 g 확인으로 해석하지 않는다.
5. 접수 실패는 같은 결과 파일로 재실행한다. 큐만 재생할 때는 `--result` 대신 `--retry`를 쓴다. 여러 후보 중 전송이 중간에 끊겼다면 큐 재생 후에도 원래 `--result`를 재실행해 아직 미전송인 후보까지 보낸다. 기존 접수는 UUID가 같아 중복되지 않는다. 세션 오류는 다시 로그인하고 원래 결과로 재실행한다.
6. 재촬영은 새로운 capture ID를 쓰고, 단순 전송 재시도는 기존 capture ID를 유지한다. 서로 다른 촬영에서 같은 물체가 반복 인식되는 것은 UUID 멱등성의 범위가 아니므로 장면 비교와 사람 확인이 필요하다. 로컬 큐·사진·갤러리를 Git에 올리지 않는다.
