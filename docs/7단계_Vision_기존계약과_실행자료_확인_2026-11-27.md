## 실제로 확인한 최신 Vision 계약

- YOLOE-v8m `yoloe-v8m-seg.pt`, CLIP 재확인 `ViT-B/16`, 기본 `REID_MODE=gallery`, `facebook/dinov2-small`의 로컬 파일, OCR·선택적 OpenVINO 경로를 사용한다.
- `compare()`는 `capture_id`, before/after 개수, `added`/`removed` 목록, 불확실·Unknown·확인 사유와 위치 등을 반환한다. `added`/`removed`의 `quantity`는 **개수**이며 g가 아니다.
- `events_from_result()`는 촬영·방향·품목·순번으로 UUIDv5를 만든다. 인식 결과는 KINI A에 `source=yolo`의 pending 이벤트로 보낼 수 있으며, 표준 재료 ID·실제 g·출고 lot은 사용자가 확인해야 한다. Unknown 이름이나 상자 개수에서 표준 ID·g를 추정하지 않는다.
- 최신 휴대폰 `/compare`는 별도 `supabase_sync`와 개수 기반 재고 테이블 `food_item/capture/stock_event/fridge_stock/current_stock`을 사용한다. 이는 현재 KINI 가구 인증·`kini_private` g 단위 재고와 다른 저장 경로다. 기존 공개 카탈로그와 이 재고를 임의로 복제·변경하거나 앱이 `current_stock`으로 갈아타게 하지 않는다.
- 기존 엄격한 `KiniInventoryClient`는 loopback HTTP origin만 받는다. 운영의 Tailscale HTTPS 주소를 그대로 전달하면 거절한다. 후속 통합은 인식 서비스를 서버의 loopback A에 연결하거나, 명시적 목적지·TLS·redirect/프록시 제한을 갖춘 원격 경계를 구현해야 한다. 단순 `allow_remote=True`로 임의 호스트를 허용하는 연결로 대체하지 않는다.
- 운영 B 실행기는 현재 이벤트 접수·확정을 제공하지만 `/reject`와 확인 대기 목록 화면은 아직 Vision용으로 연결되지 않았다. 실제 모델 계약 확인 후 이 최소 연결은 직접 구현한다.

## 확인된 실행 의존성

- 로컬 프로젝트 Python 환경에서 torch·transformers는 있으나 ultralytics·cv2·CLIP·OpenVINO·EasyOCR는 없다.
- 검사한 B 서버 전용 venv에는 torch·ultralytics·cv2·CLIP·EasyOCR·OpenVINO가 모두 없다. 다른 장치의 모델 실행 상태까지 없다고 단정한 결과는 아니다.
- 저장소에는 before/after 샘플 사진과 코드가 있지만 모델 weights·prompt cache·DINOv2/OCR 파일·재인식 gallery와 같은 검증된 실행 자산은 Git에 포함되어 있지 않다. 현재 접근 가능한 프로젝트·확인한 모델 캐시/기존 Vision 검증 worktree에서도 해당 실행 묶음을 확보하지 못했다.
- `DinoV2Embedder`는 `config.json`이 없으면 FileNotFoundError를 내고 `AutoModel.from_pretrained(..., local_files_only=True)`를 사용한다. YOLOE 등 일부 공개 모델은 자동 다운로드 경로가 있지만, 새로 받은 자산이 담당자가 실제 측정한 버전·캐시와 동일하다고 단정할 수 없다. 검증된 준비 절차를 확보하면 환경 설치·공개 모델 준비는 직접 진행할 수 있다.
- 실제 `compare()` 출력 JSON은 현재 자료에서 확보하지 못했다. 팀 기록의 ‘버터 1개 제거’ 같은 서술과 코드로 만든 합성 JSON을 실제 모델 출력으로 표시하지 않는다. 팀원의 인식 정확도 보고를 이번 환경의 실측으로 쓰지 않는다.

따라서 사용자 지시의 7단계 중단 조건인 **실제 출력 계약·실행 가능한 모델 확보 필요**에 해당한다. 레이블 오인식 사례 자체를 통합 불가로 단정한 것이 아니라, 동일한 실제 모델·출력을 재현할 근거가 없는 상태다. 이 단계에서 기존 모드를 낮추거나 mock으로 정상 성공을 대신하지 않는다.

## 답변 후 재개 위치

1. 받은 버전·실행 절차·실제 JSON을 현재 코드와 대조하고 별도 환경에서 실제 모델 1건을 재현한다. 공개 모델을 준비할 수 있으면 직접 설치·다운로드하고 digest·패키지·실행 조건을 기록한다.
2. 기존 comparer와 KINI 이벤트 클라이언트를 재사용한다. 별도 Supabase 직접 변경은 KINI 연결 경로에서 비활성으로 두고, 후보→대기→사용자 표준 재료·실제 g/출고 lot 확인→A 확정으로 연결한다.
3. 확인 대기·거절·재촬영/재시도와 같은 촬영 UUID 재사용, Unknown/중량 미확인 확정 금지, 가구·세션·원격 TLS 경계를 별도 합성 DB에서 검증한다.
4. 실제 인식 결과로 정상 확인·거절·재시도·중복 방지를 확인하고 자원·응답 시간과 실패 복구 조건을 기록한다. 운영 DB에 파괴적인 테스트는 실행하지 않는다.
