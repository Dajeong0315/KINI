# KINI 아키텍처 결정사항

작성일: 2026-11-25
상태: 팀 합의 — 이후 ThinQ·클라우드·OpenAI 연동 설계의 기준

## 1. ThinQ 재고 데이터와 로컬 캐시

- ThinQ 클라우드의 냉장고·재고 데이터는 서비스 연동 시 **원본 시스템(source of truth)** 으로 취급한다.
- 기기는 추천 속도와 오프라인 처리에 필요한 범위에서만 최신 ThinQ 재고 스냅샷을 로컬 캐시에 저장한다.
- 추천 규칙 엔진은 로컬 캐시 스냅샷을 사용하되, 응답에 스냅샷 시각과 동기화 상태를 남긴다.
- 로컬에서 발생한 재고 변경은 동기화 대기 상태로 보관하며, ThinQ 원본과 충돌하는 경우에는 자동으로 덮어쓰지 않는다. 충돌 해소 정책은 ThinQ 연동 명세를 확인한 뒤 별도로 결정한다.
- 현재 SQLite 데모 재고 데이터는 ThinQ 연동 전의 로컬 데모 원본이다.

## 2. 개인정보·클라우드·OpenAI API 전송 경계

### 로컬에만 보관

- 사용자·가족 이름과 내부 식별자
- 음성 원본과 원문 전사
- 원문 대화
- 상세 건강 상태·상세 질환명·검사 결과
- 정확한 재고 이력, 주소·전화번호·기기 식별자
- 가족 구성원을 직접 식별하거나 다른 데이터와 결합해 식별할 수 있는 정보

### OpenAI API로 전송 가능한 최소 구조화 정보

- 식사 참여 인원과 역할 없는 익명 참여자 표기
- `저염`, `특정 재료 제외`, `알레르겐 코드 제외` 같은 최소 제약 코드
- 조리 시간, 끼니 유형, 구매 허용 여부
- 개인 식별자가 없는 재료명 또는 내부 비식별 재료 코드
- 규칙 엔진이 검증한 후보·제외 사유·영양 요약

### 전송 전 처리

- Ollama 또는 로컬 개인정보 필터가 외부 전송 요청을 검사한다.
- 이름, 사용자/기기 ID, 음성 원문, 대화 원문, 상세 질환명, 위치·연락처가 감지되면 외부 전송을 차단하거나 제거한다.
- 단순히 이름을 지우는 것만으로 비식별화됐다고 판단하지 않는다. 드문 건강 조합·자유 텍스트도 재식별 위험이 있으므로 최소 제약 코드로 축약한다.
- 클라우드 DB에는 개인 식별 정보와 원문을 저장하지 않는다. 저장 가능한 범위는 비식별 운영 지표, 오류 코드, 모델 지연 시간, 기능 사용량, 집계된 품질 지표다.
- 클라우드 운영 DB는 **Supabase(PostgreSQL)** 를 사용한다. Supabase에는 위의 비식별 운영 데이터만 적재하며, 로컬 민감 데이터 SQLite를 Supabase로 동기화하지 않는다.

## 3. Redis 캐시 계층

- Redis는 원본 DB나 개인정보 저장소가 아닌 **성능용 보조 캐시**로 사용한다.
- 원본 시스템은 역할별로 유지한다.
  - ThinQ 클라우드: 연동 재고의 원본
  - 로컬 SQLite: 민감한 가족·식사·개인화 데이터
  - Supabase: 비식별 운영 데이터
  - Redis: 위 원본에서 다시 만들 수 있는 읽기 결과의 단기 캐시
- Redis 우선 대상은 개인을 식별하지 않는 반복 조회다.
  - published 영양·알레르겐 data release와 재료 메타데이터
  - 일반 조리 RAG 문서 검색 결과
  - ThinQ 공개/공유 데이터의 짧은 수명 스냅샷(연동 명세와 권한이 확정된 뒤)
  - Supabase의 집계 운영 지표
- Redis에 저장하지 않는다.
  - 이름, 내부 사용자·가구·기기 식별자
  - 음성 원본·전사 원문·대화 원문
  - 상세 질환명, 알레르기 검사 결과, 개인별 식사 이력
  - OpenAI API 키, Supabase service role key, 접근 토큰
- 로컬 SQLite 단일 조회는 이미 빠르므로 Redis를 무조건 앞에 두지 않는다. Redis는 네트워크를 거치는 ThinQ·Supabase 조회나 여러 사용자가 공유하는 읽기 부하에서 우선 검토한다.
- 캐시 키에는 data release ID·문서 버전·권한 범위 같은 버전 정보를 포함한다. 예: `nutrition:{release_id}:{official_food_code}`
- published release 변경, 알레르겐 기준 변경, ThinQ 재고 동기화, 권한 변경 시 관련 캐시를 무효화한다.
- 알레르기·안전·재고 상태가 오래된 캐시만으로 확정되면 안 된다. 캐시 만료 또는 원본 확인 실패 시 추천을 안전하게 중단하거나 최신화 요청으로 처리한다.
- Redis의 TTL, 최대 메모리, eviction 정책, 접근 제어, TLS/암호화, 운영 위치는 ThinQ·Supabase 연동 명세 확정 후 결정한다.

## 4. AI 역할 분리와 장애 정책

- **OpenAI API**: 기존 LLM 체인의 주 역할을 담당한다. 복잡한 의도 해석, 자연스러운 설명, 대화 응답과 RAG 기반 일반 안내를 수행한다.
- OpenAI 모델은 지금 고정하지 않는다. 개인정보가 없는 대표 평가셋으로 응답 품질·안전 규칙 준수·지연 시간·비용을 비교한 뒤 팀 기준으로 선택한다.
- **Ollama**: 외부 API 호출 전에 개인정보를 검사·최소화하고, 전송 가능 여부를 판정하는 로컬 안전 게이트다. OpenAI 품질을 이기기 위한 주 모델 튜닝은 우선순위가 아니다.
- **로컬 규칙 엔진**: 알레르기, 사용자 설정 제한, 영양·재고·유통기한, 데이터 품질을 최종 판정한다. 어떤 LLM도 이 규칙을 우회할 수 없다.
- **OpenAI API 오류 또는 외부 호출 실패 시**: 추천 결과를 생성하지 않는다. 사용자에게 `AI 연결 오류로 추천을 만들지 못했습니다. 잠시 후 다시 시도해 주세요.`라고 안내한다. 기존 후보나 규칙 기반 fallback 메뉴를 추천으로 표시하지 않는다.

## 5. 건강 관련 서비스 범위

- 서비스는 의료 진단, 치료, 질환별 처방, 알레르기 안전 보증을 제공하지 않는다.
- 지원 범위는 사용자가 직접 설정한 식사 제약과 목표다.
  - 저염 등 일반 식사 기준
  - 특정 재료·알레르겐 제외
  - 체중·단백질·채소 등 일반 영양 목표
- 상세 질환명은 추천 모델이나 외부 API 입력으로 사용하지 않는다.
- 정보가 부족하거나 복합식품 라벨·교차접촉을 확인할 수 없으면 안전하다고 단정하지 않고, 후보 제외 또는 사용자 확인으로 처리한다.
