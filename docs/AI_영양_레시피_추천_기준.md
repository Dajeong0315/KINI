## 1. 목적과 원칙

- 냉장고 재고, 재료 신선도, 개인 식사 기록, 영양 목표, 생활습관 전략, 취향, 조리 조건을 함께 고려해 메뉴를 추천한다.
- 개인 건강·식이·식사 기록은 동의·가구 권한에 따라 우리 서버와 Supabase 보호 영역에서 처리한다. 기기는 입력과 표시를 담당한다.
- 추천 순위는 고정된 규칙과 버전 관리되는 데이터에 따라 계산한다. 동일한 입력값·규칙 버전·DB 버전에서는 동일한 순위를 반환해야 한다.
- 영양 계산, 제한 조건 판정, 후보 순위 결정은 규칙 엔진이 담당한다. AI/Ollama의 해석·설명·조정안 표현은 선택적 후속 경로다. 현재 배포 추천은 `rules-only`와 고정 설명을 사용하며 외부 AI 설명은 비활성이다.
- AI가 생성한 재료 변경안은 규칙 엔진의 재료·단위·알레르기·영양 검증을 통과한 경우에만 제공한다.

## 2. 클라우드 중심 아키텍처

| 구성 | 처리 위치 | 내용 |
| --- | --- | --- |
| 개인 프로필 | Supabase 보호 영역 + 우리 서버 | 건강 주의사항, 알레르기, 식이 제한, 목표, 선호, 평소 식사량 |
| 냉장고 재고 | Supabase 보호 영역 | g 단위 재고 묶음(lot), 입출고 이벤트, 확인 상태 |
| 식사·섭취 기록 | Supabase 보호 영역 | 실제 인분, 영양 누적량, 식후 평가 |
| 추천 규칙 엔진 | 우리 서버 | 제한 필터, 영양 계산, 소비 권장도, 점수화, 정렬 |
| LangChain·Ollama | 우리 서버 내부 서비스 | 선택적 해석·검사·설명 보조. 현재 배포 추천에서는 호출하지 않음 |
| 공용 DB | Supabase 승인 공개 카탈로그 | published release·승인 매핑을 통한 영양 공급. 공개 데이터와 무제한 DB 공개는 다름 |
| 냉장고·모바일 | 인증된 HTTPS 화면 | 입력·표시·탭 상태. 별도 운영 DB나 관리자 키를 두지 않음 |

### 2.1 서버 역할

- 공용 레시피 DB, 식품영양성분 DB, 식재료 표준 단위 DB, 보관 기준 DB, 추천 규칙 배포
- 공용 데이터의 버전 관리 및 무결성 검증
- 동의한 서비스 처리에 필요한 개인별 건강·식사·재고 데이터 저장과 가구·객체 권한 검사
- A 입출고 확정에서만 재고 변경, B 조리 완료에서 출고 연결·개인 섭취 기록 저장. 같은 재고를 이중 차감하지 않음
- 초기 기기 DB 동기화 설계는 현재 배치의 전제가 아니다. 기존 SQLite는 별도 로컬 데모이며 실사용 데이터 이전 완료로 표시하지 않음

### 2.2 데이터 보안 규칙

- 개인 데이터는 Supabase 보호 영역에서 서버 인증·가구/객체 권한 검사·DB 역할/RLS로 보호한다. 보관·삭제·백업 정책은 서비스 동의 범위와 함께 관리한다.
- 클라우드 AI를 사용해야 할 경우 이름, 계정 식별자, 건강 상태 원문, 전체 식사 이력, 가족 관계 정보를 전송하지 않는다.
- 우리 클라우드 DB 저장과 외부 AI 전송을 구분한다. 외부 AI에는 서버가 검증한 최소 필드만 일회성 코드로 전달하고, 범주화만으로 완전 익명화를 보장한다고 표시하지 않는다.
- AI 요청·오류 로그에 개인 건강정보·식사 기록·재고 원문을 저장하지 않는다.
- 제품 개선용 데이터 수집은 기본 비활성화하고 별도 동의를 받는다.
- 가족 공유는 구성원별 열람·수정 권한과 동의를 분리한다.
- 사용자가 삭제를 요청하면 로컬 데이터, 동기화 데이터, 분석 데이터의 삭제 범위와 상태를 제공한다.
- 개인 데이터는 모델 학습에 기본 사용하지 않는다.

추천 결과에 다음 버전을 함께 저장한다.


위 목록은 목표 계약이다. 현재 응답의 `rules_version`, `prompt_version`, `db_version`, 공개 영양 release·알레르겐 버전·입력 지문은 구현돼 있으나, KDRIs 목표 산정 버전·입력 스냅샷·끼니 배분 버전은 아직 연결되지 않았다.

### 4.2 평소 식사량 입력 규칙

## 5. 수량 표준화 및 불확실성 처리

### 5.1 단위 변환

| --- | --- | ---: |
| 한 줌 | 시금치 | 50g |
| 한 줌 | 견과류 | 25g |
| 한 컵 | 우유 | 200ml |

### 5.2 변환 적용 규칙

```text
1. 상품 라벨 또는 사용자가 입력한 실제 중량이 있으면 실제값 사용
2. 식재료·상태·표현이 일치하는 표준 단위값이 있으면 표준값 사용
3. 표준값이 없으면 분류 기반 기본값을 사용하고 불확실성으로 표시
4. 영양 영향이 큰 재료의 수량이 불확실하면 사용자 확인 요청
5. 불확실한 재료를 영양 계산에서 제외하지 않음
```

### 5.3 사용자 확인 규칙

| 조건 | 처리 |
| --- | --- |
| 소량 재료이고 신뢰도 높은 표준값 존재 | 자동 적용 |
| 기름, 설탕, 소스, 고기 등 열량·나트륨·단백질 영향이 큰 재료 | 표준값으로 임시 계산 후 확인 요청 |
| 식재료 크기 차이가 큰 경우 | 표준값 범위와 함께 확인 요청 |

```text

- 높음: 주요 재료의 실제 중량 확정
- 보통: 소량 재료에만 표준 중량 적용
- 낮음: 열량·나트륨·단백질 영향이 큰 재료의 중량 미확정
```

## 6. 영양 계산 규칙

### 6.1 레시피 영양성분

```text
메뉴 영양소 총량 =
Σ(재료 사용량 g 또는 ml ÷ 영양 DB 기준량 × 재료별 영양성분)

1인분 영양소 = 메뉴 영양소 총량 ÷ 실제 제공 인분 수
```

- 원본 레시피 영양값은 참고값으로만 사용한다.
- 재료 추가·제거·대체·분량 변경 후에는 변경된 재료 목록으로 반드시 재계산한다.
- 영양 정보가 없는 재료 비율이 설정 임계값을 초과하면 자동 추천 후보에서 제외한다.
- 중량 g와 부피 ml를 동일시하지 않는다. 영양 DB 기준이 100g이면 승인된 재료별 밀도로 g 변환하고, 100ml이면 같은 부피 기준으로 계산한다. 변환 근거가 없으면 확인이 필요하다.
- 원재료 합산은 조리 후 영양 손실·흡수율·수율까지 측정한 값이 아니다. 특히 조리 후 실제 무게와 원재료 무게를 혼용하지 않는다.

### 6.2 개인별 목표 우선순위

```text
1. 의료진이 제시한 개인별 제한·목표(적용 기간·출처 구분)
2. 사용자가 직접 설정하고 확인한 목표(1의 제한을 해제하지 않음)
3. 2025 KDRIs + 확인된 개인 프로필로 산정한 목표
4. 성별·연령별 공식 표 참고값(개인 실측 목표가 아님을 표시)
```

- 영양소마다 우선순위를 적용한다. 열량만 직접 설정했다고 다른 영양소 목표까지 지우지 않는다.
- 목표·상한의 충돌, 0 이하·비유한 수치, 단위 오류는 저장·자동 적용 전에 확인한다. 의료 제한과 충돌하는 직접 목표를 조용히 적용하거나 임의로 축소하지 않는다.
- 나이·기준표 적용 성별이 없거나 연령 구간을 확정할 수 없으면 해당 공식 목표는 `unavailable`로 둔다. 가족 호칭으로 채우거나 모든 사람에게 성인 기본값을 넣지 않는다. 확인된 알레르기·명시 제한은 계속 적용한다.
- 공식 기준은 건강한 사람의 식사 계획·평가용이다. 질환명만으로 치료식·투약·감량 처방을 생성하지 않는다. 임신·수유·성장기·의료 제한에 일반 체중 감량률이나 고단백 배수를 자동 적용하지 않는다.

### 6.3 기준값의 의미와 영양소별 적용

공식 용어는 [2025 KDRIs 원문·정오표 배포 안내](https://www.kns.or.kr/fileroom/FileRoom_view.asP?BoardID=Kdr&Page=1&cnsearch=&idx=167&mode=mod&restring=96252FFileRoom96252FFileRoom%252EasP96253Fxsearch%253D0%253D%253Dxrow%253D10%253D%253DBoardID%253DKdr%253D%253DPage%253D1&xsearch=1)의 국문요약본 총론 및 영양소별 표를 따른다.

| 기준 | KINI 적용 |
| --- | --- |
| 에너지필요추정량(EER) | 유지 목적의 추정 에너지. 열량의 권장섭취량·독성 상한으로 취급하지 않음 |
| 권장섭취량(RNI) | 단백질 등 개인 식사 계획의 기본 목표. 평균필요량(EAR)을 개인 목표로 대체하지 않음 |
| 충분섭취량(AI) | RNI가 없는 식이섬유 등 참고 목표. 이보다 적게 기록됐다는 이유만으로 결핍 판정하지 않음 |
| 상한섭취량(UL) | 별도 과잉 검토 기준. 목표로 채우지 않으며, 미설정은 무제한 안전을 뜻하지 않음. 식품 외 급원에만 적용되는 등 각주 보존 |
| 에너지적정비율(AMDR) | 하루 총에너지 중 탄수화물·단백질·지방의 비율 범위. 한 메뉴마다 모든 범위를 강제하지 않음 |
| 만성질환위험감소섭취량(CDRR) | 나트륨 감량 안내 기준. RNI·AI·UL과 별도 저장하며 독성 상한이나 반드시 채울 목표로 표시하지 않음 |

초기 자동 추천에 사용할 필드는 현재 영양 경로가 지원하는 **열량·단백질·탄수화물·지방·나트륨**이다. 식이섬유·칼슘·철 등도 KDRIs 목표를 저장할 수 있도록 설계하되, 재료별 승인 데이터와 합산·섭취 기록이 갖춰진 뒤 활성화한다. 미지원 영양소는 0 또는 ‘충족’으로 표시하지 않는다. 일반 식사 기록만으로 결핍을 진단하지 않는다.

### 6.4 공식 성별·연령별 기본 표

**공식 수치**: 정오표 적용 국문요약본 인쇄쪽 xii(에너지), xiii(단백질), xix(나트륨). 에너지는 저활동적 기준의 연령군 참고값이며, 단백질은 RNI다. 나트륨 열은 **CDRR**로, KINI에서는 별도 감량 안내 예산의 기본값으로 사용한다. 표를 개인별 측정 결과로 표시하지 않는다.

| 만 나이 | 남 에너지 kcal/일 | 여 에너지 kcal/일 | 남 단백질 g/일 | 여 단백질 g/일 | 남녀 나트륨 CDRR mg/일 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 3~5 | 1,400 | 1,400 | 25 | 25 | 1,500 |
| 6~8 | 1,700 | 1,500 | 35 | 35 | 1,700 |
| 9~11 | 2,000 | 1,800 | 50 | 45 | 2,000 |
| 12~14 | 2,500 | 2,000 | 60 | 55 | 2,300 |
| 15~18 | 2,700 | 2,000 | 65 | 55 | 2,300 |
| 19~29 | 2,600 | 2,000 | 65 | 55 | 2,300 |
| 30~49 | 2,500 | 1,900 | 65 | 50 | 2,300 |
| 50~64 | 2,200 | 1,700 | 60 | 50 | 2,300 |
| 65~74 | 2,000 | 1,600 | 60 | 50 | 1,900 |
| 75 이상 | 1,900 | 1,500 | 60 | 50 | 1,800 |

- 이 제품의 일반 가족 메뉴 자동 산정 범위는 우선 **만 3세 이상**으로 한다(KINI 범위 결정). 영아·1~2세는 공식 기준이 없어서가 아니라 수유·이유식·별도 식사 계약이 필요하므로 일반 메뉴 자동 산정에서 제외한다.
- 만 나이는 한국 날짜 기준으로 구하고 생일 또는 확인된 나이의 기준일을 저장한다. 구간은 양 끝 포함, 75세 이상은 상한 없는 구간이다. 해가 바뀐다고 전원 나이를 일괄 가산하지 않는다.
- 표의 남/여는 원문의 기준 구분이다. 사용자가 기준표 적용 정보를 선택해야 하며, 미입력 시 두 표의 평균이나 가족 평균을 개인 목표로 쓰지 않는다.
- 표 전체는 같은 기준판·정오표 버전으로 적재한다. 원문 공란은 `null`이며 0으로 바꾸지 않는다. 이후 미량영양소 적재 시 RNI·AI·UL·단위·급원 범위를 각각 보존한다.

### 6.5 개인별 에너지 산정

다음은 **새 구현 계약**이며 현재 자동 산정기는 없다.

1. 6.2의 직접 목표가 있으면 그 값을 사용한다.
2. 건강한 만 19세 이상에서 성별·만 나이·유효한 최근 키/체중·확인된 활동단계가 모두 있으면 2025 KDRIs 제1권 인쇄쪽 16~17, 27~28의 성인 EER 식을 사용한다.
3. 위 입력이 부족하면 6.4 표를 `reference_only`로 제공한다. 표의 저활동적 가정을 명시하고 개인 활동량을 측정했다고 표시하지 않는다.
4. 만 3~18세는 초기 제품에서 6.4 표를 사용한다. 성인 식이나 성인 식사량의 단순 비례 축소를 적용하지 않는다. 성장기 개별 EER 식은 성장 추가량과 전용 계수를 함께 검증한 뒤 별도 활성화한다.

```text
성인 남 EER = 662 - 9.53 × 나이 + PA × (15.91 × 체중kg + 539.6 × 키m)
성인 여 EER = 354 - 6.91 × 나이 + PA × (9.36 × 체중kg + 726 × 키m)
키m = 입력 키cm / 100
```

| 확인된 활동단계 | 성인 남 PA | 성인 여 PA |
| --- | ---: | ---: |
| 비활동적 | 1.00 | 1.00 |
| 저활동적 | 1.11 | 1.12 |
| 활동적 | 1.25 | 1.27 |
| 매우활동적 | 1.48 | 1.45 |

활동단계는 사용자가 확인한 값으로 저장한다. ‘운동 주 2회’ 하나로 PA를 자동 판정하지 않는다. 원문 PA는 단순 기초대사량 배수가 아니므로 식에 PA를 두 번 곱하지 않는다. 개별 EER 원값은 보존하고 화면은 kcal 정수 반올림한다(KINI 표시 정책). **공식 연령표의 설정값을 개인 EER 식으로 재생성하지 않는다.** 공식 표에는 체위 참고치·절삭·일부 기존값 유지 판단이 포함돼 있다.

임신·수유는 별도 상태 확인과 부가량 검증 후 적용한다. 국문요약본의 **공식 부가량**은 비임신 여성 기준 대비 임신 1/2/3분기 에너지 `+0/+340/+450 kcal/일`, 단백질 `+0/+10/+30 g/일`, 수유기 에너지 `+340 kcal/일`·단백질 `+25 g/일`이다. 임신부·수유부 탄수화물 RNI는 기본 130g에 각각 `+45/+70g`을 더한다. 총량과 부가량을 혼동하거나 현재 체중 EER와 부가량을 검토 없이 중복 적용하지 않는다. 초기 자동 산정에서는 해당 상태를 `requires_review`로 두고 확인된 직접 목표를 우선하며, 일반 성인 자동식으로 조용히 통과시키지 않는다.

### 6.6 단백질·탄수화물·지방·나트륨 목표

**공식 범위**: 2025 KDRIs 국문요약본 인쇄쪽 xi~xiii, xix. 일반 만 3세 이상 탄수화물은 에너지의 **50~65%**, 단백질 **10~20%**, 지방 **15~30%**다. 지방 20~35%인 1~2세 규칙을 성인에 적용하지 않는다.

```text
E = 적용이 확인된 일일 에너지 kcal
탄수화물 계획 범위 g = [max(해당 상태의 탄수화물 RNI, E×0.50/4), E×0.65/4]
단백질 계획 범위 g = [max(해당 상태의 단백질 RNI, E×0.10/4), E×0.20/4]
지방 계획 범위 g = [E×0.15/9, E×0.30/9]
```

위의 RNI와 AMDR를 함께 반영하는 구간 계산은 **KINI 식사 계획 정책**이다. 단백질 RNI 자체를 수정한 공식 수치로 표시하지 않는다. 탄수화물 기본 RNI는 일반 만 1세 이상 `130g/일`이며 임신·수유는 위 부가량을 적용한다. 범위 양 끝을 모두 더해서 100%라고 간주하지 않고 실제 하루 탄수화물·단백질·지방 조합의 에너지 합과 비율을 검증한다. 구간 하한이 상한보다 크거나 직접 목표와 충돌하면 확인 대상으로 둔다.

- 단백질 관리 전략을 골라도 임의로 `체중×2g` 등을 적용하지 않는다. 우선 RNI 충족과 AMDR 안에서 끼니 분산을 돕는다. 공식 단백질 UL은 설정되지 않았으므로 `20%`를 독성 상한으로 부르지 않는다.
- E가 없으면 g 범위를 만들지 않는다. 확인된 RNI는 독립 제공할 수 있으나 AMDR 적합 판정은 보류한다.
- 나트륨 AI와 CDRR는 별도다. 예를 들어 일반 30~49세의 AI는 1,500mg/일, CDRR는 2,300mg/일이다. AI까지 더 먹으라고 추천하지 않는다.
- KINI 기본 나트륨 계획 예산은 **연령별 CDRR**다. 사용자가 확인한 더 낮은 관리 목표나 의료진 제한은 우선한다. CDRR 초과는 기본적으로 감량 안내·경고이며 의료상 하드 제한과 구분한다. 사용자가 제외 모드를 선택하거나 명시적인 의료 제한이면 후보에서 제외한다. CDRR를 나트륨 UL이라고 표기하지 않는다.
- 나트륨 섭취량은 mg로 합산한다. 소금 g와 혼용하지 않는다. 기존 데모의 일률적 `2,000mg`과 1끼 `600mg` 설정은 공식 연령표에서 산출된 값이 아니다.

### 6.7 일일 기록과 남은 목표량

```text
개인 섭취 영양 = 변경 후 메뉴 1인분 영양 × 개인 실제 섭취 인분
기록된 보완 필요량 = max(0, 적용 목표 - 오늘 확인된 누적 섭취량)
남은 나트륨 계획 예산 = max(0, 나트륨 계획 예산 - 오늘 확인된 나트륨 섭취량)
의료상 제한 잔여량 = max(0, 별도 의료 제한량 - 해당 기간의 확인된 섭취량)
```

- KST 일자 경계를 명시해 식사 시각을 집계한다. 서버 운영체제의 `date.today()`가 우연히 KST인 것에 의존하지 않는다.
- 미기록 끼니·외식·간식이 있으면 위 계산은 **기록된 섭취량 기준**이다. 누락을 0으로 채우거나 ‘실제 결핍’·‘남은 안전 섭취 가능량’으로 단정하지 않는다. 누적량의 신뢰 상태를 함께 반환한다.
- 0 인분은 실제 미섭취 확인이며 미입력과 다르다. 모든 영양값에 목표가 존재한다고 가정하지 않는다. 목표가 없으면 비율은 `null`, 목표 0 또는 남은 목표 0에서는 나누기를 수행하지 않는다.

### 6.8 끼니별 배분 정책

다음 숫자는 **공식 KDRIs 규정이 아닌 KINI 초기 정책**이며 버전 관리한다.

1. 사용자가 확인한 끼니·간식별 에너지 배분이 있으면 우선한다. 전체 합은 1이어야 한다.
2. 없으면 최근 **14일 중 기록이 완전한 날이 7일 이상**일 때 확인된 끼니별 에너지 합/하루 에너지 합으로 배분한다. 실제 결식 확인은 포함하고 미기록 일자는 학습에서 제외한다. 에너지 합 0인 날은 비중 계산에서 제외한다.
3. 충분한 기록이 없으면 확인된 하루 식사·간식 슬롯 수 M에 따라 `1/M`로 나눈다. 세 끼인 경우에만 1/3이며, 슬롯 수까지 없으면 먼저 확인한다. 자동으로 세 끼라고 가정하지 않는다.

```text
이번 끼니 기본 목표 = 일일 적용 목표 × 이번 슬롯 비중
이번 끼니 단백질 보완량 = min(기록된 단백질 보완 필요량, 이번 끼니 단백질 기본 목표)
이번 끼니 나트륨 계획 예산 = min(남은 나트륨 계획 예산, 일일 나트륨 계획 예산 × 슬롯 비중)
```

- 첫 버전의 추가 보정 허용량은 **0**이다. 아침 누락량을 저녁 한 끼에 모두 몰아 보충하지 않는다. 추후 보정 계수는 검증 후 별도 버전으로 변경한다.
- 끼니 계획 한도는 일일 UL이 아니다. 영양소별 공식 ‘끼니 독성 상한’이 있는 것처럼 만들지 않는다. 의료진의 별도 끼니 제한이 있으면 이를 추가 적용한다.
- 나트륨 예산이 0이면 비율을 계산하지 않는다. 추가 나트륨이 있는 메뉴에는 예산 초과 안내를 하고, 일반 관리/하드 제한 모드에 따라 경고 또는 제외한다. 0mg 메뉴만 무조건 정상 추천하거나 ‘소금을 전혀 먹지 말라’는 지시로 바꾸지 않는다.
- 기록 완전성이 부족하면 정확한 일일 잔여량 충족을 보장하지 않고 계획 목표·미확인 끼니를 함께 표시한다.

### 6.9 가족별 계산 예시와 저장 계약

아래는 실제 가족이 아닌 **합성 예시**다. 직접 목표·질환 제한이 없고 공식 표를 참고값으로 선택한 경우이며 일일 기준이다.

| 예시 | 에너지 | 단백질 RNI | 나트륨 계획 예산 | 적용 근거 |
| --- | ---: | ---: | ---: | --- |
| 만 40세 남 | 2,500 kcal | 65g | 2,300mg | 남 30~49세 |
| 만 40세 여 | 1,900 kcal | 50g | 2,300mg | 여 30~49세 |
| 만 10세 남 / 여 | 2,000 / 1,800 kcal | 50 / 45g | 모두 2,000mg | 9~11세, 성별 확인 필요 |
| 만 70세 여 | 1,600 kcal | 50g | 1,900mg | 여 65~74세 |

만 40세 남의 기록된 단백질이 40g이고 확인된 끼니 비중이 1/3이면 RNI 기준 남은 양은 25g, 이번 끼니 기본 목표는 65/3g, 보완량은 약 **21.7g**이다. 나트륨 기록이 1,000mg이면 잔여 계획 예산은 1,300mg, 이번 끼니 계획 예산은 약 **766.7mg**이다. 이는 KINI 계획 예시이며 개인별 의료 처방이나 실제 식사 측정 결과가 아니다.

새 목표 데이터는 영양소별로 다음을 보존한다(미구현 계약).

```text
nutrient, unit, target_kind: EER | RNI | AI | AMDR | CDRR | UL | custom
reference_value / range_min / range_max, scope: daily | meal
effective_value, source_type: clinician | user | kdri_formula | kdri_table
source_url, source_page, reference_version, errata_version, source_sha256
target_policy_version, input_snapshot_hash, calculated_at, effective_from
status: active | reference_only | requires_review | unavailable
```

원문 기준값과 실제 적용값을 분리하고, 사용자 override의 근거와 시각을 보존한다. 공개 KDRIs 기준 데이터와 개인 목표·입력 스냅샷은 접근 영역을 나눈다. 목표 변경 후 과거 식사의 실제 섭취 영양을 새 목표로 덮어쓰지 않고 당시 목표 버전과 현재 비교값을 구분한다.

## 7. 식재료 보관 기준 및 소비 권장도

### 7.1 원칙

- 표준 보관 기간은 추천 우선순위를 위한 소비 권장 기준이며 식품 안전을 보장하는 절대 기준이 아니다.
- 곰팡이, 점액, 비정상 냄새, 심한 변색, 사용자 입력 `unsafe` 상태가 있으면 기간 계산과 무관하게 추천에서 제외한다.
- 실제 제품의 소비기한·보관 지시가 표준 기준보다 우선한다.

### 7.2 최종 소비 권장일

```text
기본 소비 권장일 = 입고일 + 식재료별 표준 보관 기간

최종 소비 권장일 = min(
  기본 소비 권장일,
  실제 제품 소비기한(입력된 경우),
  개봉 후 소비 권장일(해당하는 경우)
)
```

- 개봉 후 보관 기준이 더 엄격한 식재료는 `개봉일`을 기준으로 계산한다.
- 보관 위치가 권장 보관 방식과 다르면 보관 기간을 단축한다.
- 냉동 보관 시 해당 식재료의 냉동 보관 기준으로 다시 계산한다.
- `use_soon` 상태는 소비 권장도를 상향한다.

### 7.3 소비 권장도

```text
기준 시작일 = 개봉 후 기준이 적용되면 opened_at, 아니면 received_at

경과 비율 =
(현재 시각 - 기준 시작일)
÷
(최종 소비 권장일 - 기준 시작일)
```

| 경과 비율 | 상태 | 소비 우선도 |
| ---: | --- | ---: |
| 0~50% | 여유 있음 | 0.20 |
| 50~75% | 계획 소비 권장 | 0.50 |
| 75~90% | 빠른 소비 권장 | 0.80 |
| 90~100% | 오늘 우선 소비 권장 | 1.00 |
| 100% 초과 | 상태 확인 필요 | 자동 추천 보류 |

## 10. 후보 점수 계산

모든 항목 점수는 `0~100`으로 정규화한다. 아래 전략별 계산은 목표 설계이며 현재 구현과의 차이는 17절을 따른다. 계산 분모가 0이거나 목표가 미확정이면 임의의 1로 치환해 ‘충족’ 점수를 만들지 않는다.

### 10.1 재고 소진 점수

```text
재료별 소진 기여도 = min(레시피 사용량 ÷ 현재 재고량, 1.0)

재료별 재고 기여 점수 =
소비 우선도 × 소진 기여도 × 재료 중요도

레시피 재고 소진 점수 = Σ(재료별 재고 기여 점수)를 0~100으로 정규화
```

### 10.2 단백질 보완 점수

```text
단백질 보완 비율 =
min(메뉴 1인분 단백질 ÷ 해당 끼니 권장 단백질 보완량, 1.0)

단백질 보완 점수 = 단백질 보완 비율 × 100

```

보완량이 0이면 추가 보완 가점은 0으로 하고 일반 영양 균형 평가를 유지한다. 단백질 AMDR 상단 초과는 하루 식사 계획의 조정 사유로 다루며, 공식 단백질 UL 또는 공식 끼니 상한이 있다고 가정한 패널티는 적용하지 않는다. 별도 의료 제한은 하드 필터로 처리한다.

### 10.3 나트륨 적합 점수

```text
나트륨 비율 = 메뉴 1인분 나트륨 ÷ 남은 나트륨 예산
```

가족별 분량을 조정한 경우에는 해당 개인 제공량 기준으로 계산한다. 6.8절의 이번 끼니 예산을 분모로 사용하며, 분모 0/미확정 처리는 6.7~6.8절을 따른다. ‘남은 예산을 쓸수록 좋다’는 점수로 해석하지 않는다.

| 나트륨 비율 | 점수 |
| ---: | ---: |
| 0~0.5 | 100 |
| 0.5 초과~0.8 | 80 |
| 0.8 초과~1.0 | 50 |
| 1.0 초과 | 제외 또는 경고 후보 |

### 10.4 채소 점수

```text
채소 사용량 점수 = min(채소 g ÷ 끼니별 채소 목표 g, 1.0) × 70
채소 다양성 점수 = min(채소 종류 수 ÷ 3, 1.0) × 30
채소 점수 = 채소 사용량 점수 + 채소 다양성 점수
```

### 10.5 기타 점수

| 점수 | 기준 |
| --- | --- |
| 열량 적합 점수 | 해당 끼니 열량 목표 범위와의 거리 |
| 영양 균형 점수 | 주요 영양소·식품군 결손 보완, 과잉 방지 |
| 선호 점수 | 선호 재료·맛·조리법 반영, 비선호 재료 회피 |
| 실행 가능성 점수 | 조리 시간, 도구, 난이도, 추가 구매, 비용 |
| 다양성 점수 | 최근 메뉴의 주재료·조리법·맛 중복 회피 |

### 10.6 최종 점수

```text
최종 점수 =
(재고 소진 점수 × 재고 가중치)
+ (공통 영양 균형 점수 × 공통 가중치)
+ (주요 전략 점수 × 주요 전략 가중치)
+ (보조 전략 점수 × 보조 전략 가중치)
+ (선호 점수 × 선호 가중치)
+ (실행 가능성 점수 × 실행 가중치)
+ (다양성 점수 × 다양성 가중치)
- 초과·반복·추가 구매 패널티
```

| 항목 | 평상시 | 임박 재료 존재 시 |
| --- | ---: | ---: |
| 재고 소진 | 15% | 30% |
| 공통 영양 균형 | 15% | 15% |
| 주요 전략 | 30% | 25% |
| 보조 전략 | 15% | 10% |
| 선호 | 10% | 8% |
| 실행 가능성 | 10% | 7% |
| 다양성 | 5% | 5% |

가중치는 규칙 버전으로 관리하며 AI/Ollama가 임의로 변경하지 않는다.

현재 구현은 위 가중치를 사용하지만 영양 균형·주요 전략·보조 전략에 같은 단백질 점수를 넣는 단순화가 남아 있다. 전략별 영양 평가 구현 완료로 표시하지 않는다. 기존 개인화 점수와 식후 맛 평가를 합한 보정은 ±15 범위다(16.3절).

## 13. 가족 공동 식사 규칙

- 모든 참여자의 알레르기·의료 제한을 공통 하드 제약으로 적용한다.
- 공통 기본 메뉴를 먼저 선정하고, 개인별 분량·소스·토핑·반찬을 조정한다.
- 공통 메뉴로 해결할 수 없는 제한이 있으면 개인별 대안을 제공한다.
- 구성원별 영양 계산과 목표 달성률은 분리해 계산한다.
- 가족의 일일 목표를 평균내서 모든 사람에게 적용하지 않는다. 개인 섭취량을 확정한 후 사람별 목표·제한을 검사한다. 공통 메뉴의 조리 총량은 각 개인 제공량의 합으로 계산하고 재고와 대조한다.
- 개인별 제공량을 자동 제안하려면 각 조정안의 재료량·소스량과 영양을 다시 계산해야 한다. 한 사람의 제한 위반을 가족 평균 점수로 상쇄하지 않는다.
- 현재는 추천 조정안이 모두 기본 1인분·기본 소스·기본 토핑이며, 식후 실제 인분을 직접 입력할 수 있다. 실제 인분 기록과 추천 전 개인별 자동 최적화는 별도 기능이다.

## 14. Ollama 입력·출력 규칙

이 절은 선택적 AI 경로를 활성화할 때의 목표 제한이다. 현재 배포 추천에서는 Ollama 보조 검사·OpenAI 설명·fake 설명을 호출하지 않고, 명시적 `rules-only` 결과와 `ai_status=disabled`를 반환한다. 실제 AI 오류 때 자동으로 이 모드로 전환하는 fallback을 뜻하지 않는다.

### 14.1 Ollama에 제공 가능한 입력

```json
{
  "recommended_recipes": [],
  "validated_adjustments": [],
  "recommendation_reasons": [],
  "nutrition_summary": {},
  "uncertainty_flags": [],
  "response_style": "concise_ko"
}
```

- 입력값은 규칙 엔진이 검증한 메뉴·재료·영양 수치·추천 사유만 사용한다.
- 건강 상태 원문, 전체 식사 이력, 계정 식별자, 가족 관계 원문은 제공하지 않는다.

### 14.2 Ollama 출력 제한

- 검증된 후보 외의 메뉴를 확정 추천으로 제시하지 않는다.
- 검증되지 않은 재료 대체·영양 수치·의학적 효능을 단정하지 않는다.
- 조정안을 새로 제안하는 경우 `검증 필요` 상태로 규칙 엔진에 반환한다.
- 최종 사용자 문구에는 추천 이유, 재료 조정, 예상 영양정보, 불확실성, 대안을 포함한다.

## 16. 2026-11-27까지 반영한 최신 변경

이 절은 최신 원격 main의 코드와 아래 검증 기록을 대조한 결과다. 검증 기록의 서버 상태를 이번에 재측정한 것으로 표시하지 않는다. 과거 문서의 ‘미커밋·미배포’ 문구보다 현재 main의 파일·코드 존재 여부와 후속 검증 기록을 우선한다.

### 16.1 서버·공식 카탈로그·섭취 기록

- 목표 배치는 기기 내부 저장에서 **우리 서버 + Supabase PostgreSQL**로 바뀌었다. 서버의 인증·가구 권한 검사와 제한 DB 역할을 통해 보호 데이터에 접근한다.
- 승인된 public published 영양 데이터와 명시적 재료 매핑을 사용하는 provider가 구현돼 있다. 공개 식품 전체가 자동으로 로컬 레시피 후보가 되는 구조는 아니다. 예시 조리법·확정 인분·재료량을 별도로 검증해야 한다.
- 조리 재료량을 바꾸면 1인분 영양을 다시 계산한다. A 출고 확정만 재고를 차감하며, B 완료는 그 출고를 연결하고 개인별 실제 인분·섭취 영양을 저장한다. 이력·영양 리포트 조회 경로도 있다.
- 배포 검증 문서에는 실제 Supabase 공개 카탈로그 3개 재료와 앱 작성 합성 시연 메뉴 1개의 추천·저장 재조회가 기록돼 있다. 실제 가족 식단의 영양 정확도·조리 손실 검증이나 기존 개인 DB 이전 결과는 아니다.
- 3·5단계의 실제 휴대폰 흐름 통과는 사용자 보고이고 PC 브라우저 자동 시험과 구분한다. 6단계 신규 평가 화면의 실제 휴대폰 확인까지 확대하지 않는다.

### 16.3 식후 평가와 추천 개인화

- 최신 정책은 **식사당 평가 1건**이다. 식사 세션 참여자 누구나 일부 항목을 답하고 같은 평가를 수정할 수 있다. 최초 응답자를 지정 평가자로 만들지 않으며 0인분·섭취 항목 없는 참여자도 세션 관계가 있으면 허용한다.
- 식사 저장 성공 후 평가/건너뛰기를 한 번 제공한다. 수정·재시도를 새 학습 표본으로 중복 집계하지 않고, 건너뛰기·단순 닫기를 보통/불만으로 학습하지 않는다.
- 맛은 해당 메뉴의 최근 식사 최대 5건에서 현재 유효한 맛 값의 평균을 사용한다. 만족 `+2`, 보통 `0`, 불만족 `-2`이며 생략/skip은 표본에서 제외한다. 이번 추천 참여자와 과거 식사 참여자가 겹치는 자료를 사용하고 응답자 개인이나 모든 재료의 선호로 확대하지 않는다.
- 기존 개인화와 합한 보정은 **±15**로 제한한다. 상한에 도달하면 원래 맛 조정량과 실제 적용량은 다를 수 있다. 이는 초기 제품 정책이며 최적 사용자 품질을 입증한 값은 아니다.
- 간·난이도는 같은 메뉴의 조리 안내에만 반영한다. 맛 평가로 알레르기·영양·건강·재고 필터를 우회하지 않고 ‘짜다’를 측정 나트륨으로 바꾸지 않는다.
- 서버·Supabase 합성 기록과 PC 390px 화면의 저장·수정·다음 추천 반영이 검증 기록에 있다. 실제 가족 대상 품질 평가와 실제 휴대폰의 신규 평가 화면 검증은 별도다.
