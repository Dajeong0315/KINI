## 재승인을 요구하지 않는 기존 확정 사항

근거: [기존 계약](B_식후_피드백_계약_v1.md), [배포 통합의 승인 근거](B_식후_피드백_배포통합_2026-11-27.md).

- 맛: 만족/보통/불만족. 간: 싱거움/적당함/짬. 난이도: 쉬움/적당함/어려움. 선택지 코드는 이미 승인 파일에 있다.
- 식사 저장 성공 후 평가 여부를 선택하고 바로 패스 가능. 필수 평가가 아니며 자동 재질문·알림은 이번 범위에 없다. 재노출 수치 미정만으로 추가 기능을 만들지 않는다.
- 지정 평가자를 배정하지 않으며 응답하는 식사 참여자를 확인한다. 모르는 항목은 생략할 수 있다. 기존 평가에서 단순 닫기는 값을 보존한다.
- 공유 가구 인증·실제 식사 참여 관계 확인, `(record_id,member_id)` revision·멱등성 계약을 재사용한다. 음성은 기존 계약의 입력 방향일 뿐 새 음성·화자 인증을 구현한 상태가 아니다.

## 확인된 중단 조건

1. **0인분으로 저장된 참여자의 평가 허용 범위가 미확정이다.** 기존 계약의 ‘0인분 저장된 참여자도 평가 대상인가?’ 항목은 운영 노출 보류로 명시되어 있다. 후보 SQL 어댑터는 저장된 item+세션 참여 관계만 확인하고 `servings>0`을 요구하지 않는다. 이를 승인된 정책으로 추정하지 않는다. 현재 UI는 미섭취자를 저장 목록에서 제외하지만 기존 API/DB가 0인분 기록을 허용하므로 이 경계를 확정해야 한다.
2. **맛·간·난이도를 다음 추천의 어떤 대상·방향·강도로 반영할지 미확정이다.** 현재 submitted 응답은 `personalization_status=pending_mapping`이며 추천 점수나 조리 안내에 연결하지 않는다. 기록 저장만 켜서 ‘다음 추천 반영’ 완료로 표시할 수 없다. 기존 `meal_record` 섭취 증거와 평가 신호를 구분하고 수정·철회 후 중복 없는 현재 증거를 유지해야 한다.

가중치가 미정이라는 사실만으로 기존의 독립 저장 검증이 불가능한 것은 아니다. 그러나 사용자 6단계 지시가 평가 대상 등 미확정 시 API·테이블 확정 전에 멈추도록 했으므로 현재 후보를 운영 확정·노출하지 않는다. 맛·간·난이도의 단계나 확정된 선택 평가 시점을 다시 승인받으려는 요청도 아니다.

## 요청 대상과 그대로 전달할 요청문

대상: 김진아 님. 팀원에게 직접 메시지를 보내지 않았다.

> KINI 식후 평가의 기존 선택지와 저장 후 선택 평가·패스·자동 재질문 없음은 확인했습니다. 두 가지만 확정 부탁드립니다. ① 0인분 참여자는 맛·간 평가에서 제외하고 난이도는 해당 식사 참여자 누구나 선택 응답하도록 할까요? ② 맛은 해당 메뉴의 추천 순위, 간·난이도는 해당 메뉴의 조리 안내에 반영하는 방향으로 할까요? 다른 방향이라면 반영 대상·방향·강도 기준을 알려주세요. 이는 제안이며 아직 운영 정책으로 적용하지 않았습니다.

확정된 사항과 제안을 구분한다. 공유 기기의 응답 참여자 확인을 타인 대리 평가 허용으로 확대하지 않고, 기존 평가 철회를 단순 닫기와 혼동하지 않는다. 후속 범위에 별도 철회나 대리 평가 기능을 넣게 되면 그 정책도 먼저 확인한다.

## 답변 후 재개 위치

받은 평가 대상·반영 기준을 계약에 반영 → 기존 저장 어댑터에 필요한 최소 변경 → 명시적 migration·제한 앱 역할/RLS → 저장·수정·패스 화면/API 연결 → 현재 평가 사실의 중복 없는 개인화 연결 → 별도 PostgreSQL 합성 시험 → 실제 서버·휴대폰 검증 순서로 재개한다. 알레르기·영양·명시 제한 등 안전 규칙은 개인화로 우회하지 않는다.

이번 단계 확인 중에는 운영 DB·서버 설정·제품 코드를 바꾸거나 커밋·푸시하지 않았다. 1~5단계 서비스는 기존 검증 상태로 유지한다.
