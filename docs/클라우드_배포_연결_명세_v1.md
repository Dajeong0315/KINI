# KINI 발표용 클라우드 배포 연결 명세 v1

작성일: 2026-11-26 (한국 시간). 목표는 **2026-12-22 발표 종료까지 동작**이다. 최신 원격 main `672106468124ee75d6962abb3cabda80d78e6e09`를 읽어 작성했다. 기존 로컬 작업 기준 `96fc3d2`와의 차이는 가족 등록 API와 가족 조회 인증 연결이며, 해당 기능을 신규 개발로 반복하지 않는다.

이 문서는 파이프라인 설계 v1의 마지막 배포 명세다. 실제 서버 생성·migration·데이터 이전·유료 전환·모델 호출은 수행하지 않았다. 아래 실행 설정은 구현할 계약이며 현재 코드에서 모두 지원된다는 뜻이 아니다.

## 1. 배치 구성

| 구성 | 배치·역할 |
|---|---|
| 기기·모바일 | 브라우저에서 화면·입력만 담당. 별도 운영 DB 없음 |
| AWS EC2 1대 | Sydney, m7i-flex.large, 2 vCPU·8 GiB·gp3 40 GB·라이선스 비용 없는 Linux |
| 접근 경로 | 팀 시연 기기의 Tailscale → tailnet HTTPS Serve → 서버 loopback API |
| Python 서비스 | Flask 앱을 Gunicorn으로 제공. API·규칙·LangChain·개인화 실행 |
| Ollama | 동일 EC2의 별도 서비스, loopback 11434. 소형 양자화 모델 한 개·동시 추론 한 개 |
| Supabase | 공개 카탈로그와 보호된 가족·재고·식사·피드백 저장. 기기와 EC2 SQLite를 쓰기 원본으로 두지 않음 |
| 외부 OpenAI | 최소화·범주화·허용 필드·검증용 AI 경계를 통과한 요청만 전달 |

초기에는 호스트 서비스(systemd)로 API와 Ollama의 시작·중지·로그 회전을 관리한다. Docker는 필수 전제가 아니다. 런타임 버전과 의존성은 Linux에서 확인한 뒤 잠그고, requirements의 현재 범위를 그대로 매번 최신 설치하는 방식은 배포 재현 기준으로 삼지 않는다.

Gunicorn은 1 worker·소수 thread로 시작하고 모델 추론은 전역 동시성 1로 제한한다. 현재 requirements에 Gunicorn·PostgreSQL 드라이버는 없으므로 후속 구현에서 추가한다. Flask 개발 서버와 debug는 발표 배포에 사용하지 않는다. STT/TTS 서비스 코드는 재사용 대상이나 첫 텍스트 파이프라인 검증에서 음성·영상 모델을 함께 로드하지 않는다.

Tailscale Serve는 tailnet 안에서만 사용한다. 공개 Funnel·공인 인터넷 공개는 범위에 포함하지 않는다. 발표 기기와 발표장 네트워크가 tailnet 접속 가능한지는 사전 리허설에서 확인한다. 접속 기기를 추가하거나 tailnet 보안 설정을 변경하는 작업은 아직 수행하지 않았다.

## 2. 포트·비밀정보·서비스 상태

| 항목 | 명세 |
|---|---|
| API | 127.0.0.1:5000. 외부에서 직접 접근 금지 |
| Ollama | 127.0.0.1:11434. 외부 공개 금지, OLLAMA_NO_CLOUD=1 |
| HTTPS | Tailscale Serve가 로컬 API로 전달. 기기에서 HTTPS URL 사용 |
| Supabase DB | 소유자가 제공한 session pooler의 IPv4 연결·5432·TLS 인증서 검증을 우선 사용 |
| 보안 그룹 | API·DB·Ollama 포트 전체 인터넷 허용 금지. 관리 접속은 tailnet 기준으로 별도 확정 |
| 비밀정보 | 서버 관리자 전용 환경 파일에 보관하고 Git·이미지·브라우저·원문 로그에 포함하지 않음 |
| liveness/readiness | 프로세스 생존과 DB·필수 모델 준비를 구분. 키·사용자 데이터·원문 출력 없이 상태만 제공하는 신규 경로 |

환경 변수는 기존 OLLAMA_BASE_URL·OLLAMA_MODEL·KINI_USE_OPENAI·OPENAI_API_KEY·KINI_CACHE_BACKEND를 재사용한다. DB provider 선택·PostgreSQL 연결 문자열·CA 인증서 경로·seed 차단·로그 정책·모델 동시성·요청 제한은 새 서버 설정 계약으로 추가할 대상이다. 임의 변수명을 현재 지원 설정처럼 배포하지 않는다. 외부 LangChain tracing은 기본 비활성화한다.

최초 연결은 합성 데이터·fake AI 모드로 검증한다. 실제 OpenAI 호출은 승인된 계정·프로젝트 잔액과 키 연결을 확인한 별도 검증 단계에서 제한적으로 수행한다. 실제 AI 모드 오류를 fake 추천으로 몰래 대체하지 않는다.

## 3. Supabase 연결과 권한

publishable key는 전체 DB 연결 자격이 아니다. 현재 서버 코드가 다중 SQL·조인·트랜잭션을 사용하므로, 초기 이전은 psycopg 계열 PostgreSQL 드라이버와 session pooler로 설계한다. 단일 행 REST 호출을 이어 붙여 출고·완료 원자성을 흉내 내지 않는다. pooler 주소·DB 역할·비밀번호·CA는 소유자가 제한된 경로로 설정하며 채팅·문서에 실제 값을 넣지 않는다.

현재 로그인 API의 요청·응답, Bearer 방식, 1시간 세션, 계정 세션과 가구 세션 구분을 우선 유지한다. local_accounts·auth_sessions 등의 명칭은 기존 코드 호환 명칭이며 저장 위치는 Supabase가 된다. Supabase Auth로의 별도 인증 전면 교체는 이번 최소 이전에 넣지 않는다.

서버는 모든 개인 API 요청마다 계정·가구·역할·객체 소속을 검사한다. public/anon/authenticated 역할은 보호된 개인 테이블을 직접 조회·변경할 수 없게 하고 서버 역할은 필요한 테이블만 접근한다. 서버의 DB 역할이 전체 행을 읽는 설계에서는 RLS만으로 개별 사용자 격리가 완성됐다고 주장하지 않는다. 사용자 단위 격리 책임은 서버 인증·객체 권한 검사와 함께 검증한다. schema 변경 권한은 실행 서비스 역할에 주지 않는다.

## 4. 기존 코드에서 필요한 이전 작업

| 현재 확인한 코드 | 이전 명세 |
|---|---|
| open_db마다 initialize·DDL·선택 seed 실행 | schema 변경은 버전 migration으로 분리. 서비스 시작·요청 중 DDL과 demo seed 실행 금지 |
| sqlite3 연결·Row·? placeholder·lastrowid | PostgreSQL 연결·행 매핑·파라미터 바인딩·RETURNING으로 변경. 공개 repository 계약은 유지 |
| 직접 SQL이 API·추천·조리·개인화에 분산 | 핵심 서비스의 저장·조회 경로를 PostgreSQL 계약으로 이관. 연결 문자열만 바꾸지 않음 |
| BEGIN IMMEDIATE로 출고 직렬화 | 재고·이벤트 행 잠금, 잔량 조건부 변경, UUID 유일 제약으로 동시성 보장 |
| 완료 중 cooking_inventory_event_links CREATE | migration에서 사전 생성하고 이벤트 유일 연결·섭취 저장·세션 완료를 한 트랜잭션으로 처리 |
| /api/inventory·chat의 별도 JSON 재고 | 보호된 Supabase 재고에 연결하거나 시연 경로에서 명시적으로 제외. 예시 JSON을 실제 재고로 안내하지 않음 |
| 가족 등록·조회 main 추가 반영 | 등록·account-login·가구 생성·구성원 생성과 인증된 목록 조회를 재사용. 전체 설정·초대 UI는 별도 |

기존 값은 관계를 보존해 변환한다. 인증 토큰은 재로그인시키는 방식을 우선하고, 실제 개인정보가 든 DB를 검증 없이 복제하지 않는다. 1차 검증은 합성 가구 두 개로 한다. 현재 쿼리의 SQLite 문법·날짜 함수·ON CONFLICT·DDL·참조·타입은 항목별로 검토한다.

A 출고만 재고를 차감한다. B 완료는 같은 가구의 applied stock_out과 중량을 검증하고 이벤트를 1개 조리에만 연결한다. A 출고와 B 완료는 별도 트랜잭션이므로 B 실패 시 이미 출고된 재고를 자동 복원하지 않는다. UUID·기존 출고 ID로 재시도하며, 중복 완료는 기존 상태를 확인해 처리한다.

## 5. AI 요청과 실패 처리

서버가 권한 범위의 데이터만 조회 → 규칙 검증 → 최소 요청 구성 → 필요한 범주화 → 검증용 Ollama → 고정 allowlist·wire schema 최종 확인 → OpenAI → 출력·후보 검증 순서로 연결한다. Ollama에 DB 자격을 주거나 LangChain 도구가 제한 없는 SQL을 실행하게 하지 않는다.

현재 privacy_gateway의 inspector는 선택적이고 예외 시 기존 deterministic 경로를 유지한다. **클라우드에서 검증용 AI 검사를 필수로 설정하는 모드에서는 검사 미실행·오류를 통과로 처리하지 않도록 보강**한다. 민감정보 발견은 privacy_blocked, 필수 검사 서비스 장애는 api_error로 외부 호출을 중단하는 계약을 적용한다. 기존 후보 코드 검증·안전 필터와 자유 문장 표시 제한은 유지한다.

단일 요청 총 처리 예산은 우선 90초 이내, 브라우저 대기는 120초 후보로 두고 구현 시 C와 합의한다. 현재 C timeout은 20초이므로 CPU 모델의 60~90초 처리를 그대로 연결하지 않는다. 모델·외부 API·대기열에 개별 시간 상한과 전체 deadline을 적용하고 바쁠 때 무한 대기하지 않는다. 숫자는 발표 전 측정으로 줄이거나 수정하되 UI와 서버가 일치해야 한다.

## 6. 구현·검증·배포의 완료 단위

| 순서 | 한 단위 | 완료 기준 |
|---|---|---|
| 1 | PostgreSQL 저장·권한 기반 구현 | 합성 가구 2개로 로그인·조회·가구 격리, 스키마 버전 관리, seed 차단, 접속 실패 안전 처리 검증 |
| 2 | 핵심 식사 트랜잭션 이전 | 추천→조리→A 출고→B 완료와 동시 출고·중복·부족·롤백 검증. 재고 1회 차감 유지 |
| 3 | AI 서버 실행 계약 구현 | 내부 Ollama·LangChain·필수 검사 장애·외부 전송 차단·deadline·원문 로그 차단 검증 |
| 4 | 배포 파일 준비 | Linux 의존성·systemd·health·환경 예시·중지/재기동 절차 검토. C 파일 수정은 담당자 합의 |
| 5 | 합성 환경 첫 배포 | 별도 서버 생성 허가 범위에서 실행. 실제 RAM·지연·재기동·권한·지출 확인. 이 문서는 생성 승인이 아님 |
| 6 | 기능별 완주 | 식후 피드백부터 기획·화면·서버를 하나씩 연결. 나머지는 별도 단위로 종료 |

서버 생성 전까지 1~4는 로컬 코드·계약·테스트 준비 범위다. 실제 PostgreSQL 시험 환경이 필요하면 별도 합성 로컬 환경으로 검증하며 서비스용 기기 DB와 구분한다. 실제 Supabase migration은 소유자와 적용 범위를 합의한 후 실행한다.

## 7. 발표일까지의 운영 계획

2026-11-26부터 12-22까지 양 끝 날짜를 포함해 **27일** 예산으로 잡는다. 40 GB 디스크를 계속 유지하고 공인 IPv4는 실행 중에만 자동 할당하는 가정이다. 크레딧은 약 USD 100이며 다른 자원·프로젝트 소모는 별도다.

| 운영 가정 | 발표일까지 기본 소모 |
|---|---:|
| 매일 4시간 × 27일 | USD 16.92 |
| 매일 8시간 × 27일 | USD 30.39 |
| 앞 26일 하루 8시간 + 발표일 24시간 | **USD 32.39** |
| 27일 24시간 상시 | USD 84.26 |

기준 단가는 서버 0.1197/h, IPv4 0.005/h, 디스크 3.84/30일이다. OpenAI 사용·추가 트래픽·스냅샷·로그·세금 등은 별도다. 상시 가동도 산술적으로 USD 100 아래지만 여유가 작아 기본안으로 삼지 않는다. **권장 운영은 평소 하루 최대 8시간, 발표 당일 필요 시 종일 가동**이다. 사용하지 않는 시간에는 명시적으로 중지하며 자동 중지 구성은 이후 구현·검증한다.

발표 전날부터 합의된 시연 시간에는 자동 중지가 끼어들지 않게 하고, 종료 시각은 발표 일정을 확인한 뒤 설정한다. 12월 22일 전에 코드·모델·의존성을 고정하고 합성 시나리오 리허설, Supabase 휴면 여부, 계정·토큰·잔액·네트워크 접속, 재기동을 확인한다. 발표 종료 후 실행 중지·원본 삭제·보존할 데이터·디스크 정리는 사용자 확인을 받아 별도 처리한다. 지금 예약·삭제·자동화는 생성하지 않았다.

## 8. 이번 명세의 완료 판정

서버 배치·DB 연결·권한·AI 경계·코드 변경 범위·실패 처리·발표일 예산·후속 완료 단위를 정리했으므로 **배포·연결 명세 작성은 완료**다. Supabase 실제 용량 답변 대기와 향후 구현·실측을 v1 작성의 미완료 조건으로 남기지 않는다. 현재 무료 한도 가정은 실제 이전 전에 소유자 수치와 대조한다.

실제 main 테스트는 이번 문서 작성에서 재실행하지 않았다. 이전 219개 테스트 결과를 가족 등록이 추가된 최신 main이나 PostgreSQL 이전 결과로 표시하지 않는다.
