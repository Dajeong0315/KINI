# KINI 3인 역할 분담 및 통합 순서

> 이 문서는 프로젝트 맥락을 처음 보는 팀원 또는 AI에게 그대로 전달하는 시작 문서다. 작업 전 처음부터 끝까지 읽고, 자신의 역할 외 영역은 직접 수정하지 않는다.

## 0. 프로젝트 한눈에 보기

KINI는 가족이 음성 또는 화면으로 저녁 식사를 요청하면, **이번 식사 참여자**, 냉장고 재고, 재료 신선도, 알레르기·사용자 설정 제한, 영양 균형, 조리 시간, 선호를 함께 고려해 메뉴를 제안하는 서비스다.

대표 사용 흐름은 다음 다섯 단계다.

```text
가족/참여자 선택
→ 메뉴 추천 3개와 근거 확인
→ 메뉴 선택
→ 조리 중 재료·양 변경 또는 질문
→ 실제 섭취 기록과 다음 추천 개인화
```

핵심 페르소나는 가족 영양 관리자이며, 자녀 알레르기·편식, 체중 관리, 냉장고 재료 소진, 시니어 식단이라는 보조 요구를 함께 다룬다. 한 가정의 모든 사람이 항상 먹는 것이 아니라, 아빠·엄마·아이·할머니 중 이번 끼니 참여자만 선택할 수 있어야 한다.

## 1. 현재 구현 상태

현재 프로젝트는 Flask + SQLite 기반 로컬 데모다.

- 구현됨: 가족·참여자·재고·레시피·알레르기·사용자 설정 제한·영양 목표, 하드 필터, 점수 기반 추천, 조리 세션, 재료 중량 변경, 식사 기록, 선호 메모리, 데이터 품질 표시, 공식 데이터 import MVP
- 구현됨: `no_safe_recommendation`, `requires_confirmation`, `data_quality`, 알레르기/라벨 미확인/영양 누락 후보 제외
- 구현됨: 공식 데이터의 staging → validation → quarantine → explicit publish → release pointer 구조
- 구현됨: 기존 STT/TTS, `/api/voice`, 별도 음성 추천 API
- 테스트 기준: 이전 작업 종료 시 `python -m pytest -q` 68개 통과
- 화면 연결 상태: 재고 조회·영양 조회·일반 조리 질문만 실제 API와 연결됐다. 가족 선택, 추천 카드, 조리 변경, 식사 기록은 아직 정적 UI 또는 부분 데모다.

현재 주요 코드 위치:

| 영역 | 위치 |
|---|---|
| Flask 시작점 | `app/main.py` |
| 추천 규칙 엔진 | `app/services/recommendation_engine.py` |
| 추천·조리 API | `app/services/recommendation_api.py` |
| SQLite schema/migration | `app/services/recommendation_repository.py` |
| 기존 Ollama/LLM 경계 | `app/services/recommendation_llm.py`, `app/prompts/` |
| 데이터 품질·정규화 | `data_quality.py`, `ingredient_normalization.py`, `unit_conversion.py` |
| 공식 데이터 import MVP | `app/services/data_import/`, `scripts/import_*.py` |
| 모바일 UI | `app/templates/`, `app/static/` |

## 2. 이미 확정된 아키텍처 원칙

### 데이터 위치

- **ThinQ 클라우드**: 향후 연동되는 냉장고·재고 데이터의 원본 시스템이다.
- **로컬 SQLite**: 이름, 가족 관계, 상세 건강/알레르기 정보, 원문 대화·음성, 개인 식사 이력처럼 민감한 데이터를 보관한다.
- **Supabase(PostgreSQL)**: 개인을 식별할 수 없는 운영 지표만 저장한다. 예: 모델 지연, 오류 코드, 집계 사용량, 품질 지표. 민감 SQLite 데이터를 동기화하지 않는다.
- **Redis**: 원본 DB가 아닌 성능 캐시다. release 기반 공식 영양 데이터, 일반 RAG 검색 결과, 비식별 운영 집계 등에 사용한다. 원문 개인정보·상세 건강 정보·토큰·키는 넣지 않는다.

### AI 역할

- **OpenAI API**: 고품질 의도 해석, 자연스러운 설명, 대화, 일반 RAG 응답의 주 모델이다. 모델명은 고정하지 않았으며, 비식별 평가셋에서 품질·지연·비용을 비교해 선정한다.
- **Ollama**: OpenAI로 보내기 전의 로컬 안전 게이트다. 개인정보 탐지·제거·최소화와 외부 전송 가능 여부 판단을 맡는다. OpenAI를 이기기 위한 주 모델 튜닝은 우선순위가 아니다.
- **로컬 규칙 엔진**: 알레르기, 사용자 설정 제한, 영양, 재고, 유통기한, 데이터 품질을 최종 판정한다. LLM 출력은 이 규칙을 우회할 수 없다.
- **OpenAI API 실패**: 추천 결과를 만들지 않는다. 화면에는 `AI 연결 오류로 추천을 만들지 못했습니다. 잠시 후 다시 시도해 주세요.`만 표시한다. 규칙 기반 대체 메뉴도 추천으로 표시하지 않는다.

### 개인정보 경계

OpenAI로 보낼 수 있는 것은 `2인 저녁`, `저염`, `새우 제외`, `20분`, 비식별 재료 코드처럼 최소화된 구조화 조건뿐이다. 이름, 사용자/기기 ID, 음성 원본, 원문 전사, 대화 원문, 상세 질환명, 위치·연락처, 정확한 식사 이력은 외부 전송 금지다.

이름을 지우는 것만으로 비식별화된 것이 아니다. 드문 질환·알레르기 조합과 자유 텍스트도 재식별 위험이 있으므로 코드화된 최소 제약으로 축약한다.

### 건강 서비스 경계

KINI는 의료 진단·치료·질환별 처방·알레르기 안전 보증을 하지 않는다. 사용자가 설정한 저염, 특정 재료/알레르겐 제외, 일반 영양 목표만 보수적으로 반영한다. 정보가 부족하면 안전하다고 단정하지 않고 제외 또는 확인 요청으로 처리한다.

## 3. 이번 스프린트의 목표

ThinQ, Supabase, Redis, Ollama, OpenAI를 실제 서비스로 무리하게 연결하는 것이 목표가 아니다. 먼저 **mock과 명확한 인터페이스**로 아래를 완성한다.

1. 개인정보가 OpenAI·Supabase·Redis로 새지 않는 경계
2. OpenAI 오류 시 추천을 중단하는 일관된 API/UI 상태
3. ThinQ·Supabase·Redis adapter를 실제 비밀값 없이 교체 가능한 구조
4. 피그마의 5단계 사용 흐름을 실제 로컬 API로 연결할 준비

목표: ThinQ 연동을 고려한 하이브리드 구조를 만들되, 세 사람이 같은 파일·DB 스키마·API를 동시에 수정하지 않는다.

## 역할 A — 데이터 플랫폼·연동 담당

### 책임

- ThinQ 연동 어댑터와 로컬 재고 캐시 경계 설계
- 로컬 SQLite 민감 데이터와 Supabase 비식별 운영 데이터의 분리
- 공식 식품 데이터 release import·publish·rollback 운영 보강
- Redis 캐시 대상, TTL, 무효화, 접근 제어 설계·구현
- 데이터 동기화 상태, release ID, cache version 제공

### 소유 영역

- `app/services/integrations/` (ThinQ·Supabase·Redis 어댑터)
- `app/services/data_import/`
- `app/services/recommendation_repository.py`의 migration·repository 부분
- `scripts/`의 import·sync·cache 운영 스크립트
- `docs/공식_식품데이터_import_설계.md`
- `docs/아키텍처_결정사항.md`의 데이터·캐시 부분

### 만들 API

- 데이터 release·동기화·캐시 상태를 보여주는 읽기 전용 API
- 개인 데이터를 포함하지 않는 Supabase 운영 이벤트 기록 인터페이스

### 하지 않는 일

- OpenAI prompt·Ollama 개인정보 필터의 판단 로직 수정
- 화면 HTML/CSS/JS 수정
- 추천 점수나 알레르기 하드 필터 정책 변경

## 역할 B — AI 안전·추천 엔진 담당

### 책임

- OpenAI API 기반 체인 설계와 모델 평가
- Ollama 기반 외부 전송 전 개인정보 검사·최소화 게이트
- OpenAI 요청 allowlist와 차단 규칙
- 로컬 정책·규칙 엔진의 하드 필터 및 추천 점수 유지·리팩터링
- OpenAI 오류 시 추천 중단·재시도 상태 구현
- 모델 출력이 규칙 엔진을 우회하지 못하도록 검증

### 소유 영역

- `app/services/ai/` 또는 기존 LLM 관련 서비스
- `app/services/recommendation_engine.py`
- `app/prompts/`
- `app/services/recommendation_llm.py`
- 추천·음성추천·조리 세션 관련 API handler
- AI 평가 fixture와 모델 benchmark 스크립트

### 만들 API 계약

- 추천 요청/응답의 구조화 schema
- `api_error`, `privacy_blocked`, `no_safe_recommendation` 상태 코드와 사용자 표시용 메시지
- 설명용 데이터와 규칙 엔진 근거의 구분

### 하지 않는 일

- Supabase 테이블과 Redis 인프라 직접 변경
- ThinQ 동기화 로직 구현
- 화면 HTML/CSS/JS 수정

## 역할 C — 모바일 UX·API 통합·품질 담당

### 책임

- 피그마 사용자 흐름을 실제 모바일 화면과 연결
- 가족 참여자 선택 → 추천 → 추천 근거/확인 필요 → 조리 변경 → 섭취 기록 흐름 구현
- OpenAI 오류·개인정보 차단·동기화 지연·추천 불가 UX 설계
- API 응답의 `data_quality`, `warnings`, `requires_confirmation`, `stale_unvalidated` 표시
- 실제 휴대폰/Tailscale 접속 E2E 테스트와 사용성 피드백 수집

### 소유 영역

- `app/templates/`
- `app/static/`
- 화면별 UI 테스트와 E2E 시나리오 문서
- `docs/휴대폰_데모_사용_가이드.md`
- 피그마 사용자 흐름과 API 화면 매핑 문서

### 하지 않는 일

- DB migration·Supabase·Redis 구현
- 모델 prompt·규칙 엔진 정책 변경
- API 응답 형식을 임의로 변경

## 공통 계약

### API 계약 파일

`docs/API_계약서.md`를 단일 기준 문서로 둔다. 역할 B가 추천·조리 API를, 역할 A가 데이터 상태 API를 작성한다. 역할 C는 문서 승인 전 API 형식을 가정해 구현하지 않는다.

각 endpoint에는 최소한 아래를 명시한다.

- 요청/응답 JSON 예시
- 성공·실패 상태
- 개인정보 포함 금지 필드
- `data_quality`, `requires_confirmation`, `warnings` 처리
- 호출 실패 시 화면 행동

### 공유 파일 보호

아래 파일은 충돌이 잦으므로 담당자 외 수정하지 않는다.

| 파일/영역 | 단일 수정 담당 |
|---|---|
| `app/main.py`, `requirements.txt`, 환경 설정 | 역할 A |
| `recommendation_engine.py`, `recommendation_llm.py`, `app/prompts/` | 역할 B |
| `app/templates/`, `app/static/` | 역할 C |
| `recommendation_repository.py` migration | 역할 A |
| 추천·조리 route handler | 역할 B |

다른 역할이 수정이 필요하면 직접 고치지 않고 issue 또는 PR 코멘트로 담당자에게 요청한다.

## 동시에 진행하는 작업 패키지

세 역할은 아래 공통 준비만 끝나면 **동시에 시작**한다. 공통 준비는 1회 짧은 합의 작업이며, 기능 구현을 기다리는 단계가 아니다.

### 공통 준비 — 첫날 30~60분

- `docs/API_계약서.md`에 v1 요청·응답 예시를 고정한다.
- 추천·조리·데이터상태 API의 mock JSON fixture를 `tests/fixtures/api_contract/`에 추가한다.
- 아래 상태 문자열은 변경 없이 사용하기로 합의한다.
  - `recommendations_available`
  - `no_safe_recommendation`
  - `privacy_blocked`
  - `api_error`
  - `stale_unvalidated`
- 이 합의 뒤에는 각 역할이 서로의 실제 구현 완료를 기다리지 않는다.

### 병렬 트랙 A — 데이터·ThinQ·Supabase·Redis

역할 A는 mock과 interface부터 만든다. 실제 ThinQ 계정, Supabase 프로젝트, Redis 서버가 아직 없어도 진행 가능하다.

- `ThinQInventoryProvider`, `OperationalMetricsRepository`, `CacheProvider` interface와 in-memory mock 구현
- 로컬 SQLite/ThinQ/Supabase/Redis 데이터 경계 테스트
- Redis cache key, TTL, release 기반 무효화 로직을 fake cache로 테스트
- Supabase로 보낼 수 있는 비식별 운영 이벤트 schema 작성
- 공식 데이터 release와 cache version 연결

**산출물:** A 전용 adapter 코드, mock fixture, repository 단위 테스트.
**다른 역할 의존성:** 없음.

### 병렬 트랙 B — Ollama 개인정보 게이트·OpenAI 체인·규칙 엔진

역할 B는 OpenAI 실제 키 없이 fake client로 구현·테스트한다.

- 외부 전송 payload allowlist와 개인정보 차단/축약기 구현
- Ollama 또는 deterministic 필터를 통한 로컬 사전 검사 interface 구현
- OpenAI client adapter와 fake client 구현
- OpenAI 오류 시 `api_error`를 반환하고 추천을 중단하는 흐름 구현
- 기존 규칙 엔진이 후보·제외 사유·영양 사실을 먼저 확정하고, OpenAI는 설명만 하도록 정리
- 모델 품질·지연·비용 평가셋 초안 작성

**산출물:** B 전용 AI 서비스, fake OpenAI 테스트, 규칙·개인정보 테스트.
**다른 역할 의존성:** A의 실제 adapter가 아닌 v1 mock contract만 필요.

### 병렬 트랙 C — 모바일 UX·피그마 흐름·E2E 화면

역할 C는 `tests/fixtures/api_contract/`의 mock JSON으로 먼저 화면을 연결한다.

- 가족 선택 → 추천 → 근거/확인 필요 → 조리 변경 → 섭취 기록의 5단계 화면 연결
- `api_error`, `privacy_blocked`, `no_safe_recommendation`, 동기화 지연 상태 UI 구현
- 응답의 `data_quality`, `warnings`, `requires_confirmation`, `stale_unvalidated` 표시
- 실제 API 호출을 한 곳(`app/static/api_client.js` 등)으로 모으고 mock/live 전환 가능하게 구현
- 휴대폰·Tailscale 접속용 핵심 E2E 시나리오 문서와 체크리스트 작성

**산출물:** C 전용 HTML/CSS/JS, mock UI 테스트, 휴대폰 검증 체크리스트.
**다른 역할 의존성:** v1 mock contract만 필요.

### 병렬 트랙 D — 공통 검증(각자 담당, 마지막에 함께 실행)

세 사람이 각자 기능 테스트를 추가하고, 통합 시점에 아래를 함께 확인한다.

- OpenAI 요청 payload에 금지 필드가 없는지
- Supabase 운영 이벤트에 개인 식별 정보가 없는지
- Redis 캐시 miss·만료·무효화가 안전 규칙을 우회하지 않는지
- OpenAI 오류 시 화면이 추천을 표시하지 않고 재시도 안내를 하는지
- ThinQ 동기화 지연 시 화면이 스냅샷 시각과 상태를 알리는지

## 통합 순서

1. 세 병렬 트랙의 PR을 mock contract 기준으로 독립 리뷰·병합한다.
2. 역할 A의 mock adapter를 실제 ThinQ/Supabase/Redis adapter로 교체한다.
3. 역할 B는 실제 adapter를 사용해 payload·오류 처리 contract test를 실행한다.
4. 역할 C는 mock 모드를 끄고 실제 로컬 API로 5단계 흐름을 E2E 검증한다.
5. Tailscale 환경에서 정상·OpenAI 오류·개인정보 차단·동기화 지연 시나리오를 확인한다.

## Git 작업 규칙

- **공통 기준 커밋**: 팀 작업을 시작하기 전에 현재 로컬 구현·설계 문서·테스트를 하나의 기준 커밋으로 원격 기본 브랜치에 푸시한다. 이 커밋 해시를 팀 채널에 공유한다.
- **작업 시작**: 각 팀원은 작업 전 원격 기본 브랜치를 fetch/pull 하고, 공유된 기준 커밋이 HEAD에 포함됐는지 확인한 뒤 자기 역할 브랜치를 만든다. 로컬에 미완료 변경이 있으면 pull 전에 먼저 커밋하거나 stash가 아닌 별도 안전 브랜치로 보관한다.
- **기준 갱신**: 공통 API 계약 또는 schema migration이 기본 브랜치에 병합되면, 각 팀원은 새 작업을 시작하기 전 기본 브랜치를 다시 반영한다. 이미 진행 중인 기능 브랜치는 담당자가 충돌을 해결하며, 다른 팀원의 작업을 reset/force push로 덮어쓰지 않는다.
- 사람마다 기능 브랜치를 하나씩 사용한다.
  - `feature/data-platform-thinq-cache`
  - `feature/ai-privacy-openai-chain`
  - `feature/mobile-recommendation-flow`
- 한 PR은 한 책임만 가진다.
- migration/API 계약 변경은 먼저 리뷰받고, UI는 mock 응답으로 병렬 개발한다.
- main에 병합하기 전 전체 pytest, API contract test, 모바일 핵심 E2E 시나리오를 실행한다.
- `git push --force`, `git reset --hard`, 다른 팀원 브랜치의 강제 변경은 사용하지 않는다.

### 팀원별 시작 명령 예시

기준 커밋이 기본 브랜치에 푸시된 뒤, 각 팀원은 아래 순서로 시작한다. 기본 브랜치 이름은 저장소의 실제 이름(`main` 또는 `master`)을 사용한다.

```powershell
git fetch origin
git switch main
git pull --ff-only origin main
git log -1 --oneline
git switch -c feature/내-역할-브랜치
```

작업 전에는 `git status --short`가 비어 있는지 확인한다. 기준 커밋이 필요한 migration·fixture·문서를 모두 포함하므로, 팀원은 이를 다시 만들지 않고 자신의 소유 영역만 수정한다.
