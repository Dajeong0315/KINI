## 0. 요약

| 항목 | 결과 |
|---|---|
| 목표 | 냉장고 안 카메라 영상으로 식재료의 추가·제거를 자동 인식하고 재고 테이블에 반영 |
| 최종 인식 엔진 | **YOLOE-v8m-seg (글자 프롬프트, 학습 없음)** + 고정 카메라 보정 + Unknown 처리 |
| 시연 영상 결과 | h264 영상: 버터 −1 ✓ / h265 영상: 오렌지 −1 ✓ (두 영상 모두 증감 정답) |
| 처리 시간 | CPU(i7-9700) 사진 1장 약 0.4~0.8초 |
| Unknown 처리 | 범용 검색어(`object`) + 쪼개진 물체 묶기 + **사용자 이름 입력·기억** |
| 재고 연동 | Supabase 재고 DB (촬영 기록 → 변경 후보 pending → 확인 함수로 재고 반영, 식재료 1개 = 1행, 칸 위치) |
| 분류 모델 실험 | Kaggle 시험 정확도 0.876 → **0.9476** (목표 0.95 에 5장 부족). 실사 적용은 보류 |

핵심 결론
1. 상자 라벨 데이터가 없는 상황에서는 **품목 이름(글자)만으로 찾는 열린 어휘 모델(YOLOE)** 이 유일하게 바로 쓸 수 있는 선택이었고, 같은 크기에서도 **모델 계열(YOLOE vs YOLO-World) 차이가 버전 차이보다 컸다**.
2. 인식 정확도의 상당 부분은 모델이 아니라 **고정 카메라라는 조건을 이용한 후처리**(같은 자리 = 같은 물건, 안 바뀐 자리는 그대로)에서 나왔다.
3. 목록에 없는 물체는 "범용 검색어"만으로는 잡히지 않았고, **쪼개진 상자 묶기 + 사람에게 한 번 물어보고 기억하기**가 실제로 동작했다.
4. Kaggle 공개 데이터로 만든 분류기는 공개 시험 세트에서 0.95 근처까지 올랐지만 냉장고 실사에서는 도메인 차이로 쓸 수 없었다. 다음 단계의 핵심은 **부스 현장 사진 수집**이다.

## 1. 배경과 목표

시연 시스템은 냉장고 안 카메라로 문 닫힘 전후 사진(before·after)을 찍고, 사진별 품목 개수의 차이로 추가·제거를 계산한다.
원칙은 **"모델은 사진별 품목 개수만 답하고, 추가·제거 계산과 확인 필요 여부는 코드가 정한다"** 이다. 모델이 직접 "무엇이 빠졌다"고 말하게 하면 오류를 검증할 수 없기 때문이다.

요구사항
- GPU 없는 노트북에서 동작 (부스 PC)
- 시연 품목 25종 (우유, 버터, 수박, 오렌지, 포도, 주스 등 — `config.ITEMS`)
- 목록에 없는 물체는 "모른다"고 할 수 있어야 함
- 인식 결과를 팀 재고 DB(Supabase)에 반영

## 3. 전체 구조

```text
카메라/영상 ─→ 문 닫힘 감지(detector.py) ─→ before·after 사진
                                              │
                    ┌─────────────────────────┘
                    ▼
   YOLOE-v8m 탐지 (품목 25종 글자 프롬프트 + 범용어 object/item + 손/팔)   [vision.py _detect]
                    ▼
   쪼개진 작은 상자 묶기 → Unknown 묶음                                    [_group_fragments]
                    ▼
   Unknown ↔ 사용자 이름표(CLIP 생김새 + 위치) 비교 → 같으면 그 품목        [_recall]
                    ▼
   before·after 보정 (같은 자리 이름 통일 / 안 바뀐 자리 채우기 / 낮은 점수 변화 버림)  [_reconcile]
                    ▼
   품목별 개수 → 추가·제거 계산, 확인 필요 판단, 칸 위치(LOC)               [build_result, compare]
                    ▼
   Unknown 남아 있음 → 사용자에게 이름 입력 → 기억 → 다시 계산               [main.py ask_unknown_labels]
                    ▼
   capture + stock_event(pending) → 재고 반영 시 confirm_stock_event() (백그라운드)  [supabase_sync.py]
```

## 4. 탐지 모델 선정 과정

### 4.1 경과

| 순서 | 엔진 | 결과 | 다음 결정 |
|---|---|---|---|
| 1 | OpenAI Vision API (gpt-4o-mini 등) | 크레딧 없음(HTTP 429)으로 실사용 불가 | PC 에서 직접 돌리는 YOLO 로 전환 |
| 2 | YOLO-World `yolov8l-worldv2` | 같은 물건에 상자 중복, 다른 품목 이름이 겹쳐 붙음 | 품목 구분 없는 NMS(agnostic NMS) + 전후 이름 통일 추가 |
| 3 | YOLO-World `yolov8m-worldv2` | "v8m 정도로" 요구에 맞춰 중형으로. **수박·버터를 놓침** | 같은 크기의 다른 열린 어휘 모델 검토 |
| 4 | **YOLOE `yoloe-v8m-seg`** (채택) | 수박·버터 인식, 두 영상 모두 증감 정답 | 검색어 조정(`"watermelon wedge"`, `"yellow butter block"` 등) |

### 4.2 왜 열린 어휘 모델인가
- 일반 YOLO 탐지 모델(YOLOv8/11/26)은 COCO 80종으로 학습되어 있다. 버터, 수박, 우유팩, 두부, 김치, 주스병 등 시연 품목 다수가 COCO 에 없다.
- 이를 쓰려면 품목마다 **상자 라벨이 달린 학습 데이터**가 필요한데 현재 없다.
- 따라서 **품목 이름(글자)만으로 찾는 열린 어휘 모델**(YOLO-World, YOLOE)이 필수였다. 품목은 `config.YOLO_PROMPTS` 의 영어 검색어로 지정한다.

### 4.3 상위 모델 비교 실측 (h264 영상, 가려진 4번째 오렌지)

| 모델 | 설정 | 잡힌 오렌지 (실제 4개, 1개는 가려짐) | 사진 1장 (CPU) |
|---|---|---|---|
| **YOLOE-v8m (채택)** | 기본 | 3개 | **약 0.4초** |
| YOLOE-v8l | 기본 | 1~2개 | 약 0.9초 |
| YOLOE-v8l | 고해상도 1280 | 3개 + 오인식 1개 | 약 3.5초 |
| YOLOE-11l | 고해상도 1280 | 3개 + 오인식 1개 (수박을 오렌지로) | 약 3.5초 |

- 대형·최신 모델이 **정확도 이득 없이 최대 9배 느렸다**. 가려진 오렌지는 어떤 모델도 잡지 못했다 → 모델이 아니라 **진열 방식·카메라 각도** 문제.

## 5. 고정 카메라 보정 (`_reconcile`)

YOLOE 단독 결과에는 같은 물건이 before 에선 사과, after 에선 오렌지로 잡히거나, 한쪽 사진에서만 놓치는 경우가 있었다. 카메라가 고정이라는 점을 이용해 세 단계로 보정한다.

| 단계 | 규칙 | 해결한 문제 |
|---|---|---|
| 1. 이름 통일 | before·after 에서 IoU ≥ 0.5 인 상자는 같은 물건 → 점수가 높은 쪽 이름으로 통일 | before 사과 0.30 ↔ after 오렌지 0.36 이 "사과 −1, 오렌지 +1" 로 잡히던 문제 |
| 2. 놓친 물건 채우기 | 한쪽에만 있는 상자인데 그 자리 픽셀이 거의 안 바뀌었으면(변화 비율 < 0.15) 반대쪽에도 있는 것으로 채움 | 한쪽 사진에서만 인식이 빠져 "추가/제거" 로 잘못 세던 문제 |
| 3. 낮은 점수 변화 버림 | 그래도 한쪽에만 있는 상자는 점수 ≥ 0.35 일 때만 추가·제거로 인정 | 잡음 상자 |

추가로 발견·수정한 문제
- **자동 노출**: h265 영상에서 사람이 움직이자 화면 전체 밝기가 163 → 138 로 바뀌어, 그대로 있는 물건 자리도 "바뀜"으로 판정 → 사과 +1, 토마토 +1 오인식. **영역 평균 밝기를 빼고 비교**하도록 바꿔 해결.
- **주스 2개**: 선반의 오일·식초병이 `juice bottle` 로 잡힘. 보정과 무관하게 before·after 양쪽에 똑같이 있어 증감에는 영향 없음 (재고 개수에는 포함됨 → 한계로 기록).

## 6. 목록에 없는 물체(Unknown) 처리

### 6.1 범용 포괄 프롬프트 (Generic Prompt) 트릭

**요청 내용**: 모델을 두 개 띄우기 무거운 환경이므로 `set_classes()` 에 구체 품목과 함께 포괄 단어(`"object"`, `"item"`, `"obstacle"` 등)를 넣는다. YOLOE 의 글자 임베딩은 의미 유사도로 품목을 고르므로, 어느 품목에도 안 맞는 물체는 포괄 단어로 밀려난다. 그 상자를 화면에 `Unknown` 으로 표시하고, 배경(벽·선반)이 잡히지 않도록 평소보다 높은 점수(0.5~0.6 이상)에서만 인정한다.

**구현**
- `config.YOLO_GENERIC_PROMPTS = ["object", "item"]`, `YOLO_UNKNOWN_CONF = 0.5`
- 클래스 순서: `[품목 25종] [범용어] [손·팔]`. 범용어가 1등인 상자 중 점수 0.5 이상만 Unknown.
- Unknown 은 재고 개수에 넣지 않고 `result["unknown"]` 에 따로 셈. 개수가 바뀌면 '확인 필요'.

**결과 (실측)**
- 두 시연 영상에서 **점수 기준을 0.05 까지 낮춰도 범용어가 1등인 상자가 한 번도 없었다**. 수박·주스병·포도 그릇 모두 구체 품목 중 하나가 더 높은 점수를 받았다.
- 기존 결과(h264 버터 −1, h265 오렌지 −1)에는 영향 없음.
- 결론: 품목 목록이 25종으로 넓으면 대부분의 물체가 "가장 비슷한 품목"으로 흡수된다. 이 트릭만으로는 Unknown 을 만들 수 없어 아래 두 방법을 추가했다.

### 6.2 쪼개진 물체 묶기

- 문제: 포도 그릇이 화면 오른쪽 끝(x 887~960)에서 **사과·오렌지 작은 상자 2~6개**(점수 0.11~0.40)로 쪼개져 "사과 1" 같은 재고가 생겼다.
- 규칙: 아래를 모두 만족하는 상자가 서로 겹치거나 붙어 있으면(짧은 변의 15% 이내) **2개 이상을 하나의 Unknown 묶음**으로 합친다.
  - 점수 < 0.45 (`YOLO_GROUP_MAX_CONF`)
  - 넓이 ≤ 화면의 1% (`YOLO_GROUP_MAX_AREA`)
  - 묶음 찾기에만 점수 0.1~0.2 의 약한 조각도 사용 (`YOLO_FRAGMENT_CONF`), 이런 조각은 혼자서는 개수에 넣지 않음

시행착오

| 버전 | 문제 | 수정 |
|---|---|---|
| 1차 (크기 제한 없음) | h264 영상에서 **나란히 붙은 큰 오렌지 2개(0.38·0.37)** 까지 묶여 포도로 오인식 | 화면 1% 이하 작은 조각만 묶음 → 오렌지 3 유지 |
| 2차 (점수 0.2 이상만) | 실제 실행(압축 전 원본 프레임)에서 0.2 근처 조각이 생겼다 사라져 묶음이 2개로 쪼개지고 "사과 1" 이 남음 | 0.1 이상 약한 조각까지 묶음 찾기에 사용 → 2회 연속 실행에서 묶음 1개로 안정 |

### 6.3 사용자 이름 입력과 기억 (Human-in-the-loop)

- 창 모드에서 Unknown 이 남아 있으면 영상을 멈추고 해당 상자를 빨갛게 표시한 뒤, 터미널에서 이름을 묻는다. (Enter 만 누르면 건너뜀, `--no-window` 에서는 묻지 않음)
- 이름 → 품목: 기존 품목의 한글 이름·영문 id·검색어와 같으면 그 품목(`포도`·`Grape`·`grapes` → grape, `소시지` → ham), 아니면 새 품목 `user_N` 추가 (재고·Supabase 에 입력한 이름 그대로).
- 기억: `user_labels.json` 에 **CLIP ViT-B/32 생김새 특징(512차원) + 상자 위치** 저장 → 결과를 즉시 다시 계산 → 다음 촬영부터 Unknown 을 이름표와 비교해 자동 적용.

유사도 기준 결정 (실측, 포도 이름표 기준 코사인 유사도)

| 비교 대상 | 유사도 |
|---|---|
| 같은 포도 (after, 이름표 원본) | 0.996 |
| 같은 포도 (before, 같은 자리) | 0.894 |
| 주스병 | **0.881** |
| 오렌지 (여러 개) | 0.844 ~ 0.850 |
| 버터 | 0.841 |
| 포도 조각 하나 | 0.829 |
| 수박 | 0.756 |

- 냉장고 배경이 비슷해서 **다른 물체끼리도 0.84~0.88** 이 나온다. 그래서 다음처럼 정했다.
  - 같은 자리(IoU ≥ 0.5): 0.85 이상이면 같은 물체 (`USER_LABEL_SIM_SAME_PLACE`)
  - 다른 자리: 0.95 이상이어야 같은 물체 (`USER_LABEL_SIM`) → 옮기면 다시 물어볼 수 있음 (오인식보다 재질문이 안전)

### 6.4 검증

| 시험 | 결과 |
|---|---|
| h265 사진, 기억 없음 → `포도` 입력 | Unknown 1개 질문 → 포도 1 로 재계산, 오렌지 −1 유지 |
| h265 사진, 다시 실행 | 묻지 않고 포도 1 자동 인식 |
| h265 영상 (`python main.py`, 창 모드) 2회 | 두 번 모두 Unknown 1개(포도 그릇 전체)로 질문, 오렌지 −1 |
| h264 사진 | 버터 −1, 오렌지 3, Unknown 없음 (포도 오인식 없음) |
| 이름 매핑 | 포도·Grape·grapes→grape, 햄·소시지→ham, green onion→green_onion, 올리브오일→user_1 |

## 7. (실험) 2단계 분류 모델 — Kaggle 데이터

YOLOE 의 품목 혼동(오렌지/레몬, 오일병/주스 등)을 줄이려고 **2단계 인식**(YOLOE 상자를 잘라 분류 모델이 재판정, 점수가 낮으면 "모름")을 시험했다.

### 7.1 데이터
- Kaggle `alyamibrahim/smart-fridge-food-dataset` (kagglehub, 약 607 MB). 품목별 폴더에 사진만 있는 **분류용** 데이터 (상자 없음)
- 20종: apple, banana, bread, butter, carrots, cheese, chicken, cucumber, eggs, fish, grapes, lettuce, mango, milk, onions, orange, peppers, strawberry, tomato, yogurt
- train 12,237 / val 2,043 / test 2,042 (클래스당 약 600 / 100 / 100)
- 품질 점검: train 내 라벨이 다른 완전 중복 **0건**, test 중 train 과 거의 같은 사진 282장 중 라벨 불일치 **0건** → 한계는 데이터가 아니라 특징(백본) 품질

## 8. 모델 선택 근거 — 왜 YOLO11 / YOLO26 이 아니라 v8m 인가

> 예상 질문: "최신 YOLO11, YOLO26 이 있는데 왜 2023년 모델인 YOLOv8m 을 썼나?"

### 8.1 'v8m' 이 쓰인 두 자리

| 자리 | 모델 | 역할 | 상태 |
|---|---|---|---|
| A. 물체 탐지 (메인) | YOLOE-v8m-seg | 품목 상자 찾기·개수 세기 | 시연에 사용 |
| B. 품목 분류 (실험) | YOLOv8m-cls | Kaggle 미세조정 기준선 | 최종에서는 CLIP 앙상블로 교체 |

### 8.2 공통 근거
1. **크기(m)는 요구사항이었다**: "yolov8m 정도로" 요청 + GPU 없는 CPU 환경. 속도를 정하는 것은 버전보다 크기다.
2. **병목은 버전이 아니었다**: 실사 실패 원인은 (1) 물건끼리 가림, (2) 학습 데이터와 냉장고 사진의 도메인 차이. 버전을 올려도 그대로다 (8.3, 8.4 실측).
3. **교체 비용이 거의 없다**: 탐지는 `config.YOLO_MODEL` 한 줄, 분류는 `train_kaggle_cls.py --model <이름>` 인자 하나로 바뀐다.

### 8.3 A. 탐지
- 일반 YOLO11/26 탐지 모델은 COCO 80종이라 시연 품목 다수를 모른다. 실제 비교 대상은 "v8 vs 11 vs 26" 이 아니라 **"YOLOE-v8 vs YOLOE-11 vs YOLOE-26"** 이다.
- 같은 영상 실측(4.3): YOLOE-11l·v8l 이 정확도 이득 없이 최대 9배 느렸다. YOLO-World-v8m → YOLOE-v8m 교체로 수박·버터 문제가 풀렸다 → **계열 차이 > 버전 차이**.
- YOLOE-26 (s/m/l, ultralytics 8.4.0 이상)은 설치된 8.4.131 에서 쓸 수 있지만 **아직 실측하지 않았다**. NMS 없는 구조라 CPU 속도 이득 가능성이 있어 후속 과제로 둔다.

### 8.4 B. 분류 (Ultralytics 공식 수치, 224px)

| 모델 | ImageNet top-1 | 파라미터 |
|---|---|---|
| YOLOv8m-cls (사용) | 76.8% | 17.0M |
| YOLO11m-cls | 77.3% | 10.4M |
| YOLO26m-cls | 78.1% | 11.6M |

- v8m → 26m 은 ImageNet **+1.3%p**. 반면 백본을 CLIP 으로 바꾼 효과는 Kaggle 시험 **+7.2%p** (0.876 → 0.9476). 사전학습 방식의 차이가 버전 차이보다 훨씬 컸다.
- 그 CLIP 앙상블조차 실사에서는 대부분 "모름" → 버전을 올려도 실사 문제는 데이터 문제로 남는다.

### 8.5 인정해야 할 한계
- YOLO11m-cls / YOLO26m-cls 를 같은 Kaggle 데이터로 직접 학습해 비교하지 않았다 (CPU 학습이 모델당 1시간 이상).
- YOLOE-26 탐지 모델은 아직 실측하지 않았다.
- 정확한 주장: "v8m 이 최선이다" 가 아니라 "**v8m 으로 시연 요구를 만족했고, 상위 버전이 병목(가림·도메인 차이)을 풀지 못한다는 실측 근거가 있다**".

- YOLO26 문서: https://docs.ultralytics.com/models/yolo26/

## 9. Supabase 고내 재고 DB 연동

DB 는 팀 DB 담당이 설계한 구조(테이블 4개 + 뷰 + 함수 3개)를 그대로 쓰고, 인식 코드와 맞물리도록 일부만 보강했다. 자세한 구조·규칙은 [DB 설계 설명](DB_재고테이블_설계_설명.md).

### 9.1 구조

| 이름 | 역할 |
|---|---|
| `food_item` | 식재료 목록 (`food_id` = 인식 코드의 item_id) |
| `capture` | 촬영 1회 = 1행 (엔진, 사진 경로, result.json 원본, 처리 시간) |
| `stock_event` | 변경 후보 (`pending` → `confirmed`/`rejected`), 칸 `loc_x`·`loc_y` |
| `fridge_stock` | 실제 재고, 식재료 1개 = 1행 (넣은·꺼낸 시각, 소비기한, 먹음/폐기) |
| `current_stock` (뷰) | 품목별 현재 개수 (화면용) |
| `confirm_stock_event()` / `reject_stock_event()` / `reset_demo()` | 재고 반영(선입선출)·거절·초기화 — 한 트랜잭션 |

### 9.2 연동 흐름 (`supabase_sync.py`)

| 프로그램 시점 | DB 작업 |
|---|---|
| 인식 결과가 나옴 | `capture` 1행 + `stock_event`(pending) 품목·칸별 1행 |
| 재고 반영 (자동 또는 `y`) | pending 이벤트마다 `confirm_stock_event()` |
| 거절 (`n`) | `reject_stock_event()` |
| 영상 파일 시험의 첫 촬영 | DB 재고를 카메라 before 개수에 맞춤 (`source='manual'` 이벤트 → 확인) |
| 목록에 없는 품목 (사용자 이름표 새 품목) | `food_item` 자동 등록 |

- 칸: 상자 중심이 화면 가로 3등분 중 어디인지(L/C/R), 세로 경계 위·아래(1 = 위 칸, 2 = 아래 칸)인지. DB 규칙과 같게 맞췄다.
- 멱등성: `capture` 중복 무시, 같은 촬영의 이벤트가 있으면 다시 만들지 않음, pending 이 아닌 이벤트는 다시 확인하지 않음 → 재전송해도 두 번 반영되지 않음.
- 장애: 네트워크·5xx 는 `captures/supabase_queue.jsonl` 에 보관 후 다음에 먼저 재전송, 재고 부족 같은 4xx 는 로그만 남기고 이벤트는 pending 유지.
- 보안: 노트북은 service_role 키(`.env`), 화면은 anon 키로 읽기만. 사진은 올리지 않고 경로 문자열만 저장 (KINI 비식별 원칙).
- 구현: Supabase REST(PostgREST)를 `requests` 로 직접 호출 (추가 라이브러리 없음).

### 9.3 팀 초안 `schema.sql` 에서 바꾼 점

| 바꾼 점 | 이유 |
|---|---|
| `food_item` 에 인식 품목 19종 추가 (초기 재고 0, `shelf_days` 임시값) | 오렌지·버터·수박·포도·주스 등이 외래키 때문에 저장되지 않음 |
| `service_role` 에 자동 증가 시퀀스 권한 명시 | 서버가 이벤트를 넣을 때 필요 |
| `stock_event (capture_id)` 인덱스 | 재전송 시 같은 촬영의 이벤트 조회 |

### 9.4 검증 (실제 Supabase 키 없이)

수정한 `schema.sql` 을 **실제 PostgreSQL(pgserver)** 에 그대로 실행하고, Supabase REST 요청을 SQL 로 바꿔 `service_role`/`anon` 역할로 실행하는 시험 서버(`tests/test_supabase_sync.py`)로 확인했다. 함수·GRANT·RLS·외래키가 실제로 동작한다.

| 시험 | 결과 |
|---|---|
| 설치 직후 | 품목 25종, 데모 5종 각 1 ✓ |
| 첫 결과 저장 | 시작 재고 맞춤(manual 11건, 칸별 분리) + capture + 오렌지 −1 pending, 재고는 그대로 ✓ |
| 확인 / 재확인 | 오렌지 3 → 2, 다시 보내도 2 유지 ✓ |
| 재고보다 많이 빼기 (수박 −3) | 함수 거부, pending 유지 ✓ |
| 거절 | rejected, 재고 변화 없음 ✓ |
| 새 품목 `user_1` | food_item 자동 등록, 칸 L,2 ✓ |
| 네트워크 장애 | 2개 보관 → 복구 후 재전송, 사과 +2 ✓ |
| anon 키 | 읽기 성공, 쓰기·`reset_demo()` 거부(401) ✓ |
| **h265 영상 전체 실행** (`main.py`) | capture 1행(4640ms), 이벤트 12건 confirmed, 오렌지 1개 consumed → 버터 1·수박 1·오렌지 2·포도 1·주스 2 ✓ |

시험용 PostgreSQL(Windows)에는 시간대 데이터가 없어 `'Asia/Seoul'` 을 같은 뜻의 `+09:00` 으로 바꿔 실행했다. **실제 Supabase 프로젝트에서는 아직 실행하지 않았다.**

## 10. 한계와 다음 단계

### 한계
1. 가려진 물건은 어떤 모델도 잡지 못한다 → 한 층으로 펼쳐 진열, 위에서 내려다보는 카메라 각도.
2. 범용 검색어 Unknown 은 시연 영상에서 동작하지 않았다. 실제로 동작한 것은 묶기 + 사용자 이름표.
3. 사용자 이름표 생김새 비교는 배경 영향이 커서 같은 자리일 때 주로 동작한다 (옮기면 재질문).
4. 오일·식초병이 주스로 세어진다 (증감에는 영향 없음, 재고 개수에는 포함).
5. 칸(LOC) 경계는 화면 비율 근사값 → 부스 카메라에서 조정 필요.
6. Supabase 는 실제 PostgreSQL + REST 흉내 서버로 검증. 실제 Supabase 프로젝트에서는 아직 미실행. `shelf_days` 는 임시값.
7. 분류 모델 실험은 Kaggle 0.9476 (목표 0.95 미달), 실사 적용 불가.
