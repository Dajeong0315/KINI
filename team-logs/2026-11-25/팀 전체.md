### 측정 조건과 근거

- 모델 비교: 당시 Windows 개발 PC·CPU, `qwen2.5:3b-instruct-q4_K_M` / `qwen3.5:4b-q4_K_M`, 합성 사례 4개×각 2회/모델. 새 레시피 과제 평균과 전체 8응답의 JSON 결과를 구분한다. 정보 부족 확인·위험 요청 거절은 사례 관찰이다.
- 모델 적용: Qwen3.5 non-thinking·컨텍스트 4096. 당시 전환 테스트 33개 통과 보고. PR 병합은 원격에서 확인했지만 현재 전체 앱을 재시험하지 않았다.
- A 전체: `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` 환경의 `python -m pytest -q`, 당시 85.04초. Windows의 `xxhash` DLL 로딩 차단으로 기존 Ollama 설정 테스트 1개 실패. 코드 결함 여부·환경 문제 해결 후 재검증 필요.
- SQLite 무결성·FK와 Supabase 권한·제약 rollback 검사는 [PR #3](https://github.com/Dajeong0315/KINI/pull/3) 및 [개인 기록](김재웅.md)의 당시 보고다. 원격 DB와 로컬 테스트를 이번 회고에서 다시 실행하지 않았다.
- 데이터 출처·버전: 규칙·import 검증은 fixture·시연 데이터 기반. 정식 영양·레시피 전체 수집은 미실행. 실제 사용자·의학적 효과 평가가 아니다.
- 처리 구간: 모델 표는 LLM 응답이며 STT→LLM→TTS 전체 시간이 아니다. 실제 ThinQ·카메라·OpenAI·휴대폰 E2E는 이 결과로 입증하지 않는다.
- 기존 B/통합 테스트 78·81개와 A의 101개는 기준 커밋·검증 대상·환경이 달라 전후 성능 비교나 합산에 사용하지 않는다.

- 총 실험 횟수·설정: 확장 모델 비교 당시 합성 4사례×2회×5모델=40회 보고. 모든 개발 반복 횟수는 미확인이다. TTL 24시간/15분은 시작 제안값으로 측정된 최적값이 아니다.
- 실패한 시도와 원인: STT PyAV DLL 차단, 별도 Ollama 테스트 xxhash DLL 차단, 정식 데이터 인증키 미설정. 서로 다른 장애를 하나의 해결 완료로 묶지 않는다.
- 사용자 경험 의미: 화면·음성보다 먼저 재고·개인 조건·출처·데이터 버전을 신뢰할 수 있는 처리 경로로 연결해야 한다.

## 통합 상태와 다음 검증

- 역할 간 연동: A 데이터 상태·재고 API와 B 추천·조리, C 화면을 연결한다. 기존 JSON 재고와 SQLite 재고의 기준 및 전체 쓰기 버전 정책을 합의한다.
- A: 식약처 승인 키 설정 → 정식 수집·검증·staging/publish → Supabase 카탈로그 다운로드 → B 추천용 투영. 만개의레시피 이용 권한·제공 방식 확정.
- A+B+C: 로그인 HTTP·전체 객체 권한·식사 참여자/실제 섭취자/기록자 구분, 화면 상태·오류 계약 점검.
- B: 개인정보 최소화·실제 전송 차단·OpenAI 오류/응답 검증. C: 시연 표시·확인 대기·오류 UI와 모바일 E2E.
- 캐시: hit/miss·TTL·release 무효화·DB fallback을 fake/in-memory부터 시험. 현재 Redis provider·패턴 수집기는 미구현.
- 다음 측정: A 재고 이벤트 재시도·동시성·release 복구, B 고정 평가셋 및 STT/추론/TTS 구간 지연, C 핵심 시나리오 성공률. 담당자 검토 후 결과 갱신.
