## 작업 내용과 판단

### 1. 로컬 모델 비교와 Qwen3.5 전환

- 기존 로컬 모델로 우리 서비스의 상황 이해·레시피 생성이 가능한지 질문하고 같은 합성 사례로 모델을 비교하도록 요청했다.
- AI의 비교 보고에서 Qwen3.5 4B가 정보 부족 확인·위험 요청 거절에서 나은 사례를 보였지만 새 레시피 생성은 더 느렸다. ‘큰 모델이면 무조건 좋다’는 식으로 판단하지 않고 품질·속도·메모리를 함께 검토했다.
- Qwen3.5 4B로 코드를 바꾸고 브랜치에 올리도록 요청했다. 당시 33개 테스트 통과 보고가 있었다. [PR #1](https://github.com/Dajeong0315/KINI/pull/1)은 작성 시 원격 조회에서 **병합 완료**, 병합 커밋은 `5d80dc2`로 확인했다.
- 단순 재고 조회는 DB·코드로 처리하고, AI는 해석·짧은 설명에 집중하며 새로운 레시피 생성은 별도로 검증하는 최적화 방향을 검토했다. 전체 음성 지연 개선이 완료됐다는 뜻은 아니다.

### 2. 실제 ThinQ 연결과 시연 범위 결정

- LG 클라우드·디벨로퍼스 연동을 확인하는 과정에서 **실제 ThinQ 인증·토큰 발급·실기기 연결은 이번 데모에서 진행하지 않는 방향**을 명확히 했다.
- 원하는 결과를 ‘ThinQ와 유사한 화면에서 KINI 흐름을 실제로 경험하는 데모’로 설명했다. 기기·인식 유입은 모의 처리하되 API·DB의 저장·조회·변경은 실제로 동작하도록 요청했다.
- 사용자 흐름은 냉장고 진입 → 재고 확인 → 이번 식사 참여자 선택 → 메뉴 추천 → 조리 중 변경·질문 → 섭취 기록 → 다음 추천 반영이다.
- 현재 A의 데이터 경로가 구현됐다고 해서 C의 전체 화면 흐름과 휴대폰 E2E까지 완료된 것은 아니다.

### 3. 로컬 개인정보와 공개 카탈로그 분리

- 민감정보는 로컬에 두고 서비스에 필요한 공개 데이터는 클라우드에서 관리하는 구조를 검토했다.
- **SQLite:** 가족·알레르기·영양 목표·실제 재고·입출고·식사·섭취·로그인 세션.
- **Supabase:** 공개·승인 식품 영양·레시피·출처·배포 버전과 개인을 식별하지 않는 운영 집계.
- 내가 제시한 워크플로우의 가구별 입출고 cloud 저장은 AI 구현 과정에서 로컬 보관으로 조정됐다. 이 차이를 다시 설명받고 보관 경계를 정리했다.
- 로컬 AI는 개인정보 탐지·최소화, OpenAI는 근거 기반 해석·설명이라는 목표 구조를 확인했다. 감지와 실제 전송 차단은 별개이며, 최종 알레르기·재고·영양 제한은 로컬 규칙 엔진이 맡는다. B의 전체 실연동 완료로 기록하지 않는다.

### 5. ‘DB를 먼저 채운 후 검색’하는 구조와 용량 예산

- 테이블만 만드는 것에서 끝내지 않고 **식약처·승인 레시피 데이터를 사전 수집·정규화·검증해 DB에 넣고, 실행 중에는 그 DB를 검색해 AI에 근거를 제공**하는 방향을 반복해서 명확히 했다.
- 식품·영양성분·레시피·재료·조리 단계·출처/release의 컬럼과 연결 키를 검토했다. 같은 이름만으로 식품을 합치지 않고 기준량·단위를 보존하며 누락값을 0으로 바꾸지 않는 방향이다.
- 무료 플랜을 사용하고 냉장고 변화 데이터를 위한 여유를 남기도록 요청했다. 당시 설계 기준 500MB를 공개 카탈로그 200MB, 냉장고 변화용 150MB, 운영 집계 20MB, 시스템 30MB, 교체·복구 50MB, 안전 여유 50MB로 나눴다. **논리 예산이며 물리 공간을 선점한 것은 아니다.**
- 당시 개발 문서는 전체 300MB 운영 목표·350MB 경고·400MB 신규 카탈로그 적재 중단, DB 약 12.1MB를 보고했다. 실제 개인 입출고 원본은 SQLite에 남기므로 150MB 예약을 cloud 개인 이력 기능의 완료로 해석하지 않는다.
- 전체 페이지 수집·checkpoint·정규화·SQL 배치 준비 코드, 용량 제한 SQL과 신규 테스트가 추가됐다. 이 후속 변경은 조회 당시 **로컬 미커밋 상태**로 PR #3의 `9be602b`와 구분한다.
- **실제 식품·레시피는 0건.** 당시 정식 API 키가 미설정이어서 전체 수집·cloud 적재·publish는 실행하지 못했다. 만개의레시피 제공 방식·이용 권한도 미확정이다.

### 6. 반복 패턴·캐시·Redis 개념 정리와 설계 추가

- 반복 요청을 재사용하는 방법을 질문하고 설계에 반영하도록 요청했다.
- DB는 원본, 반복 패턴 분석은 무엇이 자주 조회되는지 측정, 캐시는 결과 재사용, Redis는 이를 구현하는 도구로 구분했다.
- 공개 식품·레시피는 24시간, 승인 FAQ는 15분을 시작 정책으로 제안했다. release/version별 키를 사용하고 장애 시 원본 DB를 조회한다. 현재 가족별 최종 추천·알레르기·실재고·원문·토큰은 캐시하지 않는다.
- `docs/A_반복패턴_및_캐시_설계.md`, `config/cache_policy.json`이 로컬에 추가됐다. **설계·비활성 설정 단계**이며 provider·패턴 수집기·실제 Redis 연결·캐시 효과 측정은 미완료다.

## 성능 측정과 비교

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 모델 | Qwen2.5 3B instruct Q4_K_M | Qwen3.5 4B Q4_K_M |
| 새 레시피 생성 평균 | 15.27초 | 20.71초 |
| 모델 메모리 | 약 2.02GiB | 약 2.93GiB |
| 토큰 생성 속도 | 9.54개/초 | 6.79개/초 |
| 요구 JSON 필드·타입 준수 | 6/8회 | 6/8회 |

- 측정 조건: 당시 Windows 개발 PC·CPU, 합성 사례 4개를 모델별 각 2회. 총 8응답/모델 중 새 레시피 과제 평균과 전체 JSON 준수 결과를 구분한다. GPU·드라이버·온도·캐시 등 전체 재현 조건은 원본 보고서 추가 확인이 필요하다.
- 변화량: 새 레시피 생성 평균은 **5.44초 증가, 약 35.6% 느려짐**. 이 비교만으로 모델 전반의 품질이나 전체 음성 지연을 판단하지 않는다.
- 정보 부족 확인·알레르기 충돌·악성 지시 대응은 소수 합성 사례 관찰이다. 안전성 보장·일반 정확도로 표현하지 않는다.
- A 전체 pytest 당시 보고: **101 passed, 1 failed / 85.04초**. Windows에서 `xxhash` DLL 로딩 차단으로 기존 Ollama 설정 테스트가 실패했다. 실행 보고 명령은 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` 환경에서 `python -m pytest -q`. 실패를 제외하고 전체 통과로 기록하지 않는다.
- 사전 적재·용량 후속 테스트: **신규 12개 통과** 보고. 앞의 전체 결과와 커밋·대상이 다르므로 합쳐서 ‘113개 전체 통과’로 쓰지 않는다.
- SQLite 2개 DB의 테이블 53개, integrity_check=ok·FK 위반 0개, Supabase 권한·제약 rollback 시험은 개발 문서의 당시 보고다. 이번 회고에서 DB를 다시 조회하지 않았다.
- 미측정: 실제 사용자 추천 품질, 영양 효과, 실제 식품 수집 성공률, STT→추론→TTS 전체 지연, Redis hit rate·p95·전후 개선.

- 추가 실험: 고정 평가셋·같은 환경에서 모델 품질/오류율과 음성 구간별 지연, 이벤트 재시도·동시성, release 교체/rollback, 실제 데이터 매핑 검증을 수행한다.
