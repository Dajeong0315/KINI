## 작업 내용과 판단

### 1. Supabase 연결과 핵심 식사 흐름 통합

- 기존 SQLite·Ollama 합성 배포와 최신 PostgreSQL 코드를 대조하고, 기존 public 카탈로그를 복제하지 않는 직접 읽기 어댑터와 private 명시적 연결을 사용했다.
- 당일 구현 기록상 private schema·제한 앱 역할·migration 001~009 적용 뒤 실제 앱 자격 인증과 TLS `verify-full`을 확인하고 서버를 PostgreSQL/rules-only로 전환했다. 초기 인증서 실패는 공식 Supabase CA 적용으로 해결했으며 검증 강도를 낮추지 않았다.
- 공개 식품 347,421행·레시피 1,152행을 확인한 시점에 private 식품 카탈로그 복제는 0행, 최소 시연용 명시적 참조는 3행이었다. 원본 로컬 SQLite는 이전하지 않았다. 이 건수는 당일 문서의 조회 시점 값이다.
- 새 합성 시연 자료로 실제 카탈로그 추천·출처·저장 재조회, 인증된 재고 요청, 조리 변경·섭취 저장·이력·리포트 화면을 연결했다. 원재료 영양 추정치와 demo/확인 필요 표시를 유지했다.
- 재고는 A 출고 확정에서 한 번만 차감하고 B 완료는 확정 출고 연결·식사 저장만 수행한다. 저장 응답을 잃었을 때 기존 조리 GET으로 완료 상태를 복구하는 경로를 보완했다.
- 사용자 휴대폰 시험에서 비슷한 재고 행·식사 기록이 여러 개 보인 현상을 DB와 대조했다. 문서상 에이전트 검증 입고와 사용자 입고는 서로 다른 이벤트였고, 식사 3건도 에이전트 검증 2건과 사용자 시험 1건으로 구분됐다. 중복 생성이라고 단정해 저장 로직을 다시 만들지 않았다.

### 2. AI 운영 범위와 모델 설정

- 현재 배포는 `rules-only`, 외부 AI는 `disabled`로 운영한다. 추천·안전 규칙과 고정 설명을 사용하며 비활성 경로를 실제 AI 성능 검증 완료로 표현하지 않는다.
- 로컬 기본 모델은 `qwen2.5:3b-instruct-q4_K_M`으로 맞췄다. 모델 설치·설정 확인과 실제 추론 성능은 구분한다. 후속 운영 검증 범위의 보조 검사·OpenAI 호출은 0회, 해당 유료 호출 비용은 USD 0이다. 이날 초기 배포의 Ollama readiness 호출까지 없었다는 뜻은 아니다.

### 3. 식후 평가와 개인화 통합

- 기존 `MealFeedbackService`와 revision 계약을 재사용하고 migration 010으로 **식사당 평가 1건**을 보장했다. 참여자 중 한 명이 제출하고 다른 참여자도 같은 평가를 수정할 수 있으며 재시도를 새 평가로 집계하지 않는다.
- 맛은 같은 메뉴 추천 순위, 간·난이도는 같은 메뉴 조리 안내에만 반영한다. 평가로 알레르기·영양·재고·조리량을 바꾸지 않는다. 건너뛰기는 학습에서 제외하며 자동 재질문은 하지 않는다.
- 초기 개인화 정책은 최근 평가 최대 5건, 만족 +2/보통 0/불만족 -2 평균, 기존 개인화 총점 상한 ±15다. 실제 사용자 품질로 최적화된 가중치가 아니라 제한된 초기 정책이다.
- 실제 서버·PC 화면에서 저장·동일 요청 재시도·수정·재로그인 복원을 확인한 기록이 있다. migration 10과 호환되는 복구 배포본도 준비했다.

### 4. Vision 결과 연결과 후속 팀원 보고 반영

- PR #40에서는 민준의 최신 Vision 전체 브랜치를 통째로 병합하지 않고 저장된 실제 결과를 기존 재고 API로 전달하는 bridge와 확인 화면을 통합했다. 동일 촬영에는 동일 UUID를 사용하며 개수를 g으로 추정하지 않는다. 이후 전체 소스 통합은 아래 PR #41로 구분한다.
- KINI 확인 경로는 후보 → 표준 재료·수량/중량 근거·출고 lot 확인 → 확정/거절이다. Unknown은 자동 확정하지 않고, 거절은 재고를 바꾸지 않는다. 응답 유실 때 같은 내용으로 재시도한다.
- 후속 대화에서 민준의 테이블·뷰 추가 및 ERD의 PK/FK 육안 확인 보고와 DB 업데이트 성공 보고를 전달받았다. 첨부 화면에서는 전·후 비교의 카스테라 1개 입고와 DB 반영 성공 표시를 확인했다. 원문 채팅·사진·네트워크 주소는 저장소에 싣지 않는다.
- 따라서 **Vision 단독 경로에서 휴대폰 전·후 비교 → 품목·개수 변화 감지 → Supabase 재고 업데이트 성공 사례 확보**로 검증 상태를 갱신했다. 이는 팀원 보고·화면 근거이며 이번 대화에서 직접 DB를 재조회하거나 FK 위반·동시성까지 시험한 결과는 아니다.
- Vision 측 직접 Supabase 재고 경로와 KINI의 확인 기반 재고 경로는 구분한다. 이 성공 사례만으로 KINI 추천·조리·섭취까지 전체 통합 완료로 확대하지 않는다. 양쪽 쓰기를 동시에 켜 이중 반영하지 않도록 경로 대조가 필요하다.
- **저울은 프로젝트 범위에서 제외한다고 결정했다.** 저울 실측은 남은 완료 조건에 넣지 않는다. 개수와 g의 근거는 구분하고, 중량 근거가 없으면 미확인으로 남긴다. 이 결정이 기존 g 기반 API·영양 계산을 개수 기반으로 전환하는 코드 변경까지 완료했다는 뜻은 아니다.

## 판단·시행착오와 한계

- 초기 문서의 접근 불가·미적용·미커밋 문구는 작성 시점의 상태다. 같은 날 후속 연결·배포·PR 병합 근거로 갱신해 읽고, 과거 중단 상태를 현재 상태로 보고하지 않는다.
- 동일 재료의 여러 lot와 시험용 식사 기록을 중복 저장으로 오해하지 않도록 이벤트·세션 근거를 대조했다. 에이전트 시험 데이터와 사용자 시험 데이터를 구분하는 것이 필요했다.
- 개인화 +2가 항상 최종 점수에 더해진다는 초기 점검 가정은 기존 상한 때문에 맞지 않았다. 실제 적용량을 구분했고 상한을 완화하지 않았다.
- 운영 DB 파괴적 시험·실패 주입 결과와 별도 합성 DB 시험을 혼동하지 않는다. 후속 Vision DB 성공도 단일 성공 사례이며 PK/FK 무결성·인식 정확도·통합 전체 안정성의 보증이 아니다.
- 접근 가능한 근거는 이 대화·사용자 첨부 화면·Git 이력·저장소 문서다. 다른 당일 대화 전체, 팀 채팅 전체, 운영 DB·서버의 현재 상태는 이번 기록 작성에서 직접 재확인하지 않았다.

## 협업과 다음 작업

- 민준의 휴대폰 CV 경로와 KINI 재고 이벤트 경로의 테이블·단위·식별자·확정 책임을 대조하고, 실제 입력이 KINI 화면·추천에 반영되는지 확인한다.
- 실기기 입고·출고·거절·동일 촬영 재전송·재접속에서 중복 반영이 없는지 팀과 확인한다. 이미 있는 합성/HTTP 시험과 실제 휴대폰 시험을 구분해 기록한다.
- 저울 없이 사용하는 품목·개수와 영양 계산의 중량 근거 표시를 정리한다. 근거 없는 개수→g 환산은 하지 않는다.
- 남은 8단계는 발표용 휴대폰·카메라·장비·네트워크 리허설이다. 저울 검증은 제외한다.
