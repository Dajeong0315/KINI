### 11월 13일 — 수집 데이터의 편향을 점검하고 DCX 분석 재설계

- **목표:** 이미 수집한 댓글에서 사용자의 행동과 기회영역을 탐색한다.
- **문제 발견:** 자동 경험 후보 5,008건과 고신호 1,780건의 관계를 질문했고, 8건이 전자에 없는 이유를 추적했다. 두 목록은 서로 다른 조건으로 독립 선별된 것으로 재현했다. 사용자는 2만여 댓글 중 많은 양을 초기에 조건식으로 걸러내면 유용한 표현을 놓칠 수 있다고 문제를 제기했다.
- **조치:** 원본을 보존하고 광고·후보 여부를 우선 표시하는 쪽으로 분석 계획을 바꿨다. 실제 댓글을 살펴보며 경험뿐 아니라 의견·감정·계획도 분석할 가치를 확인했다. 데이터가 충분한 유튜브 24,349건을 주 분석 대상으로 정했다. 당시 대부분 영상은 댓글 첫 응답 묶음만 수집된 한계가 있었다.
- **분석:** 단어 빈도만으로는 검색어의 영향과 실제 행동을 구분하기 어렵다고 보고 임베딩과 군집화를 탐색했다. Doc2Vec에 고정하지 않고 방법을 비교했으며, 인사·반응 필터가 유용한 댓글까지 제거할 가능성을 점검했다.
- **결과와 한계:** 24,349건 중 1,067건을 단순 반응 등으로 분리하고 23,282건을 12개 잠정 묶음으로 분석했다는 보고가 있다. 군집 구분력이 낮고 영상 주제의 영향이 있어 검증된 사용자 유형으로 확정하지 않았다. 같은 영상 댓글 쌍의 동일 군집 비율 21.0%, 임의 댓글 쌍 6.5%는 영상 효과를 의심하게 한 탐색 지표다. 사람의 독립 검토와 중요도·만족도 측정이 남았다.
- **표현 수정:** 사용자는 Actor 이름에 행동을 보여주는 동사가 빠졌다고 지적했다. 이에 ‘식사를 준비하려고 한다’처럼 행동 중심의 가설로 고쳤다. 이는 행동이 실제로 일어났는지, 계획인지까지 구분해야 한다는 기준으로 이어졌다.
- **별도 조사:** 시니어 걱정 조사에서는 영상 35개, 댓글·답글 16,414건, 정제 후 16,168건을 보고했다. 위 24,349건과는 별도 분석이며 합산하지 않는다.
- **근거 대화:** 「크롤링 CSV 자료 정리」, 「DCX 분석 Phase 2 임베딩」, 「유튜브 분석 키워드 계획」.

### 11월 14일 — 타깃을 시니어에서 가정 내 영양관리로 확장

- **문제:** 사용자는 결과에 시니어 본인보다 부양 자녀의 고민이 주로 보인다고 지적했다. 영상의 주인공이 시니어라는 이유만으로 댓글 작성자도 시니어라고 추정할 수 없었다.
- **판단:** 팀 방향에 맞춰 맞벌이 가정의 아이 식사, 1인 가구, 시니어의 식사를 분리해 탐색하기로 했다. 작성자 본인·가족·연령 미확인을 구분하고 본인이 영상에서 말한 경험은 댓글과 별도 자료로 취급하도록 계획했다.
- **산출물:** 가정 영양관리 새 분석 계획과 후속 작업용 지시문. 이날 새 분석 실행 요청 중 실패로 표시된 턴이 있으므로 모든 수집이 이날 완료됐다고 적지 않는다.

### 11월 15일 — ‘많은 댓글’보다 ‘질문에 맞는 원문’으로 전환

- **사용자 검토:** 수집 결과가 영양관리보다는 요리·보관의 번거로움에 치우쳐 있고, 기대한 인사이트가 보이지 않는다고 직접 피드백했다. 원본 CSV와 실제 검색어도 확인했다.
- **판단:** 영상 반응과 일반 조언이 많은 댓글을 계속 늘리기보다, 판단·행동·결과가 드러나는 공개 글을 살펴보기로 했다. 기사나 통계로 대체하는 가능성도 열어 두었다.
- **진행:** 공개 글 11편의 원문을 직접 수집해 화자와 행동을 검토했고, 그중 5편이 영양관리의 어려움과 당사자·돌봄 가족의 경험을 함께 보여준다는 보고를 받았다.
- **배운 점:** ‘요리 부담이 영양 걱정보다 더 크다’는 순위는 현재 표본으로 단정할 수 없다. 질문에 맞는 자료의 깊이와 대표성은 다른 문제다.

### 11월 16일 — 소량의 원문을 검증하고 분석 결과의 왜곡을 교정

- **진행:** 브런치·티스토리 등의 글을 추가해 서로 다른 URL 기준 총 25편, 그중 핵심 경험 근거 10편을 확보했다. 100편 확대를 검토했지만 관련성이 낮은 조언·판매글을 섞어 숫자를 맞추기보다 25편의 탐색 분석을 선택했다.
- **시행착오:** 핵심 글에서 추출한 95개 구절을 임베딩·군집화했으나, 군집이 사용자 유형보다 특정 글의 구절을 묶는 경향이 있어 Actor의 근거로 충분하지 않았다. 팀 노트북의 분석을 참고하되 검색 제목·요약이 아니라 실제 본문을 사용했다.
- **사용자 피드백:** 직접 읽은 내용과 DCX 결과가 다르다고 지적했다. 재검토 결과 식재료 보관 문제에는 음식물 폐기뿐 아니라 채소를 꾸준히 먹고 다양한 식단을 유지하려는 목표도 있었다. 자동 분류 결과가 원문의 목적을 지우지 않도록 수정했다.
- **누락 보완:** 실행하지 않은 분석도 빠짐없이 밝히라고 요청했고, LDA 및 기회점수 관련 보고 누락을 보완했다. 계산이 있었다는 사실만으로 점수의 타당성과 고객 대표성이 확보되는 것은 아니므로 산식·입력값을 원본 보고서에서 확인해야 한다.
- **추가 검토:** 건강정보를 다루는 식단 서비스의 개인정보와 의료 조언 경계를 조사했다. 법률 검토 결과를 최종 법률 자문으로 단정하지 않는다.
- **근거 대화:** 「가정 영양관리 DCX 분석 실행」, 「한국 법규와 주의사항 정리」.

### 11월 25일 — 추천 데모 확장과 하이브리드 전환, 안전 경계 리뷰

#### 1. 가족 맞춤 추천의 단계적 구현

- AI에게 기존 STT/TTS를 보존하면서 가족 참여자 선택, 알레르기·나트륨 제한, 재고와 영양을 고려한 추천 데모 구현을 요청했다. 초기 구현 보고의 전체 테스트는 30개 통과였다.
- 이후 개인화 메모리, 조리 변경·섭취 기록, 데이터 정규화·품질 계층을 단계적으로 확장했다. 보고된 테스트는 시점별 48개, 63개로 늘었고, 마지막 정규화 단계에서는 합성 평가 41건 실패 0건으로 보고됐다. 합성 평가는 실제 사용자 성능이 아니다.
- **판단:** AI가 대화·설명을 담당하더라도 알레르기·재고·영양 안전은 로컬 규칙으로 검증하고, 학습된 선호가 명시적인 제한을 덮어쓰지 않도록 했다.

#### 2. 데이터 출처와 배포 경계

- 공식 식품·영양·알레르겐 데이터를 요청 때마다 외부에서 바로 가져오는 대신 출처·버전을 관리하며 검증한 뒤 배포하는 파이프라인을 설계했다.
- import MVP는 raw → staging/검증 → 격리 → 검증된 release → 명시적 publish 흐름으로 구현됐다고 보고됐다. 실제 대량 수집, raw 보관과 재개, 운영 데이터 발행 전 검증은 후속 과제로 남겼다. fixture 기반 데모와 공식 데이터의 운영 반영을 구분한다.
- **근거:** [공식 식품데이터 import 설계](../docs/공식_식품데이터_import_설계.md), [데이터 안전 정규화 설계](../docs/데이터_안전_정규화_설계.md).

#### 3. 협업 브랜치 통합과 환경 문제

- 팀원이 비교한 Qwen/Ollama 변경을 PR #1에서 검토하면서 기존 추천 경로의 모델 설정 불일치를 맞췄다. Git 이력상 PR #1 병합 커밋은 `5d80dc2`다.
- 다른 기준 커밋 `cdfab03`을 올릴 때 원격 main이 5개 커밋 앞서 분기되었다. 강제 푸시 대신 통합 브랜치에서 원격 변경을 병합해 `04e13b2`를 만들었다.
- 통합 테스트에서 `langchain_core` import가 실패했다. 후속 보고에 따르면 저장소 요구사항 자체의 누락이 아니라 로컬 설치 누락이 원인이었고, 격리 환경의 `pip check`, pytest 81개, 합성 평가 41건을 통과한 뒤 통합 브랜치를 푸시했다. 이는 그 시점의 검증이다.
- **상태:** 사용자가 제공한 당시 기준은 `chore/hybrid-architecture-baseline`, `04e13b2`, PR 병합 대기다. 현재 원격 PR의 실시간 상태는 이 문서에서 재확인하지 않았다.

#### 4. 하이브리드 구조와 역할 결정

- 사용자는 ThinQ 연계를 전제로 로컬 개인정보 보호와 OpenAI의 응답 품질을 함께 추구하는 방향을 결정했다. 민감 데이터는 로컬 SQLite, 비식별 운영 데이터는 Supabase, 캐시는 Redis로 나누고 Ollama를 로컬 개인정보 안전 게이트로 두는 설계를 논의했다.
- 의료 진단·치료·질환별 처방이 아닌 일반적인 제안으로 범위를 정했다. API 오류 시 대체 메뉴를 정상 추천처럼 보여주지 않고 `api_error`와 재시도 안내를 선택했다. 모델은 품질·지연·비용 평가 전 고정하지 않기로 했다.
- 세 역할을 A 데이터·연동, B AI 안전·추천, C 모바일 UX로 나눴고 사용자는 B를 맡았다. API 계약 변경은 팀 합의가 필요한 공통 의존성이다. 상세는 [아키텍처 결정사항](../docs/아키텍처_결정사항.md), [3인 역할 분담 및 통합 순서](../docs/3인_역할분담_및_통합순서.md)를 참고한다.

#### 5. 테스트 통과 뒤에도 발견한 개인정보 취약 경로

- **목표:** 외부 AI에는 필요한 비식별 정보만 보내고, 최종 안전 판단은 로컬에서 유지한다.
- **첫 구현 보고:** 허용 목록 기반 payload, fake client, 오류 상태와 API 계약 초안을 추가하고 pytest 75개가 통과했다고 보고됐다. 실제 OpenAI 호출은 하지 않았다.
- **재검토에서 발견:** 사용자는 구현 완료 보고를 그대로 수용하지 않고 별도 리뷰를 요청했다. `excluded_ingredients`의 임의 문자열이 길이 검사만 거쳐 외부 payload에 들어갈 수 있음이 재현됐다. ‘allowlist를 쓴다’는 설명과 실제 데이터 흐름이 일치하지 않았던 사례다.
- **보완:** 검증된 로컬 재료만 코드로 바꾸고 후보명·경고 원문 등을 제거하도록 수정했다는 보고가 있다. fake/capturing client에 전달되는 payload를 검사했고, 당시 pytest 78개 통과로 보고됐다. 개인정보 패턴 검사가 모든 표현을 완벽하게 찾아낸다는 뜻은 아니다.
- **다음 리뷰에서 남은 문제:** reason code가 실제 허용 코드 목록이 아닌 형식만 검사하는 점, 안정적인 재료·레시피 ID의 연결 가능성, AI 자유 문장의 안전성, 실제 HTTP 오류 경로·평가 지표의 검증, 화면의 고정 추천 근거 카드가 남을 수 있는 점이 제기됐다. 마지막 보완 요청의 실행 기록은 **중단(interrupted)** 상태이므로 완료로 기록하지 않는다. 역할 C 소유 화면은 C에게 전달할 항목이다.
- **현재 로컬 확인:** 작성 시점 브랜치는 `feature/ai-privacy-openai-chain`이며 작업 트리에 수정·미추적 파일이 존재한다. 진행 중인 다른 작업과 테스트 상태는 변할 수 있다.
- **근거:** 「구현 AI 안전·추천 엔진」, 「상태별 추천 카드 숨김 처리」, [API 계약서 v1 초안](../docs/API_계약서_v1_초안.md).

## 포트폴리오용 문제 해결 사례

### 사례 1. 댓글 수집량 중심에서 근거 품질 중심으로 전환

- **상황:** 영양관리 문제를 찾기 위해 수만 건의 댓글을 분석했지만, 영상 반응과 조언이 많았고 댓글 작성자의 연령·관계가 불명확했다.
- **내 판단:** 자동 필터가 유용한 의견·계획까지 버릴 수 있고 영상 주인공의 속성을 댓글 작성자에게 적용해서는 안 된다고 문제를 제기했다. 원문을 직접 확인한 뒤 원하는 영양관리 인사이트가 보이지 않는다는 피드백도 제공했다.
- **행동:** AI와 함께 필터 조건을 재현·수정하고 원본을 보존했다. 군집의 영상 편향을 확인했으며, 이후 화자와 행동이 구체적으로 드러나는 공개 글 분석으로 조사 방법을 전환했다.
- **결과:** 별도 원문 조사에서 25편 중 핵심 경험 글 10편을 확보했고, 자동 군집이 글 단위 편향을 보인다는 한계도 확인했다. 가설 탐색의 근거이지 모집단을 대표하는 정량 성과는 아니다.
- **면접에서 설명할 포인트:** “데이터 양이 많아도 질문에 답하지 못하면 수집 단위와 분석 방법을 바꾸고, 원문으로 결과를 반증했다.”

### 사례 2. 일관된 추천과 개인정보 보호를 함께 고려한 구조 결정

- **상황:** 재고 활용, 가족의 알레르기, 건강 목표, 기호를 동시에 반영해야 했다. AI가 매번 다른 결과를 생성하거나 중앙 서버에 민감정보를 모으는 위험이 있었다.
- **내 판단:** 서버 중심 계산의 개인정보 경계를 질문하고, 절대 제외 조건과 점수화·설명을 구분했다. 이후 사용자 경험 품질을 위해 OpenAI를 고려하면서도 로컬 데이터 최소화와 규칙 검증을 유지하도록 방향을 구체화했다.
- **행동:** 안전 필터 → 후보 점수화 → AI 설명이라는 책임 구분, 외부 payload 허용 범위, 오류 시 추천 중단, 의료 조언을 하지 않는 서비스 범위를 팀 문서와 구현 요청에 반영했다.
- **현재 수준:** 데모와 fake client 기반 검증이 진행됐으나 실제 외부 AI 운영 안전성이나 의학적 효과가 검증된 서비스는 아니다.

### 사례 3. 완료 보고와 테스트 수치 뒤의 취약 경로 재검토

- **상황:** AI 안전 경계 구현 보고와 75개 테스트 통과 이후에도 실제 payload에 자유 입력이 들어가는 경로가 남아 있었다.
- **내 행동:** 완료 보고를 독립 리뷰하도록 요청하고 발견된 입력 경로에 대한 수정·테스트 지시를 구체화했다. 재료 정규화, 민감정보 차단, 실제 fake client 전달 payload 검증을 요구했다.
- **결과:** 당시 수정 보고와 78개 테스트 통과를 확인했다. 이후 ID 연결 가능성과 AI 설명 안전성 등 추가 위험을 발견해 후속 작업을 요청했다. 마지막 작업은 중단 상태로 남아 있어 완결된 보안 성과로 쓰지 않는다.
- **면접에서 설명할 포인트:** “기능과 테스트의 존재를 넘어 실제 데이터가 외부 경계에 어떻게 도달하는지 확인했다.”
