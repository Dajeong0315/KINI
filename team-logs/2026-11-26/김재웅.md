# 2026-11-26 | 김재웅

> 작업일: **2026-11-26 (Asia/Seoul)** / 기록 작성·원격 상태 확인일: **2026-11-27**.
> 이 대화에서 확인한 요구사항·AI 구현 및 테스트 출력, 당일 커밋과 저장소 명세를 대조했다. 아래 수치는 11월 26일 실행 결과이며 기록 작성 중 테스트를 다시 실행하지 않았다. 다른 대화의 작업 전체를 수집한 기록은 아니다.

## 오늘의 목표와 담당 범위

- 해결할 문제·목표: C가 HTTP로 로컬 로그인하여 발급받은 가구 토큰으로 A 재고 조회와 B 조리 완료까지 연결한다. 후속으로 최초 계정 등록 → 가족 생성 → 구성원 등록 API를 제공한다.
- 내 역할과 담당한 기능: A 서버 API의 요구사항·권한 경계·완료 기준 결정과 팀 저장소 전달 요청. 기존 로컬 인증을 재사용하고 C 화면·B 조리 차감 서비스는 신규 구현 범위에서 제외하도록 정했다.
- 상태: API·테스트·명세 작성과 팀 저장소 브랜치 푸시 완료. 11월 27일 확인한 main에는 로그인 및 가족 온보딩 커밋이 포함돼 있다. 가족 등록 화면·초대 가입·전체 API 인증 개편은 별도 작업이다.

## 작업 내용과 판단

### 당일 A 데이터 플랫폼 진행

- 11월 25일 개인 기록에 남긴 사전 적재·Redis 검증의 후속 결과를 PR #16의 11월 26일 보고서에서 확인했다. 공개 카탈로그는 식약처 정식 API 전체 페이지를 수집하고 기준 단위·영양·조리 단계가 불충분한 행을 격리한 뒤 배포했다. 이 항목은 A 팀 산출물의 진행 상황이며 개인 구현 분담은 이 기록의 근거만으로 특정하지 않는다.
- 식품 영양 347,324건 중 347,321건 활성·3건 격리, 레시피 1,156건 중 1,152건 활성·4건 격리. 클라우드와 로컬 SQLite의 활성 건수와 배포 버전이 일치했다.
- 적재 후 PostgreSQL 전체 약 166.8MB, 공개 카탈로그 약 155.0MB를 보고했다. 공개 카탈로그 예산 200MB를 유지하고 내부 배분을 식품 80MB·레시피 40MB·공통 80MB로 조정했다. 수치는 당시 적재 상태이며 물리 디스크나 WAL 사용량은 포함하지 않는다.
- 실제 데이터의 식품 상세와 레시피 상세를 각각 두 번 호출해 HTTP 200 → 200, Redis miss → hit를 확인했다. 당시 전체 테스트 155개 통과(127.44초), 마지막 예산 변경 후 관련 테스트 13개 통과를 보고했다. 응답 지연은 미측정이다. [A 적재·캐시 검증 보고서](https://github.com/Dajeong0315/KINI/blob/85daa9f/docs/A_식약처_실제적재_2026-11-26.md)

### 1. HTTP 로그인으로 A 재고와 B 완료 연결

- 변경 전에는 local_identity.login()이 내부 함수로만 존재했다. 내부 토큰을 사용한 테스트는 통과했지만 일반 HTTP 흐름은 토큰 누락으로 B 완료가 401이었다.
- POST /api/auth/login에 login_name, password, household_id를 전달하면 기존 비밀번호 검증과 가구 소속 검사를 거쳐 토큰을 반환하도록 요청했다.
- household_id를 권한 증거로 신뢰하지 않고 서버가 활성 계정·가구 소속·현재 역할을 확인하도록 했다. 없는 계정·잘못된 비밀번호·미소속 가구는 같은 401 응답으로 처리한다.
- AI가 로그인 blueprint·입력 검증·캐시 방지 응답을 구현했다. 토큰 수명은 서버 기준 3600초이며 만료 시각을 반환하고 DB에는 토큰 해시만 보관한다.
- 통합 테스트의 토큰 발급을 내부 login() 직접 호출에서 HTTP 응답 사용으로 바꿨다. 동일 토큰으로 재고 조회 200, A 확정 출고 연결, B 완료 201·섭취 및 영양 기록 생성, 완료 전후 재고 스냅샷 동일성을 확인했다. B의 중복 차감 방지 자체는 이미 존재하던 팀 작업을 재사용했다.

### 2. 최초 계정 → 가족 → 구성원 등록으로 확장

- 로그인 계정과 가족 구성원 프로필의 차이를 확인하고, 가족 하나를 만든 뒤 구성원 네 명을 등록하는 구조를 선택했다. 프로필 네 개가 로그인 계정 네 개를 의미하지 않도록 했다.
- 요청한 흐름은 POST /api/auth/register → POST /api/auth/account-login → POST /api/households → 기존 가구 로그인 → POST /api/households/{id}/members다.
- 가구가 없는 초기 단계에는 별도의 계정 토큰을 쓰도록 했다. 계정 토큰은 가족 생성·소속 가족 목록 전용이며 재고·구성원 접근에는 사용할 수 없다.
- 가족 생성자는 서버에서 owner로 연결한다. 구성원 등록은 owner/editor만 허용하고 viewer는 조회만 가능하다. 등록 필드는 이름·나이와 선택 알레르기·기피 식품이다.
- AI가 기존 SQLite 구조에 계정 세션 테이블과 migration version 3을 추가하고, 기존 계정·프로필·가구 토큰의 보존을 검증했다. 신규 계정 등록 시 데모 가족을 자동 생성하지 않는다.
- 기존 /api/members와 데모 조회가 실제 가족 정보를 우회 노출하지 않도록 서버 조회 권한을 보완했다. C 화면은 수정하지 않았다.
- HTTP로 계정 한 개·가족 한 개·구성원 네 명을 생성하고, 네 구성원 ID로 식사 세션을 만드는 테스트를 추가했다.

### 3. 저장소 전달과 Supabase 공유 정보 확인

- 처음 AI가 brian180099/KINI 포크에 올린 뒤 팀 저장소 Dajeong0315/KINI가 대상임을 바로잡았다. 팀 저장소 푸시는 쓰기 권한 부족으로 403이었으며 협업자 초대 수락 후 성공했다.

- Supabase KINI의 프로젝트 주소·공개 클라이언트 키를 팀에 전달할 수 있도록 확인했다. 키 원문은 이 기록에 포함하지 않는다. 당시 읽기 전용 조회에서 public 앱 테이블 14개 모두 RLS가 활성화돼 있고 anon/authenticated의 SELECT 권한이 없음을 확인했다. 이 대화의 작업으로 DB 권한·데이터를 변경하지 않았다.
- 공개 키와 서버 비밀 키, 로컬 가구 토큰이 서로 다름을 설명했다. 공개 키만으로 DB 테이블을 직접 조회할 수 있는 상태로 오해하지 않도록 했다.

- B와 확인할 내용: 같은 가구의 applied 출고 ID를 완료 요청 inventory_event_ids에 연결하며, 완료 단계에서 다시 재고를 차감하지 않는 계약 유지.

- 현재 기록은 본 대화의 11월 26일 작업과 저장소 근거에 한정한다. 다른 대화에서 수행한 후속 PostgreSQL 이관·AI 작업과 카탈로그 작업의 개인별 분담는 추가 확인이 필요하다.

## 포트폴리오 메모

- 내부 함수 테스트가 통과해도 화면에서 실제 호출할 HTTP 인증 경로가 없으면 업무 흐름이 완성되지 않음을 확인했다. HTTP 로그인 응답부터 재고·출고·조리 완료까지 검증 기준을 바꾸고, 첫 사용자 계정과 가족 구성원 프로필을 분리해 서버 온보딩을 확장했다. 합성 데이터 기준 226개 테스트 통과와 재고 스냅샷 동일성으로 기능·권한·일관성을 확인했으며, AI 구현 지원·기존 팀 기여·브라우저/운영 검증의 한계를 구분했다.
