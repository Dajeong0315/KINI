### 2. 추천·안전·데이터 운영 기반 통합

- 기존 `official_*` 조회와 A 공개 `catalog_*`의 책임을 provider 계약으로 정리하고, 승인된 published 카탈로그 및 검토된 재료 매핑을 추천 영양에 사용하도록 진행했다. 미검증·누락·부피 기준 자료를 무조건 g 영양 계산에 넣지 않고, fallback은 데모 상태를 표시하거나 후보를 제외한다.
- 추천 1인분, 이번 조리 전체 재료 g, 구성원별 실제 섭취 인분을 분리했다. 재고는 A 출고 확정에서 한 번만 감소하고 B 완료는 출고 연결·섭취 저장만 수행한다.

### 4. PostgreSQL 저장·권한 기반과 재고 동시성

- 문서/코드 초안의 SQLite 시험 통과만으로 PostgreSQL 이전을 완료 처리하지 않았다. 이동된 worktree에 설계 문서가 없을 때는 복원 확인 후 재개했고, 실제 DB 환경 부재도 미완료 원인으로 명시했다.
- Docker Desktop Linux engine의 일회성 `postgres:16-alpine`에서 PostgreSQL **16.15**를 사용해 합성 두 가구의 로그인·저장·조회·접근 권한·rollback·migration 재실행을 검증했다.
- SQLite `?`/PostgreSQL `%s`, Boolean, `RETURNING id`/lastrowid, tuple·mapping 행, 연결 재사용과 트랜잭션 경계를 보완했다. PostgreSQL 요청 중 DDL/demo seed를 막고 `scripts/run_migrations.py`를 명시적 적용 경로로 둔다.
- `BEGIN`만으로 PostgreSQL 출고 경쟁이 직렬화되지 않는 문제를 확인했다. `FOR UPDATE`, 잔량 조건부 갱신, 동일 client_event_id의 멱등 접수로 재고·이벤트·이력·버전을 원자적으로 처리했다.
- 독립 DB 연결과 barrier를 사용한 동시성 **6개 시나리오 × 10회 = 60/60**을 검증했다. 단일 연결의 순차 호출을 동시성 시험으로 표시하지 않았다.
- 1,000g에서 700g씩 동시 출고하면 한 건만 반영돼 300g이 남는다. 400g+300g은 순서와 무관하게 300g, 이력 2건·버전 2가 된다. 확정/거절 경쟁과 중간 DB 오류의 전체 rollback도 확인했다.
- 근거 커밋: `05c7105`, `3ebfcee`, 통합 `412e1f9`; [PR #32](https://github.com/Dajeong0315/KINI/pull/32)로 main 반영.

### 5. Vision A 이벤트 최소 연결과 남긴 경계

- 보고받은 기존 Vision 연결 코드의 원격/로컬 사본을 찾지 못해, 복원했다고 표현하지 않고 main A 계약에 맞는 최소 클라이언트를 새로 작성하도록 진행했다(`e67b0d2`).
- 합성 Vision 입력 → 실제 루프백 HTTP → PostgreSQL pending → 사용자 재료·중량 확인 → 확정 경로를 검증했다. 인식 접수·거절만으로 재고는 바뀌지 않는다.
- 로컬 클라이언트는 loopback HTTP만 허용하고 redirect를 따라가지 않는다. 토큰은 파일/큐에 남기지 않으며 재시도는 같은 이벤트 ID를 사용한다. 큐는 성공 항목만 제거하고 401/403/409의 미처리 항목을 보존한다. 기존 A 계약의 만료 세션 403과 새 조회 API의 401을 구분한다.
- 실제 카메라·YOLO 실행/정확도를 이 합성 입력 통합 결과로 주장하지 않는다. 조민준의 OCR·인식 평가 수치는 별도 팀원 성과다.
- 별도 `feature/fridge-vision-yolo`의 main 미반영 두 커밋을 검토했다. Supabase 별도 재고 직접 변경·개수 기반 수량·자동 확정 경로가 현재 A 단일 재고 원칙과 달라 **그대로 병합하거나 삭제하지 않았다.** 민준에게 A 이벤트 계약으로 맞추는 일을 요청하기로 했다. 이 확인은 코드 검토이며 해당 Vision 프로그램을 실행하거나 Supabase에 적용한 것이 아니다.

- 조리 완료에서 재고를 다시 차감하지 않는다. 합성 1인 사례는 1,000g → A 100g 출고 후 900g → B 완료 후 900g이다. 2인 조리 전체 200g 출고 후 [1.5인분, 0인분] 저장도 남은 재고를 바꾸지 않는다.
- A 출고와 B 완료는 별도 트랜잭션이다. B 실패는 B 기록/연결만 rollback하며 이미 확정한 A 출고를 자동 취소하지 않는다. 실패 재시도에 새 출고를 추가 생성하지 않는다.
- 리포트는 현재 레시피로 과거 영양을 재계산하지 않는다. 0인분과 누락 영양을 구분하고, 누락은 null/부분 합계/품질 상태로 표시한다. week는 KST 오늘 포함 최근 7일이다.
- 재료 검색은 활성 재료 최대 30개·바인딩된 부분 문자열 검색이다. g/kg와 ml/L를 분리하고, 개·컵은 검증된 재료별 근거가 없거나 충돌하면 실측 확인을 요구한다. 조회 API가 재고를 자동 확정하지 않는다.
- 후반 PostgreSQL 단위에서 C 화면·스타일·UI 시험 파일은 수정하지 않았다. 기존 C 호출의 토큰 전달과 새 GET 화면 연결은 계약 문서에 남겼다.
- 서버 구현의 단위 완료와 실제 Supabase 적용 완료를 구분했다. 최종 main의 명시적 migration 범위는 **001~008**이다.
- 모든 레거시 API의 PostgreSQL 이전이 끝났다는 뜻은 아니다. 직접 `POST /api/meal-records` 등 미지원 경로는 501을 유지하며, 기록 생성은 검증한 조리 완료 흐름을 사용한다.

미완료는 팀원을 모두 기다려야 한다는 뜻은 아니다. 구매 제안과 배포 준비는 독립 진행할 수 있으며, 정책/계정/인식 출력이 필요한 최종 연결만 담당자와 맞춘다. 식후 피드백·구매 제안·선제적 질문·실제 클라우드 운영을 오늘 완료된 PostgreSQL 단위에 소급해 포함하지 않는다.

## 포트폴리오 메모

- 문제: SQLite 데모·서로 다른 재고 경로·역할별 브랜치를 합치는 것만으로는 클라우드 식생활 서비스의 저장·가구 권한·중복 차감을 보장할 수 없었다.
- 본인의 행동: A·B 통합 책임과 서버/화면/Vision 경계를 정하고, 실DB 시험과 한 단위 완료 기준을 요구했다. AI와 함께 migration·권한·원자성·저장 스냅샷·API 계약을 기능별로 검증하고 main에 통합했다.
- 결과: 합성 데이터·PostgreSQL 16.15·루프백 HTTP 조건에서 최종 250개 DB 시험, 일반 회귀 296개, Node 35개가 통과했다. A 출고와 B 섭취 기록을 분리하고 조회에서도 재고 불변을 확인했다.
- 배운 점: mock 통과·실DB 통과·운영 적용·실제 인식 성능은 서로 다른 증거다. “완료”는 시험 범위·main 반영·미연동 경계를 함께 설명해야 팀과 다음 단계를 합의할 수 있다.
